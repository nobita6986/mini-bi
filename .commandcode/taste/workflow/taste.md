# Workflow

- Requires a mandatory preflight before starting any task: verify the correct repo, worktree, branch, base SHA, clean working state, and (where applicable) migration ledger. Confidence: 0.9
- Expects requirements, AGENTS.md, and related documentation/handoffs to be read thoroughly before beginning work. Confidence: 0.8
- Never works directly on the primary checkout; creates a clean worktree plus a dedicated branch from the current origin/main for each task. Confidence: 0.9
- Keeps scope tight: does exactly one assigned task, does not expand scope, does not do another task's work, and does not change locked contracts. Confidence: 0.8
- Must not touch Production (no reads/writes), apply migrations, deploy, or run browser/UAT unless explicitly assigned. Confidence: 0.9
- Preserves others' changes; if the worktree contains changes outside the task scope, stop and report rather than proceeding. Confidence: 0.8
- On blockers or factual contradictions, only surveys/investigates and reports evidence — never guesses or unilaterally changes the contract. Confidence: 0.8
- Operates in a hierarchical multi-agent model where an orchestrator assigns single, tightly-scoped "lanes" to named agents, each on an isolated worktree/branch. Confidence: 0.7
- Requires contract/design documents to be internally consistent (no contradictions between sections, invariants, totals, and acceptance criteria) and treats such inconsistencies as blocking before implementation may start. Confidence: 0.75
- Tracks iterations with explicit revision numbers and status tokens (e.g. R7 → R8, `..._REVIEW_CHANGES_REQUIRED_AWAITING_R8` → `..._PASS_AWAITING_T0_REVIEW`) and expects an append-only revision log documenting what each pass closed. Confidence: 0.6
- When a contract/spec advances across revisions, actively sweeps for and retires stale wording left behind by earlier revisions (e.g. outdated field/key counts or a listed set of fields that grew), and confirms via a content scan that current sections no longer contain the stale phrasing while all affected sections stay consistent. Confidence: 0.65
- Treats revision-history/review-log text as an immutable historical record: legitimate historical mentions (even when they quote now-outdated terms) are left as-is and not mechanically rewritten during a cleanup pass. When a later revision supersedes an earlier revision's wording, keeps the original text in place and adds an explicit `[SUPERSEDED by Rn …]` marker (rather than deleting or rewriting it) while also noting which earlier locks remain unchanged. Confidence: 0.6
- Pins the authoritative spec/master-plan document by absolute path + SHA-256, verifies the actual file hash matches before acting, and records the authority path + hash in the revision log as the basis for the change. Confidence: 0.6
- Requires the focused lane to pass first, then runs the canonical full test suite once before handoff; if a failure is pre-existing / outside the diff, proves it against a pristine base rather than claiming it is unrelated. When a task is scoped to only focused + related lanes, expects an explicit statement of whether the canonical suite was run and of any known pre-existing blockers. Confidence: 0.75
- Requires mutation probes: reintroduce the original bug/mutation and confirm the new regression test goes red, then restore the source byte-identical and re-confirm green. The user repeatedly issues the probes as mandatory RED evidence with byte-identical restoration after every probe. Confidence: 0.8
- Runs a fixed gate set before handoff: focused lane, related regression lane, typecheck, lint, build, docs:check, secrets:check, offline migration validation (no DB access), and git diff --check.
- When a required gate cannot run because of a missing dependency/tooling blockage, records the exact failure and reports it as-is; never installs dependencies on its own, never silently skips a gate while claiming a pass. Confidence: 0.7 Confidence: 0.75
- In a fresh worktree, runs `next typegen` before typecheck (Next's generated types are otherwise missing). Confidence: 0.6
- Requires a regression test that drives the real end-to-end path (e.g. repository result → API response → client projection) rather than isolated units, and keeps existing strict tests green. Confidence: 0.7
- When a task splits into an unblocked part and a part blocked by a missing backend/authoritative contract, completes and verifies the unblocked part independently, then reports precisely which part is blocked and what contract/projection is still required — never faking the missing contract with mock data or an invented shape, and never claiming the whole lane complete while a part remains blocked. Confidence: 0.75
- When adding a migration, rebaselines every canonical migration-ledger pin across the test suite (count pins like `length, 85`, from-end position pins like `names.length - (N)`, and tail pins like `.at(-N)` / `slice(0, -N)`), and never edits unrelated source just to make a lane green. Confidence: 0.7
- Registers each new focused test lane exactly once in the canonical `pnpm test` chain. Confidence: 0.7
- Prefers tracing symbols with a code-graph tool (CodeGraph) before falling back to grep/read. Confidence: 0.6
- In a fresh isolated worktree, reuses the primary checkout's `node_modules` (junctioned) rather than reinstalling dependencies; in such a worktree the production build is run with the Webpack opt-out (`next build --webpack`) because Turbopack cannot handle the junctioned `node_modules`. Confidence: 0.55

- Expects a survey/reuse memo to ground every claim in exact file/symbol references and to include a call/component graph, a reuse matrix (reuse unchanged / extend / new sibling / do-not-reuse), the smallest per-feature file-touch set, an accessibility contract, a loading/error/empty/conflict/retry state map, an acceptance-test + mutation-probe plan, the explicit backend-contract blockers, a data relationship map, a smallest-safe-scope section, an explicit list of decisions requiring T0/Owner approval, migration impact, an acceptance/mutation matrix, and a proposed implementation ordering. Confidence: 0.7
- When the base branch has advanced, diffs the new base against the previously surveyed/cited files and stops to report to the orchestrator (T0) if any cited file changed, proceeding only when no cited file was modified. Confidence: 0.6
- Actively trims scope to a minimal MVP: moves out-of-MVP capabilities (e.g. zoom/fullscreen, extra charts, period comparison, new helper layers) to an explicit deferred list, keeps them out of the touch set and acceptance contract, and warns against building more abstractions than one small component needs. Confidence: 0.6
- Expresses ownership of a backend contract in architecture/handoff documents by a stable contract/role label (e.g. "W2-S0-B backend contract", "T0-accepted backend decision") rather than by the name of the agent currently assigned to it — backend trust is expressed deontically, not by state, and the long-term architecture must not depend on agent names since assignments rotate. Confidence: 0.65
- In a targeted follow-up repair, changes only the requested items and leaves all previously-accepted corrections untouched (explicitly "không thay đổi các correction R1 khác"); the follow-up is layered append-only on top of earlier passes rather than rewriting them. Confidence: 0.6
- Before editing framework code (e.g. Next.js components), reads the matching guide bundled in the framework's own docs (e.g. `node_modules/next/dist/docs`) as directed by AGENTS.md, and consults the CodeGraph index first when the repo has one. Confidence: 0.6
- Never performs browser/UAT itself — the Owner is the only one who runs UAT — and instead hands off a written, step-by-step UAT checklist (happy path + negative permission cases, reviewer before/after, conflict/OCC, audit) for the Owner to execute. Confidence: 0.7
- Writes a dedicated implementation handoff doc under `docs/handoffs/<slug>.md` (status token, base/impl SHA, branch/worktree, preflight findings, contract reuse, file list, test/gate results, mutation evidence, risks, and an Owner UAT checklist), separate from the chat completion report. Confidence: 0.65
- For identity/account audits, operates strictly read-only: never changes Git/CLI config, never commits/pushes, never invites members, never redeploys, and never modifies data. Confidence: 0.85
- Never discloses passwords, tokens, API keys, environment values, or .env/auth contents in reports. Confidence: 0.9
- Checks the active GitHub CLI account via `gh auth status --active` and `gh api user --jq .login` (never `--show-token`, never printing tokens), and the active Vercel CLI account via `vercel whoami`. Confidence: 0.7
- For a follow-up/continuation task on an existing lane, resumes on the same branch/worktree as the prior pass (no new branch): first verifies the actual HEAD and working-tree status, keeps the previously-completed work intact, and fast-forwards on top of it rather than re-implementing or rewriting the already-pushed history. Confidence: 0.75
- When the focused lane(s) already pass, is comfortable pushing the branch and letting GitHub CI run the full/remaining suite instead of always running the whole suite locally, and reports the CI result honestly. Confidence: 0.6
- Applies mutation probes at the TypeScript/API/UI layer as well (not only the DB), targeting security invariants such as removing an authority/provenance guard, firing an external Auth call a second time after claim-loss, or leaking a secret (password/auth_subject). Confidence: 0.6
- Counts a mutation probe as valid evidence only when it actually turns the focused lane red; a probe that stays green because an earlier guard already rejects the input is removed and the reason reported honestly rather than claimed as a passing check. Confidence: 0.6
- When summarizing work-in-progress state, keeps an explicit live todo list with completed/in-progress/pending statuses and activeForm labels, and updates it as each phase (preflight → recon → design → implement → tests → gates → handoff) completes. Confidence: 0.6
- When a locked contract contains a genuine internal contradiction (e.g. a strict interval rule vs. a same-day immediate-revoke requirement), does not pick a side silently: checks upstream/survey sources for the intended resolution, then stops implementation and escalates with a structured decision question presenting the viable options (with trade-offs and an explicit recommendation), and implements only the resolution the orchestrator/owner approves. Confidence: 0.65
- When a task is re-issued (duplicate/redispatch, possibly citing a stale HEAD), first verifies the actual branch HEAD, clean-worktree state, and current source for the requested change, and reports it as already completed with concrete evidence (commit SHAs, source matches, prior gate results) rather than re-implementing it or creating duplicate commits. Confidence: 0.6

Confidence: 0.65
