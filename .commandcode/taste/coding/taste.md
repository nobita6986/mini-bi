# Coding

- Strongly prefers reusing existing code, components, helpers, test patterns, and libraries; new code and abstractions should be minimized and avoided unless truly necessary. Confidence: 0.9
- Explicitly rejects creating new frameworks or unnecessary abstractions, and building parallel/second implementations of mechanisms that already exist. Confidence: 0.8

- Keeps shared/common utilities (e.g. the shared filter parser and its types) unchanged and unpolluted by feature-specific concerns; a feature's extra needs (pagination, drill-down fields) go into a thin dedicated adapter that reuses the shared code rather than extending the shared abstraction. Also wants strict allowlists and rejection of fields outside them. Confidence: 0.7
- Requires each API/route endpoint to enforce its own authentication guard itself (e.g. call the session guard directly) instead of relying on an upstream/page-level gate, and to never trust client-supplied actor/audience/authority. Confidence: 0.8
- Marks fields that are needed only server-side explicitly as server-only/internal and keeps them off the wire; adds such explicit fields to the data contract when required to implement a behavior without a client-side join or an external catalogue call. Confidence: 0.6
- Strongly prefers the smallest possible diff to fix a bug ("chọn diff nhỏ nhất"), and avoids touching anything beyond the necessary change (e.g. no changes to user-facing warning copy or the confirmation flow beyond what's required). Confidence: 0.85
- Fixes wire/contract mismatches on the producer side (e.g. drop the offending extra field from the response) while keeping the consumer's strict exact-key projection intact, rather than loosening the consumer validation to tolerate extra fields. Confidence: 0.7

- Dislikes introducing new static maps or fallbacks; prefers deriving values from the canonical source. Confidence: 0.6
