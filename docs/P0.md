# P0 — Foundation: Kế hoạch thực thi cho AI Coding Web và AI Assistant n8n

| Thuộc tính | Giá trị |
|---|---|
| Phiên bản | 1.0 — 01/10/2026 |
| Baseline | `master-plan.md` v1.0 |
| Trạng thái | Kế hoạch triển khai; chưa xác nhận môi trường hay nghiệp vụ nguồn |

| Owner Pipeline | AI Assistant n8n, viết tắt **N8N** |

Tên file kế hoạch phase chính thức là `P0.md`; dùng tên này thay cho tên dự kiến `phase-0-plan.md` trong master plan. Tài liệu này hướng dẫn thực thi, chưa tạo code, database, workflow hoặc deployment.

## 1. Kết quả phải đạt

P0 tạo nền kỹ thuật đủ để P1 bắt đầu làm dashboard với dữ liệu thật. Khi hoàn thành, đội có:

1. Repository và web app chạy local, build được và có URL test.
2. Môi trường DEV được cô lập; cấu hình PROD được tài liệu hóa, không dùng credential DEV cho PROD.
3. Supabase schema tối thiểu qua migration, seed test và contract v0.1.
4. Một Sheet test có khóa dòng ổn định; workflow đọc, validate và ghi dữ liệu qua contract.
5. Trang kiểm tra pipeline đọc dữ liệu từ DB, có trace về nguồn và run.
6. Chạy lại không nhân đôi dữ liệu; lỗi đầu vào có lý do; lỗi kết nối không bị báo thành thành công.
7. Gói bàn giao gồm code, workflow export, cấu hình mẫu, bằng chứng kiểm tra và hướng dẫn chạy lại.

**Không coi UI dùng mock hoặc chỉ node Supabase ghi thành công là hoàn thành P0.** Bằng chứng chính là dữ liệu từ Sheet xuất hiện trên URL web đã triển khai.

## 2. Scope và giới hạn

### Làm trong P0

- Khảo sát mẫu nguồn và môi trường; chốt contract tối thiểu.
- Next.js/TypeScript, Tailwind, một số component shadcn/ui và Supabase SDK.
- Schema nguồn, master data cần cho mẫu test, facts và sync logs tối thiểu.
- Google/Supabase credentials, workflow một nguồn theo cấu hình.
- Manual trigger để kiểm thử; cấu trúc cho lịch chạy sau này.
- Validation, idempotency, trace và nhánh lỗi căn bản.
- Layout nền và trang kiểm tra pipeline, không phải dashboard BoD hoàn chỉnh.
- GitHub, Vercel, env mẫu và hướng dẫn phục hồi/chạy lại tối thiểu.

### Chuyển sang phase sau

| Hạng mục | Phase |
|---|---|
| Trend, ranking, filter đầy đủ, drill-down BoD | P1 |
| Loop N nguồn, incremental sync, reconciliation, retry nâng cao, monitoring UI | P2 |
| Auth người dùng, user-role, RLS theo BoD/Leader/Staff | P3 |
| Target, KPI engine, form và performance | P4 |
| Commission/Payroll | Ngoài V1 |

P0 vẫn phải chặn truy cập DB không hợp lệ và bảo vệ credentials. Việc dời phân quyền người dùng sang P3 không có nghĩa mở tables cho anonymous. Không triển khai business logic KPI/hoa hồng/lương ở đây.

## 7. Contract tối thiểu: đề xuất để Agent chốt

### 7.1. Grain và dữ liệu test

Đề xuất test: **một dòng là một kết quả độc lập có `record_key` ổn định, ngày nghiệp vụ, nhân viên, project và một giá trị test**. Chỉ số `test_amount` không khẳng định là doanh thu hoặc tiền công ty. Grain production được chốt lại sau khi xem mẫu thật, giữ contract có version.

Sheet test đề xuất:

| record_key | business_date | employee_code | project_code | metric_code | value | unit |
|---|---|---|---|---|---|---|
| TEST-001 | 2026-10-01 | NV_TEST_01 | PR_TEST_01 | test_amount | 1000000 | TEST_UNIT |
| TEST-002 | 2026-10-01 | NV_TEST_02 | PR_TEST_01 | test_amount | 2000000 | TEST_UNIT |
| TEST-003 | 2026-10-01 | NV_TEST_01 | PR_TEST_01 | test_amount | abc | TEST_UNIT |

Master data seed chỉ là test, không giả làm danh sách nhân viên thực. Dữ liệu fixture nằm trong Sheet riêng. Số hàng chỉ dùng làm locator để tra lỗi; khi sort/chèn hàng, khóa không đổi.

### 7.2. Schema logic tối thiểu

WEB chuyển mô hình sau thành DDL phù hợp sau C01, không coi đây là SQL đã triển khai.

| Entity | Nội dung tối thiểu | Constraint/ý nghĩa |
|---|---|---|
| `employees` | ID, code, display name | Code unique trong scope công ty đã chốt |
| `teams` | ID, code, name | Seed nếu cần kiểm tra team |
| `projects` | ID, code, name | Project code không suy từ tên |
| `data_sources` | ID, type, spreadsheet/tab locator, mapping version, active | Không chứa secret; một nguồn test ở P0 |
| `result_records` | ID, source/key, employee/project IDs, business date, metric/unit/value, raw reference, run ID, timestamps | Unique `(source_id, source_record_key)` cho grain test; FK tới master/source/run |
| `sync_runs` | Run ID, source, version, start/end, status, counters, error code | Run trace và trạng thái độc lập với fact |
| `sync_errors` | Run/source/key/row locator, code, reason | Raw lỗi test có thể lưu; giới hạn/redact trước dữ liệu thật |

Nếu một dòng nguồn có nhiều metrics, phải điều chỉnh grain và unique key trước ingest; không dùng khóa đề xuất để ghi đè các metric khác nhau. Không thêm bảng KPI/commission/payroll. Team assignment không suy từ `employees.current_team`; nếu seed team vào facts, ghi bối cảnh test rõ ràng và chuẩn bị effective-date model khi vào P2.

### 7.3. Canonical payload đề xuất

```json
{
  "contract_version": "0.1",
  "run_id": "<uuid-of-active-run>",
  "source_id": "<uuid-of-registered-source>",
  "source_record_key": "TEST-001",
  "business_date": "2026-10-01",
  "employee_code": "NV_TEST_01",
  "project_code": "PR_TEST_01",
  "metric_code": "test_amount",
  "value": "1000000",
  "unit": "TEST_UNIT",
  "raw_reference": { "tab": "P0_TEST", "row_number": 2 }
}
```

UUID placeholders phải được thay bằng ID thật khi chạy. Chuỗi `value` là decimal chuẩn, không dấu phân nhóm; DB dùng numeric phù hợp độ chính xác đã chốt. Raw text từ Sheet được normalize theo định dạng nguồn rõ ràng; số mơ hồ bị reject, không tự đoán. Ngày phải là ngày hợp lệ, không chỉ khớp regex. Giá trị 0 hợp lệ cho fixture; thiếu giá trị không biến thành 0. Chính sách số âm ở dữ liệu thật chưa được xác nhận.

N8N normalize và kiểm tra sớm; DB kiểm tra cuối cùng, resolve code sang master ID và từ chối code không biết. Contract phải nêu version không hỗ trợ sẽ bị reject; không âm thầm parse như v0.1.

### 7.4. Response và idempotency

RPC trả outcome `inserted`, `updated`, `unchanged` hoặc `rejected`, record ID nếu có, error code/reason nếu lỗi. Tên và cấu trúc JSON cuối cùng được khóa ở C01.

- Cùng source/key và canonical business fields giống nhau: `unchanged`; fact count và tổng không tăng.
- Cùng source/key nhưng giá trị đổi: `updated`; cập nhật cùng fact, giữ created time và last-changing run. Run mới vẫn ghi log, không cần sửa fact để chứng minh đã đọc lại.
- Hai dòng cùng key trong một lần đọc: reject các dòng thuộc key xung đột trước write; không chọn tùy tiện dòng cuối.
- Ghi thành công nhưng mất response: replay có thể trả `unchanged`; được coi accepted sau DB xác nhận, không ghi thêm fact.
- P0 không hỗ trợ sync cùng nguồn đồng thời; DB/run control phải chặn hoặc tuần tự hóa, không chỉ dựa vào thao tác thủ công.
- Không hard-delete facts khi một dòng vắng mặt. Delete/revision audit đầy đủ nằm P2; P0 log outcome/run đủ chứng minh update test.

## 8. Run logs và lỗi

### 8.1. Trạng thái

| Status | Khi dùng |
|---|---|
| `running` | Đã bắt đầu run; chưa xác nhận kết thúc |
| `succeeded` | Đọc hoàn tất, mọi dòng dữ liệu hợp lệ được DB xác nhận; không có rejects/write failure |
| `partial` | Đọc hoàn tất; một số dòng bị reject, các dòng hợp lệ đã được xác nhận |
| `failed` | Không đọc được nguồn, DB/kết nối lỗi hoặc run chưa hoàn thành toàn bộ bước ghi |

Run bị dừng đột ngột có thể còn `running`; hướng dẫn phục hồi phải có cách đánh dấu failed/stale sau khi xác nhận không còn execution. Timeout detection tự động có thể hoàn thiện P2. `last_successful_sync` chỉ lấy từ run `succeeded`; đồng thời hiển thị run `partial/failed` gần nhất, không che lỗi bằng thời gian thành công cũ.

### 8.2. Counters

`rows_read` đếm dòng dữ liệu không rỗng; `rows_accepted = inserted + updated + unchanged`; `rows_rejected` là lỗi validation; `rows_write_failed` là lỗi ghi đã xác nhận; `rows_unprocessed` là dòng chưa xử lý do run dừng. Khi run được đóng, các nhóm phải cộng lại bằng `rows_read`; write không rõ outcome sau mất kết nối được ghi riêng trong reason và giải quyết bằng replay, không báo thành inserted chắc chắn.

### 8.3. Error codes đề xuất

| Code | Ý nghĩa | Xử lý |
|---|---|---|
| `MISSING_RECORD_KEY` | Thiếu khóa | Reject dòng |
| `INVALID_DATE` | Ngày sai/không hợp lệ | Reject dòng |
| `INVALID_VALUE` | Số thiếu/sai/mơ hồ | Reject dòng |
| `UNKNOWN_EMPLOYEE` / `UNKNOWN_PROJECT` | Code chưa có master | Reject; không tự tạo master |
| `DUPLICATE_KEY_IN_SOURCE` | Khóa trùng trong run | Reject các dòng xung đột |
| `UNSUPPORTED_CONTRACT_VERSION` | Contract không tương thích | Dừng phần write, báo lỗi |
| `SOURCE_READ_FAILED` | Google/permission/network | Fail run; không suy thành xóa |
| `DB_WRITE_FAILED` | DB/network/grant | Fail run; replay sau sửa |
| `SOURCE_RUN_ALREADY_ACTIVE` | Nguồn đang sync | Không mở run thứ hai |

Log tối thiểu chứa run ID, source ID, stage, code và sanitized reason. Không log access token, authorization headers, full credential hoặc SQL connection string. Không gửi alert ra Slack/email trong P0 khi chưa được cấu hình và cho phép; execution log/DB log là đủ cho test.

## 11. Secrets và môi trường

- DEV và PROD dùng credentials/DB/source config riêng; local và preview dùng DEV hoặc database test.
- Public env chỉ chứa cấu hình thực sự public. DB reader secret và credential ingestion chỉ ở server/n8n.
- N8N cần quyền Google đọc Sheet và quyền ghi qua ingestion boundary; không cần quyền DDL hay deploy web.
- Web runtime cần quyền đọc reporting, không cần credential Google hoặc credential ingestion.
- Nếu tích hợp hiện tại buộc dùng Supabase key đặc quyền, ghi rõ key có thể bypass RLS và chỉ giữ trong môi trường server; đó không phải credential hạn chế quyền. Không coi RPC tự động làm key đặc quyền thành ít quyền. WEB phải kiểm soát API server, grants và ghi kế hoạch giảm quyền.
- Trang/API private phải gate trước query và không cache dữ liệu riêng cho người khác. URL public P0 chỉ được dùng synthetic test data; DB vẫn deny anonymous direct access.
- Log/export/docs không có giá trị secrets; secret scan gồm kiểm tra thủ công các Code/HTTP nodes và env files.
- Chỉ ghi manifest tên biến/credential, nơi cấu hình, owner và mục đích; không ghi token.

PROD readiness ở P0 là env map và quy trình cấu hình riêng. Nếu đã provision PROD, phải kiểm tra cô lập; không bắt buộc sync dữ liệu thật lên PROD để đóng P0.

## 12. Mẫu handoff và quy trình xử lý blocker

Mỗi handoff ghi:

```text
Task ID / status: done | blocked | needs-review

Contract / mapping version:
Commit SHA hoặc workflow version:
Deliverables và đường dẫn:
Checks đã chạy + evidence:

```

Nếu thiếu quyền/môi trường, Agent hoàn thành phần độc lập, giao artifact và ghi chính xác thao tác đang bị chặn. Không tự đánh dấu task tích hợp done chỉ vì đã viết docs. Nếu mapping cần đổi contract, N8N gửi request gồm sample, field cần đổi, lý do và ảnh hưởng; WEB cập nhật contract/migration/fixtures, hai bên review trước write.

Rollback P0: dừng trigger → lưu logs và version hiện tại → revert code/workflow sang version đã kiểm tra → áp dụng migration sửa có kiểm soát khi cần. Không xóa toàn bộ schema hoặc reset DB dùng chung. Chỉ reset dataset test cô lập theo runbook; không suy diễn quyền xóa dữ liệu thật.
