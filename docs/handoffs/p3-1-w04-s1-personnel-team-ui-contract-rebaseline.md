**Shared API boundary for all rows:** each route returns `NOT_FOUND` (404) unless `DIRECT_ENTRY_API_ENABLED === "true"`; enabled routes resolve a server session and pass only its trusted actor identifiers to the repository. Mutations additionally require same-origin/CSRF validation, JSON content type, bounded JSON, strict exact-key parsing, recursive rejection of client authority fields (`CLIENT_AUTHORITY_FIELD_FORBIDDEN`), and a matching optional `Idempotency-Key` header. GETs do not require an Origin header. The API/repository does not authorize from UI state: the canonical database catalog-operator guard is authoritative.

Sanitized response taxonomy: malformed payload/query or header mismatch → entity `*_INVALID` / `IDEMPOTENCY_KEY_MISMATCH` (400); recursive authority injection → `CLIENT_AUTHORITY_FIELD_FORBIDDEN` (400); unauthenticated → 401; CSRF or catalog guard deny → 403 (`CSRF_REJECTED` / entity `*_DENIED`); absent/ineligible target → entity `*_NOT_FOUND` (404); stale OCC, unique collision, interval overlap, or reused idempotency key with different content → entity `*_CONFLICT` (409); unclassified RPC/session failure → entity `*_UNAVAILABLE` (500). Raw SQLSTATE messages, reason text, and raw database errors are not returned. Empty means a successful list with zero total; denied, not-found, and unavailable remain their own states.

## D. UI information architecture

1. A single Admin entry opens `/admin`; its internal sub-nav exposes only sections allowed by the server-derived Admin-area projection.
2. Admin landing provides catalog navigation. Personnel and Teams are separate catalog pages; create/edit/set-active are row-level dialogs, not a generic CRUD framework.
3. Membership is personnel-contextual: select/open a Personnel row, then show its current, scheduled and history intervals and offer assign/move/unassign/cancel. The membership API returns `recruiter_id` and `team_display_name`, but **not** recruiter display name. Do not render IDs as names or fetch one detail request per row. Keep the UI anchored to a selected Personnel whose authoritative label is already loaded; use the returned Team label for the team side. A future roster-wide screen would require a deliberately reviewed projection contract, not hidden N+1 reads.
4. Team page initially owns Team master fields only. W01C-A `getTeam` is not a roster or leader projection; do not promise roster/leader panels from it.
5. Deactivated Personnel and Teams remain visible when the page requests inactive rows; they are not hard-deleted and remain available for historical context.

## F. Interaction and error states

- Every mutation requires a nonblank reason shown in its confirmation form/dialog.
- Generate one idempotency key per user intent; preserve it for retries of that same intent. A newly edited/resubmitted intent gets a new key. If an `Idempotency-Key` header is sent, it must equal the body key.
- Include the last authoritative entity version. On OCC conflict, disable all mutations for that entity until a successful authoritative reload supplies the new version. A failed reload keeps the mutation lock.
- No hard delete. Use set-active only. Inactive Personnel and Teams remain readable for history; inactive teams are not valid new membership targets.
- Keep loading, empty, denied, unavailable, generic error and mutation conflict visually and semantically distinct. In particular, a 403 is never “0 records”; a successful zero-count list is empty; a 404 detail is not an empty list.
- Membership intervals are half-open and grouped by the server state. Moving closes the previous interval; unassign/cancel closes it; do not rewrite historical attribution. Closing membership remains possible when a person's creation eligibility has changed; assign/move remain subject to the backend HRP and active-subject checks.
- Show business labels when known. Never display a technical identifier in place of an available Personnel or Team label. Do not expose raw database errors or reason/audit internals in a UI error.
- Keep forms and tables semantic and keyboard operable; dialogs have associated labels, announced errors, predictable focus return, and no color-only state. Responsive/mobile and accessibility acceptance are Owner UAT responsibilities; this agent must not run browser, Playwright, CUA, or UAT.
