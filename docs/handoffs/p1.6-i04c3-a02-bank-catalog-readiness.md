### Q2. Why does banks=0 block only payment-bearing rows rather than every full-profile row?

Because **the empty catalog only blocks rows where `payment.state = 'provided'`**. There are three independent failure modes and the catalog gates only the third:

| Row shape | Empty bank catalog effect | Source |
| --- | --- | --- |
| No `payment` field at all | passes (no catalog call) | `src/lib/direct-entry/payment-api.ts:127` (`if (parsed.payment.state === "provided")`) |
| `payment.state` ∈ `{ omitted, unknown, intentionally_blank }` | passes (catalog lookup is **skipped**; only the API shape `projectPaymentInput` runs, which accepts null fields) | same |
| `payment.state` = `provided` with a `bank_id` | **rejected** with `BANK_INVALID` 400 by the API layer (because `activeBankIds` set is empty) | same; test `payment-api.test.mjs:165–176` |
| `payment.state` = `provided` (DB layer, hypothetically bypassing API) | **rejected** by DB trigger `direct_entry_payment_active_bank` with `23514 bank is not active` | `20261002170000_…:617–633` |

R3A's preview UI independently **disables the CTA** when any row needs bank resolution and `source.banks.length === 0`, but this is a UI safeguard — it does not change the write path. A non-payment-bearing full-profile batch is fully functional today (it skips the bank catalog entirely) and is the primary path for I04C3 non-payment acceptance.

**Net effect**: I04C3 **non-payment batch** can continue while banks remain empty; only rows that include `payment.state = 'provided'` are blocked.

### Q6. Can I04C3 non-payment batch continue while banks remain empty?

**Yes**. The non-payment batch path does not touch `direct_entry_banks`:

- A full-profile batch without any `payment` field is accepted (no catalog call).
- A full-profile batch with `payment.state` ∈ `{ omitted, unknown, intentionally_blank }` is accepted (no catalog call; only `projectPaymentInput` shape check).
- A full-profile batch with `payment.state = 'provided'` is **rejected** with `BANK_INVALID` 400.

**Conclusion**: I04C3 non-payment acceptance can proceed on the **full-profile RPC** (`direct_entry_create_full_profile_batch`, design per matrix doc `13bed05` §5.1) and on **single-entry payment updates** that omit `payment` entirely or use `state` ≠ `provided`. Payment acceptance on Production requires banks to be populated.

**Note for T1A**: R3A's preview UI independently flags the empty catalog as a CTA blocker for the full-profile paste dialog. R3A's blocker is a UI safeguard and does not block server-side write operations that don't include `payment.state='provided'`. **T1A may need to relax R3A's CTA for non-payment rows** — but T1A's blocker logic should be re-verified after T1B scopes the full-profile RPC.
