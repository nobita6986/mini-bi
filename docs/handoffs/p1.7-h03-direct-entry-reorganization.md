## Changes

- The existing W02 grid now supports a versioned `.xlsx` template/import path through pinned
  `exceljs@4.4.0`. Import is limited to 4 MiB and 100 data rows; formulas, unsupported cell
  values, and numeric sensitive identifiers are rejected rather than silently coerced.
- Grid validation uses the existing worker-profile preview/catalog resolver. HRP/Vendor
  recruiter groups come from the date-effective catalog; the selected recruiter ID and
  catalog-derived provider assertion are submitted, not free text.
- New full-profile rows use `worker-profile/1.1`. The client omits `employee_code`; the server
  returns the generated value after the database transaction. The `worker-profile/1.0` path
  remains available for existing callers.
- New staged rows remain client-only until the single atomic full-profile batch save succeeds.
  The existing persisted-draft drawer, six safe editable fields, CCCD, payment, document,
  conflict/OCC, and mobile flows remain in place. No generic full-profile update or delete path
  was added.

## Contract and database boundary

The v1.1 request envelope is:

```json
{
  "contract_version": "worker-profile/1.1",
  "rows": [{
    "project_id": "synthetic-project",
    "first_work_date": "2026-10-15",
    "provider_type": "hrp",
    "recruiter_id": "00000000-0000-4000-8000-000000000001",
    "labor_type": "TEMPORARY",
    "display_name": "Synthetic Worker",
    "worker": {},
    "general_note": { "state": "omitted" },
    "payment": null,
    "employment": null
  }]
}
```

The response projection is `{ ok, submission_id, state, version, entry_ids, employee_codes }`.
The API strictly validates response keys, row counts, unique UUIDs, generated-code format, and
the year derived from each `first_work_date`; malformed projections fail closed. The generated
codes are returned to the client only after success and the UI reloads the drafts projection.

Migration #39 adds an RLS/FORCE-RLS counter table with no runtime table grants and a
`SECURITY DEFINER` `direct_entry_create_full_profile_batch_v2` RPC restricted to
`service_role`, using `search_path = pg_catalog, public`. The RPC validates date-effective
recruiter/provider membership, allocates `hrp-YYYY-NNNNNN` inside the transaction, and calls the
existing full-profile batch RPC. The outer idempotency record stores the generated codes for
replay; transaction failure rolls back both allocation and entry creation.
