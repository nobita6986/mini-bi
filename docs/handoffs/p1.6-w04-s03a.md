## What changed

The forward-only migration
`20261003180000_p1_6_w04_s03a_actor_context.sql` adds the narrow
`public.direct_entry_resolve_actor_context(p_auth_subject uuid)` RPC. It
returns only the W02 authorization record fields: verified subject mapping,
enabled state, currently effective capabilities, recruiter links, referenced
teams, team grants, and all-scope grants. Effective capabilities use the
`Asia/Ho_Chi_Minh` date. Missing subjects return `null`; disabled mappings
retain `enabled=false` for W02 to reject.

The function is `SECURITY DEFINER` with fixed `search_path=pg_catalog`. Its
only execute grant is `service_role`; no table DML grants were added. Earlier
W03 migrations were not changed.

`GET /api/direct-entry/session` is gated by the exact server-side flag
`DIRECT_ENTRY_API_ENABLED=true`. The disabled path returns 404 before session
or repository setup. When enabled, it reuses `getDirectEntryActor`, the
`@supabase/ssr` cookie session, `auth.getUser()`, and W02 `resolveActor()`.
The server-only repository calls only the new RPC with the verified
`auth_subject`; malformed results, RPC errors, and transport errors resolve
to an invalid actor record and fail closed.

Unauthenticated requests receive sanitized 401; all unavailable, disabled,
malformed, or ambiguous actor mappings receive the same sanitized 403 code.
Success returns only `app_user_id`, `capabilities`, resolved `scopes`, and
`self_recruiter_suggestion`. Responses use `Cache-Control: private, no-store`.
The endpoint does not read actor, user, role, capability, or scope values from
the request. It does not create or update entries.
