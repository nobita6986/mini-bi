# P1.6-I04C3-S01 full-profile server foundation

## Outcome

The isolated server foundation implements the locked `worker-profile/1.0` request contract, an atomic full-profile batch RPC, a bounded API route, and a safe single-entry read projection. It does not implement the UI and does not apply migration #36 to Production.

The implementation follows the locked T1C decisions D11–D22 and A1–A3, and projects the T1A parser model to stable catalog IDs and the server vocabulary. It creates no new capability and does not accept actor, scope, team, provider, revision, state, or audit authority from the client.

## Contract and boundaries

The API accepts a versioned JSON envelope with 1–100 rows. A row uses `project_id`, `recruiter_id`, `display_name`, `first_work_date`, canonical `employee_code`, `labor_type`, optional `worker` values, `general_note`, `payment`, and historical `employment` status. UI/import code must resolve project and recruiter labels to stable IDs, map `Mã NLĐ` to `employee_code`, map payment to an active `bank_id`, and omit T1A-only `sourceRow` and `derived` data before posting.

The route is `POST /api/direct-entry/batches/full-profile`. It checks the existing Direct Entry API feature flag before constructing dependencies, enforces same-origin and JSON, validates a UUID idempotency key, reads at most 4 MiB, calls `auth.getUser()` through the existing actor mapping, and invokes only `direct_entry_create_full_profile_batch`. Responses are private/no-store and contain only the submission ID, ordered entry IDs, draft state, and version. Request values and PII are not logged.

The RPC contract is:

```text
direct_entry_create_full_profile_batch(
  p_auth_subject uuid,
  p_app_user_id uuid,
  p_contract_version text,
  p_rows jsonb,
  p_idempotency_key text
) returns jsonb
```

The database checks active project and recruiter records and exactly one effective-date provider and team membership. The actor needs `entry_create`, `submission_create`, and an effective `own` scope; payment-bearing rows additionally require `payment_view` and `payment_edit`; historical status rows require `employment_status.apply`. Provider type and team ID are derived from recruiter membership, not accepted from the client.

`employee_code` is required in `hrp-YYYY-NNNNNN` form, its year must match the exact calendar `first_work_date`, and leading-zero suffixes remain strings. The batch rejects duplicate employee codes and 9/12-digit national IDs within the batch and against saved rows. Phone duplicates remain permitted, matching the locked policy. National ID validation does not calculate a checksum.

Optional worker values preserve explicit `omitted`, `unknown`, and `intentionally_blank` states where permitted; missing values are not converted to unknown or blank. `gender` is limited to `MALE`, `FEMALE`, and `OTHER`. `display_name` stays a plain string in the canonical stored `worker_details`. `general_note` is entry-level, only omitted or explicitly provided, and capped at 4,000 characters. Payment is either absent/explicitly state-only or contains all three account fields plus an active catalog bank ID; bank labels are never converted to IDs. With no active banks, non-payment rows succeed and payment-bearing rows fail closed.

Historical `ON`/`OFF` imports are accepted only for records whose first-work date is before the authorization date. `OFF` requires a valid leave date and reason. New records without a historical status continue through the existing post-submission workflow.

## Atomicity, revisions, and projection

The entire batch, including submission/entry creation, status and payment rows, revisions, sanitized audits, and idempotency result, runs in one database transaction. A replay with the same actor, action, key, and payload returns the original ordered IDs without adding rows, revisions, or audits; a changed payload conflicts. Creation has no OCC update path because it creates new entries.

The existing entry snapshot is changed to store only worker-detail and note presence. Audit `changed_fields` contains field names only; no national ID, address, phone, payment value, note, or leave-reason text is written to audit/revision snapshots. The read projection reveals worker details and full note only with `pii_view`; otherwise it returns per-field state/presence markers and a note-presence marker. Payment masking remains capability-bound.

The new read projection is a single-entry projection only; it is not an unrestricted PII list. It is executable by `service_role` only. The new validator/snapshot helpers are not executable by `service_role`, `anon`, `authenticated`, or `PUBLIC`. Direct table DML remains denied to `service_role`, and relevant tables retain FORCE RLS. The migration adds exact-match index foundations for employee code, national ID, and plain-string display name; it does not add a search endpoint.

## Migration and database state

Migration #36 is `supabase/migrations/20261005060000_p1_6_i04c3_full_profile_server_foundation.sql`. It is forward-only; migrations #1–#35 are unchanged. PGlite applies all 36 migrations from scratch and exercises the full-profile function inventory, ACLs, forced RLS, direct-DML denial, atomic success/failure, ordered IDs, replay/conflict, 100-row limit, duplicate codes/IDs, recruiter/provider/team/project validation, payment/bank states, banks-with-no-active-entry behavior, historical OFF rules, redaction, and audit-failure rollback.

A rollback-only local acceptance test invokes the RPC inside an outer transaction, checks the uncommitted result, rolls it back, and confirms no fixture residue. It compares row counts and deterministic row fingerprints for reporting sources/breakdowns, catalog, bootstrap ledger, Direct Entry, revision/audit/idempotency, and document state before and after. This is an isolated PGlite test, not a shared-DEV or Production write.

The read-only shared migration dry-run reported 35 applied, only #36 pending, and zero checksum mismatches. Migration #36 has not been applied to Production. No manual SQL, catalog bootstrap, R2 operation, deployment, or reporting-data mutation was performed.
