# P1.7-H05-R1 — Direct Entry production UI gap closure (Fast Track)

## Scope and status

Closes verified source-level UI gaps that remained after
`P1.7-H05 — Direct Entry production UI fixes` (`b4a6f74`).

Implemented and locally verified on `feature/p1.7-h05-direct-entry-ui-fixes`,
based on `origin/main@524961e6b515774b88df3cf68f49b46c5437b384` (required HEAD
`b4a6f74a70d48e25bcc51467055402e1351c6831`). Local matches remote and the

This handoff covers the source-level gap closure for:

1. Completely removing `save_status` / `row_actions` / `cccd_documents` as
   data/pseudo columns of `DataGrid` (18 columns only).
2. Moving the desktop action rail to the right side of the grid, side by side

   `clientRowId`.
3. Splitting `Lưu NLĐ` in the quick editor so it sends only the open row's
   payload and removes only that row on success.
4. Tightening the `Thêm dòng` button to always add 10 staged rows, disable at
   91–100, and never partially add.
5. Making `Mã NLĐ` (employee code) read-only everywhere on the UI
   (server-generated by migration #39).
6. Keeping STK / Tên ngân hàng / Tên chủ tài khoản / Ghi chú as normal
   columns for staged rows and XLSX, and explicitly **not** claiming them as
   editable on persisted rows in this R1 (read-only projection only — see
   §6 below).

It does not authorize applying migrations, deploying, changing shared data, or
performing Production UI UAT. It does not claim P1.7 PASS or Production
readiness. Status at the end of R1 is
`P1.7-H05-R1_DIRECT_ENTRY_UI_GAPS_CLOSED_LOCAL_PASS_FAST_TRACK`.

## Changes

### 1. DataGrid no longer renders status/action/document pseudo-columns

`DirectEntrySpreadsheetGrid` builds the column array from
`DIRECT_ENTRY_DEFAULT_GRID_COLUMN_KEYS` (18 columns) and no longer appends the
`save_status`, `row_actions`, or `cccd_documents` keys. The duplicate red `×`
delete button has been removed from inside the grid — it lives in the external
action rail (see §2). `onOpenDraft` and `onManageDocuments` props/callbacks are
no longer consumed inside the grid component.

`DIRECT_ENTRY_GRID_COLUMNS` (28-column contract registry) still includes the
full set so `DirectEntryCccdManager`, drawer/projection/validation, and any
future column toggles keep working. The 18 default keys are the only ones that
flow into the data-column array passed to `DataGrid`.

### 2. Desktop action rail is on the right, side by side with the grid

The grid and the action rail are wrapped in a single layout container
(`<div className={styles.gridWithRail}>`). The rail is rendered as
`<aside className={styles.actionRailDesktop} aria-label="Thao tác theo dòng"
data-testid="desktop-action-rail">` directly after the grid section, outside
the 18 data columns. It does not participate in horizontal scroll and does not
duplicate any column header.

For each `clientRowId` the rail renders exactly one item, marked with
`data-row-index={row.clientRowId}` and `data-rail-state="persisted" |
"staged"`. Persisted rows render a `Hồ sơ` / `Tải hồ sơ` button (aria-labelled
with the row's employee code) and a `disabled` state matches
`!row.canManageCccd`. Staged rows render a single red `×` button
(`data-testid="row-delete-{clientRowId}"`) wired to the existing
`onStagedDelete` callback. The rail never re-renders a long-label table.

Mobile keeps the two actions in the row card / quick editor footer; no
horizontal desktop rail is rendered on mobile.

### 3. `Lưu NLĐ` in the quick editor sends only the open row

A dedicated `onQuickSaveRow(clientRowId)` callback is wired to the
`data-testid="quick-save-row"` button. It:

- Locates the open row in `stagedModel.rows` and `stagedValidation.rows`.
- Maps the open `clientRowId` to the matching `WorkerProfilePreviewRow` via the
  `stagedValidation.rows` index (validation rows are 1:1 with preview rows).
- Calls `buildServerGeneratedFullProfileRequestBody([matchingPreview])` so the
  request body contains only that one row. `Lưu các dòng hợp lệ` still uses
  the existing `onStagedSave()` to send all valid staged rows.
- Computes the idempotency digest (`fullProfileIntentDigest`) and the
  per-intent key (`"quick_full_profile_row:" + clientRowId + ":" + digest`)
  strictly from the single-row selection.
- On `saved`: removes only the saved row via `deleteSpreadsheetRow(current,
  clientRowId)`, keeps the rest of the staged model intact, calls
  `reloadDrafts()`, and closes the quick editor
  (`setQuickEditClientRowId(null)`).
- On `retry` (network/5xx): keeps the intent key, keeps the row and its
  data, and does not close the editor. The user can retry; the digest/key
  match the same selection.
- On conflict/rejected (non-`saved`, non-`retry`): clears the intent key,
  shows a sanitized message, keeps the row and its data, and does not close
  the editor. The row remains in the staged batch for the next attempt.

There is no optimistic success, no new endpoint, no new route, and no new
side-channel state. The selection is encoded entirely in
`quickEditClientRowId`.

### 4. `Thêm dòng` always adds 10 and is disabled at 91–100

`addStagedRows` checks `current.rows.length + ADD_STAGED_ROW_BATCH >
SPREADSHEET_MAX_DATA_ROWS` (where `ADD_STAGED_ROW_BATCH = 10` and
`SPREADSHEET_MAX_DATA_ROWS = 100`) and returns the model untouched if the
guard fails, while showing the limit notice
`Đã đạt giới hạn 100 dòng dữ liệu; không thêm được 10 dòng mới.`. It uses the
existing `ensureSpreadsheetRowCount` helper, so newly added rows always
receive fresh monotonic `clientRowId`s (no recycling).

The header button `data-testid="add-rows-batch"` is `disabled` when
`!canAddStagedRows(stagedModel)`, which evaluates
`stagedModel.rows.length + 10 <= 100`. Behaviour table:

- 30 → 40: enabled, adds 10.
- 90 → 100: enabled, adds 10.
- 91–100: disabled, button refuses the click (no partial add).
- 100: disabled, no rows added.

### 5. Mã NLĐ is read-only on the UI

`employee_code` is no longer in the writable field set
(`SPREADSHEET_WRITABLE_FIELD_KEYS` already excludes it because
`WORKER_PROFILE_FIELDS` filters out the server-generated field). The persisted
drawer renders the server-issued code as `<output aria-label="Mã người lao
động" data-testid="persisted-employee-code">` with fallback text `Máy chủ sẽ
cấp mã khi lưu`. There is no `<input>` for `employee_code` in the grid, the
quick editor, or the persisted drawer.

`onSpreadsheetCellsChange` strips any `patch.employee_code` from cell-change
patches (it never reaches the staged model mutation path). The persisted
row's `editableFields` list is exactly `["first_work_date", "display_name",
"project_id", "recruiter_id", "labor_type"]` — no `employee_code` and no STK /
Bank / AccountHolder / Note.

### 6. Four optional fields — staged editable, persisted read-only in R1

`account_number`, `bank_name`, `account_holder_name`, and `general_note`
remain as normal data columns for staged rows and as columns of the
17-header XLSX template (H05 §2/§11 unchanged).

For **persisted** rows in R1 the UI does **not** claim editable mutation for
these four fields. The persisted drawer still surfaces the projected values
read-only via the existing `profileCells` projection; the
`editableFields: editable ? [...] : []` list deliberately omits these keys
alongside `employee_code`. This R1 does not introduce a server-side mutation
path for them; that is explicitly out of scope and recorded as a known
limitation here. The earlier H05 handoff paragraph that described these four
fields as directly editable on persisted DRAFT rows is corrected by this R1.

## Known limitations explicitly carried by R1

- Persisted-row editing of the four optional fields (STK / Tên ngân hàng /
  Tên chủ tài khoản / Ghi chú) is not implemented in R1; the UI surfaces them
  as read-only projection. A safe mutation path for persisted rows is
  intentionally deferred.
- The two add-row buttons still share `SPREADSHEET_MAX_DATA_ROWS = 100`; a
  dynamic cap per-actor is out of scope.
- The action rail alignment during virtualized vertical scroll relies on
  `react-data-grid`'s default rendering; the row-height constant
  (`rowHeight={40}`) keeps the rail list and the grid rows in lockstep for
  the current dataset. The two containers are siblings, not nested, so a
  future virtualization tweak must keep them in sync.
