## Migration boundary

Migration #35 is
`20261005050000_p1_6_i04c2b_catalog_bootstrap_boundary.sql`. Migrations #1–#34
were not edited.

It creates:

- `direct_entry_catalog_bootstrap_runs`, with forced RLS and no table
  privileges for `PUBLIC`, `anon`, `authenticated`, or `service_role`. The
  ledger stores only actor ID, source fingerprint, counts, status,
  idempotency key, reason ID, and timestamp.
- `direct_entry_catalog_bootstrap_plan(auth_subject, app_user_id)`, which
  requires the enabled actor plus `entry_admin`, `recruiter_master_manage`,
  and `team_master_manage`. Its response contains only the fingerprint,
  counts, invalid/ambiguous counts, and `catalog_empty`.
- `direct_entry_apply_catalog_bootstrap(auth_subject, app_user_id,
  expected_fingerprint, idempotency_key, reason)`, which re-derives and
  compares the source under a transaction advisory lock, fails closed on
  fingerprint drift or a non-empty target, and applies atomically.

Both exposed functions are `SECURITY DEFINER`, pin
`search_path = pg_catalog, public`, and are executable only by `service_role`.
Their owner is `direct_entry_catalog_bootstrap_executor`, a `NOLOGIN`,
`NOBYPASSRLS` role with narrowly scoped grants and role-specific RLS policies.
The projection helper is not executable by API roles. `service_role` receives
no catalog or ledger table DML privileges. The operator calls the two RPCs
only; it does not read or write tables directly.

Supabase's managed PostgreSQL grants the creator (`postgres`) one administrative
link on a newly created role, with grantor `supabase_admin` and admin option.
The installer cannot impersonate `supabase_admin` to revoke that managed grant.
Migration #35 distinguishes this exact role-created-in-current-transaction
case from pre-existing membership residue. It allowlists only that one managed
creator link; pre-existing installer membership and every unrelated/runtime
membership still fail closed. `service_role`, `anon`, and `authenticated` have
no executor membership, and the executor remains `NOINHERIT`.

The source projection is derived from `data_sources.active = true AND
data_sources.is_test = false`; its SHA-256 fingerprint covers only the
canonical source facts that determine the catalog. Invalid IDs/displays,
same-day display conflicts, non-`hrp`/`vendor` providers, missing valid
provider history, and same-day provider ambiguity block apply.

Valid provider history is deduplicated per recruiter/day, carries forward
through unchanged valid providers, uses half-open intervals at provider
changes, and leaves the final `valid_to` null. Each recruiter gets one
reporting alias and one unassigned team membership beginning no later than
the first provider period. The only team is `unassigned` / `Chưa phân nhóm`.
No bank, capability, scope, or reporting row is inserted or changed.

The apply RPC creates the restricted reason through the existing
`direct_entry_reason` boundary, inserts one ledger row, and appends one
`catalog_bootstrap` audit event in the same transaction. The audit capability
is `entry_admin`, scope is `all`, outcome is `APPLIED`, and changed fields name
entity types only. A matching actor/idempotency key/fingerprint replays without
duplicate catalog, ledger, reason, or audit rows. A different key against a
populated catalog fails closed.
