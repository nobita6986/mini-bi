## Locked write boundary

T0 selected RPC-only writes. Browser roles receive no table DML. The migration
enables and forces RLS on every new table and revokes table privileges from
`PUBLIC`, `anon`, `authenticated`, and `service_role`. Runtime writes and
restricted reads are through the narrow `SECURITY DEFINER` functions listed
below. Each callable RPC pins `search_path`; internal helpers and trigger
functions are not executable by application roles. The only role granted
`EXECUTE` on the application RPCs is `service_role`; no role receives table
DML.

No browser/client operation can write these tables. The RPC accepts actor
identity only because it is callable by the server-only `service_role`; callers
must first resolve the actor from `auth.getUser()` and the W02 repository.
Client-supplied actor identity must never reach this boundary without that
server resolution. `service_role` has no direct table privileges.

## Schema foundation

The physical `public.recruiters` and `public.teams` tables implement the
existing P1.5-W02 identity model; they are shared identity tables, not a
second direct-entry-specific master. Both stable IDs are UUID primary keys.
Recruiter aliases and effective-dated provider/team memberships reference
those same UUIDs. App-user/recruiter links and entry rows use UUID recruiter
references; team membership, entry, authorization scope, and audit scope use
UUID team references. A team scope grant has a foreign key to `public.teams`,
not a free-form text reference.

The migration also defines explicit app-user/recruiter links, capability
grants, project/bank references, submissions, entries, payment details, status
events, document versions/events, change requests, restricted reasons,
entry/submission/change-request revisions, idempotency records, and sanitized
audit events.

Database checks cover canonical employee codes and global uniqueness,
effective membership resolution on entry insert/update, half-open interval
overlap rejection, batch ownership/non-emptiness, status reason/date rules,
payment completeness and active bank, document size/MIME/idempotency/version
uniqueness, soft-delete/nonempty batch rules, and append-only
audit/revision/status/document history. Full entry and proposal snapshots are
restricted; general audit rows retain only opaque identity, action/capability,
scope, outcome, reason/revision references, and field names.

Recruiter/team IDs are UUIDs in the shared P1.5 identity tables
(`public.recruiters`, `public.teams`) and all membership/link/entry/team-scope
references use UUID foreign keys. No text team scope or second direct-entry
identity master is introduced.

## RPC matrix

| RPC | Capability/scope | OCC and atomic writes |
|---|---|---|
| `direct_entry_create_batch` | `entry_create` + `submission_create`, own scope | Payload-hash idempotency; entries, initial status, entry/submission revisions, audit |
| `direct_entry_create_draft_row` | `entry_create`, owner and own scope | Expected submission version; entry + submission revisions, audit, idempotency |
| `direct_entry_update_draft_row` | Exact own/team/all `entry_*` capability/scope | Expected entry version; immutable entry/submission revisions, audit, idempotency |
| `direct_entry_delete_draft_row` | Exact own/team/all `entry_*` capability/scope | Soft-delete; expected entry version; cannot remove last active row |
| `direct_entry_transition_submission` | `submission_create`, creator/own scope | Expected submission version; REVIEW/SUBMITTED revision, audit, idempotency |
| `direct_entry_update_payment` | DRAFT: exact `entry_own/team/admin` scope; SUBMITTED: `payment_edit` + effective resource scope | DRAFT/SUBMITTED only; entry/payment versions, mandatory reason; revision, audit, idempotency |
| `direct_entry_apply_employment_status` | `employment_status.apply` + effective resource scope | Expected entry version; append-only event, revision, audit, idempotency |
| `direct_entry_correct_latest_status` | `employment_status.apply` + effective resource scope | Expected entry/status versions; appends a correction superseding only the latest event, revision, audit, idempotency |
| `direct_entry_create_document_metadata` | DRAFT: `document_upload` + exact `entry_own/team/admin` scope; SUBMITTED: `document_upload` + `entry_privileged_edit` + effective scope | DRAFT/SUBMITTED only; expected entry version; required reason after submit; server-generated key, replacement lineage, checksum-bound idempotency, revision, audit; same-content retry reports `reused` with no duplicate row mutation |
| `direct_entry_append_document_event` | Backend uploader only; `service_role` EXECUTE | Expected per-document event version; append-only state transition validation, monotonic attempts, payload-hash idempotency |
| `direct_entry_create_change_request` | `change_request_create` + each entry scope | Expected entry version per item; restricted proposal/reason, request revision, audit, idempotency |
| `direct_entry_withdraw_change_request` | Proposer with `change_request_create` | Expected request version; request revision, audit, idempotency |
| `direct_entry_approve_change_request` / `direct_entry_reject_change_request` | `change_review` + each entry scope; proposer cannot review own request | Expected request and item versions; request/entry revisions, audit and idempotency; multi-entry approval is one transaction |
| `direct_entry_privileged_edit` | `entry_privileged_edit` + effective resource scope | Mandatory reason and expected entry version; direct single-step edit, revision, audit, idempotency |
| `direct_entry_read_projection` | Exact `entry_*` scope; optional PII/payment/document capability gates | Redacts worker details, payment values and document metadata absent their separate capabilities |
| `direct_entry_read_audit` | `audit_view` + effective resource scope | Bounded sanitized audit projection |

All mutation idempotency hashes are server-computed from canonical `jsonb`
inputs. Same actor/action/key/input returns the prior result; key reuse with
different input is rejected. Identity, capability, and scope are checked
before returning a replay. Mutations, revisions, audit events, and idempotency
results share the RPC transaction.

## R1 semantic closure

Capability grants and enabled actor mappings are evaluated at the current
`Asia/Ho_Chi_Minh` authorization date. Resource scope and recruiter/team
membership use the entry's `first_work_date`. Draft edits, privileged edits,
and change approval re-resolve recruiter/provider/team on the proposed
recruiter/date and require the same authorized scope kind on the destination;
an out-of-scope destination aborts the whole transaction.

Status append events follow `UNCONFIRMED → ON|OFF`, `ON → OFF`, and `OFF → ON`.
Ordinary events cannot be no-ops, dated before the latest effective status, or
future-dated and always have `supersedes_event_id = null`. A backdated event
within that interval is valid. Corrections use the separate
`direct_entry_correct_latest_status` RPC with expected entry/status versions;
the trigger only accepts a correction of the current latest event, and a
correction cannot be a no-op.

Payment and document metadata direct mutations lock the submission and are
allowed in `DRAFT` and denied in `REVIEW`. After `SUBMITTED`, ordinary users
must use a change request; payment editors need `payment_edit`, while direct
document editors need both `document_upload` and `entry_privileged_edit`.
Both privileged paths require expected versions, reason, revision, and audit,
and do not require a second reviewer. The document RPC and change-request
proposal reject caller-supplied storage keys. The database generates keys from
candidate UUID, document type, version, and a new opaque document UUID. Each
replacement records its predecessor and each idempotency key is bound to the
content checksum/metadata. Same-content retry across authorized actors returns
the existing document with `reused=true` and does not increment the entry
version or duplicate revision/audit. Read projections first resolve each
document's latest append-only upload event, filter to `READY+CLEAN`, then
choose the highest valid version per candidate/type. A pending or rejected
replacement therefore leaves the previous ready/clean version current.

The backend uploader can append document events through
`direct_entry_append_document_event`, which is executable only by
`service_role`; table DML remains revoked. Invoke it only through a trusted
server or worker/n8n boundary—never expose it directly to a client. It checks
per-document expected event version, legal upload/scan transitions, attempts
monotonicity, and idempotency key/payload hash. `REVIEW` is read-only for
entry, payment, document, status, and privileged-edit mutations. Status
transitions accept any effective date between the latest status date and
current HCMC date; backdating within that interval is valid.

The `worker_details` check now validates the W01 shape: exact field set,
required optional-value states, real calendar DOB, and per-field limits. It
does not accept an arbitrary JSON object or only enforce a byte-size ceiling.

## G3 DEV acceptance — fast-track evidence

The W03 foundation migration
`20261002170000_p1_6_direct_entry_foundation.sql` and the forward-only
no-op-transition correction
`20261003170000_p1_6_w03_submission_noop_guard.sql` are applied on Supabase
DEV. Both applied files are immutable. The final DB-aware migration dry-run
reports 21 applied migrations, 0 pending migrations, and 0 checksum
mismatches.

The repeatable DEV harness is `pnpm run test:p1.6-w03-g3-dev`
(`scripts/p1.6-w03-g3-dev-acceptance.mjs`). Its latest run passed 95 checks
covering the migration registry, sanitized baseline, RLS/FORCE RLS and table
ACLs, service-role RPC grants and function properties, anon/authenticated and
service-role denials, capability/scope and actor checks, OCC and concurrent
idempotency, submission and change-request lifecycle, status events and
correction, privileged edits, document lineage/current-document selection,
restricted projections, rollback injection, and exact cleanup. It reported
`cleanupVerified=true` and `baselineUnchanged=true`. The exact synthetic
namespace, fixture IDs, run results, baseline, and cleanup evidence are in
`scripts/p1.6-w03-g3-dev-manifest.json`; it contains no connection data,
credentials, tokens, PII, or document payloads.

The sanitized reporting baseline was 26 sources (2 fixture sources), 30
recruited total, 30 breakdown rows, and W03 user/entry counts of zero.
Post-cleanup values match these pre-test values. **It is not possible to
retroactively prove pre-migration business counts; the evidence proves only
post-apply pre-test = post-cleanup.** A separate post-run W03 table count also
confirmed zero residual rows in the checked user, entry, document-version,
and change-request tables; the harness cleanup check covers its exact fixture
manifest.

The `pg@9` deprecation warning was traced to the concurrent OCC probe: it
passed separate database clients to `updateDraft`, but that helper ignored
the client argument and issued both mutations on the shared client. The helper
now executes on the supplied client (defaulting to the shared client for
sequential cases). The 95-check DEV acceptance was rerun successfully with
no `pg@9` query-concurrency warning. No production RPC or schema was changed
to address the harness warning.

This status applies only to W03 DEV acceptance. It does not declare all of
P1.6 PASS, does not authorize PROD, and does not open W04.
