## 3. Executive summary

T1C has read the full P1.6 Direct Entry database surface (34 migrations) and the related TypeScript contracts, and has produced a **policy / contract proposal** for the full worker profile superset that the business wants. The proposal is built around four observations:

1. **The current schema covers ~70% of the superset.** Fields B1–B7, C1, C3, C5, C8, C9, D1, D2, E1–E4, F1–F4, G1–G3 are already supported. The contract `WorkerDetails` (`src/lib/contracts/direct-entry-v1.ts:69`) defines 5 fields, and the `direct_entry_valid_worker_details` JSONB validator (`20261002170000_…:127–184`) enforces them. PII redaction at read time is layered: list projection (S03CD) is PII-clean; detail projection (S04A) masks `payment.account_number` last-4 if no `payment_view`; revision snapshots are redacted at write time (S03B3-R1) so new revisions are PII-clean.

2. **The remaining ~30% is genuinely missing.** Fields C2 (`gender`), C6 (`national_id_issued_at`), C7 (`national_id_issued_place`), B8 (`general_note`) are not in the schema, not in the TypeScript contract, and not in any current RPC. Adding them is a T1B migration, not a T1C decision.

3. **Two hard production blockers exist today and are unrelated to the full profile.** Per I04C2A (`p1.6-i04c1-production-api-activation.md:329–411`): (a) Production has **0 active banks**, **0 projects**, **0 recruiters**, **0 teams**; (b) the database has **no sanctioned, audited master-catalog write boundary** (no `recruiter/team/project/bank` mutation RPC, FORCE RLS with no applicable policies, no audit triggers on those tables). The catalog blocker is a **separate task** that must complete before any full-profile smoke can run on Production. T1C has flagged this as **G10, G11, G21** in the matrix doc.

4. **T1A R2's paste model is partial.** `7a3a04c` implements a fixed 6-column paste (Mã NLĐ, Ngày bắt đầu làm việc, Họ tên, Dự án, Người tuyển, Loại hình lao động). T0 D4 says the target is a **union of two templates, not a fixed N-column import**, so the full-superset work is **partially reusable** (idempotency, atomic batch, result classification, CCCD two-slot management) and **partially to be redone** (header-based parser, full preview, drawer, PII sections).

The matrix doc proposes a `worker-profile/1.0` contract version (separate from `direct-entry/1.1`) and a single superset template with optional columns (recommended over two templates). It does not propose a new capability; the existing 21 capabilities are sufficient if T0 confirms the field vocabulary. It surfaces 12 T0 decisions that T1C cannot resolve unilaterally.

### 5.1 T1B (server foundation, gated by T0 decisions)

After T0 confirms the field vocabulary (T0-1, T0-3, T0-5, T0-6, T0-8):

1. **Migration #35+**:
   - Extend `direct_entries.worker_details` JSONB with `gender`, `national_id_issued_at`, `national_id_issued_place`, `general_note`.
   - Update `direct_entry_valid_worker_details` to accept the new keys.
   - Add `direct_entry_create_full_profile_batch` RPC (or extend `direct_entry_create_batch` with optional `payment` / `status_event` / `general_note` keys).
   - Update `direct_entry_update_draft_row` to accept the full `worker_details` shape (not only `display_name`).
   - Update `direct_entry_apply_change_item` ENTRY_FIELD branch to accept the new fields.
   - Update `direct_entry_change_request_required_capabilities` and `direct_entry_change_request_proposal_projection` for the new fields.
   - Update `direct_entry_list_own_drafts` projection to include `gender`, `national_id`, `phone`, `address`, `general_note` **only if `pii_view` is present** (otherwise PRESENCE_ONLY).
   - Update `direct_entry_input_catalog` to include `teams[]` and `banks_active_count`.
   - Add search indices (G23) for `lower(employee_code)`, `worker_details->'display_name'->>'value'` (lower), `worker_details->'national_id'->>'value'` (partial where provided), `worker_details->'phone'->>'value'` (partial where provided).
   - **Bump `DIRECT_ENTRY_CONTRACT_VERSION`** to `"direct-entry/1.2"` (or keep `1.1` and add `WORKER_PROFILE_CONTRACT_VERSION = "worker-profile/1.0"`).
   - **Do NOT** add a master-catalog write boundary in this migration; that is a separate T0-authorized task.

2. **Backwards compatibility**:
   - Existing 5-key `WorkerDetails` continues to validate; new keys are optional.
   - Existing 6-key batch (`project_id, first_work_date, employee_code, worker_details, recruiter_id, labor_type`) continues to validate.
   - New RPC is **additive**; old RPC is not removed.

3. **Atomic full-profile batch**:
   - One transaction per batch submission.
   - Capability union check at the entry of the RPC (mirroring S03B3-R1 `direct_entry_decide_change_request` line 401).
   - If any row's capability union is incomplete, the entire batch is rejected (no partial commit).
   - If any row's catalog/employee_code/recruiter/payment/status validation fails, the entire batch is rejected (no partial commit).

4. **Payment / work-status atomicity**:
   - `direct_entry_update_payment` already atomic per entry; unchanged.
   - For an initial `OFF` event (T0-6), introduce a new `direct_entry_apply_initial_status_event` RPC that runs in the same transaction as the entry creation, with reason in `direct_entry_restricted_reasons`.

5. **CCCD boolean projection**:
   - Existing `direct_entry_read_projection` already returns the document array; verify it never includes `idempotency_key`, `checksum_sha256`, `size_bytes`, `mime_type` in the response (it does NOT today, by design).
   - Add a server-side helper `documentCompletenessByEntry(entryId)` that returns `{ CCCD_FRONT, CCCD_BACK, EMPLOYMENT_CONTRACT }` counts of `READY+VALIDATED+(CLEAN|NOT_REQUIRED)` documents.

6. **Search readiness** (per matrix §7):
   - New RPC `direct_entry_search_profile` (or extension of `direct_entry_list_own_drafts` with `query` parameter) that takes `query` text and `page_size` / `cursor` and returns masked PII if no `pii_view`.
   - P0002 for "not found" and "not authorized" (anti-enumeration).

7. **DEV acceptance**:
   - 40 test cases per matrix §10.
   - PGlite fixture per I04A pattern.
