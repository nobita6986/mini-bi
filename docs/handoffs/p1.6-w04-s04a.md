## Implementation

The existing server-only write repository now projects the active bank catalog
and calls `direct_entry_update_payment`. The new
`PATCH /api/direct-entry/entries/[entryId]/payment` handler checks the
server-side API feature flag before session/database setup, resolves the
existing Supabase actor boundary, validates the request and same-origin
headers, and delegates final authorization, scope, OCC, idempotency, revision,
and audit enforcement to the RPC. It does not access Direct Entry tables
directly.

The payment group is in the existing row editor/drawer, not the grid. The four
states are `omitted`, `unknown`, `intentionally_blank`, and `provided`.
`provided` requires a string account number, active stable `bank_id`, and
account-holder name. The account number remains a string, preserving leading
zeroes. The UI does not persist payment values in browser storage. It masks
saved values when `payment_view` is absent, blocks copy/cut/context-menu on
masked-entry inputs, and offers explicit server/local choices on OCC conflict.
The editor is locked while its parent row is saving or conflicted.

The demo shell remains synthetic and does not call `/api/direct-entry`; live
mode does not fall back to fixtures if an API call fails.
