## Integrated behavior

The full-profile dialog submits one atomic batch:

- `POST /api/direct-entry/batches/full-profile`
- `Content-Type: application/json`
- UUID `Idempotency-Key`
- JSON root contains only `contract_version: "worker-profile/1.0"` and `rows`.
- It sends no actor, role, capability, scope, app-user, auth-subject, team, or
  provider authority fields and makes no per-row request or six-column
  fallback.

The client accepts success only for a strict server projection containing
`ok`, a UUID `submission_id`, `state: "DRAFT"`, a positive integer `version`,
and one unique, ordered server `entry_id` per submitted row. It does not
synthesize IDs or show optimistic success. A valid success reloads the parent
draft view using the server response.

### CTA and catalog gates

Submission is disabled for an empty/invalid preview, unresolved or ambiguous
project/recruiter, unresolved bank for a provided payment, row/body limit,
missing required capability, or an in-flight request. The submit handler
recomputes the blockers and guards duplicate clicks with both a ref and busy
state.

With banks empty, a non-payment (`payment: null`/omitted) batch remains
submittable; any payment-bearing row fails closed unless it resolves to an
active bank. A mixed batch with one invalid payment row is blocked as a whole.
No bank is hard-coded or bootstrapped. There is no account-data lookup in this
flow.

An integration review found that the initial client body-size guard counted
JavaScript characters rather than UTF-8 bytes. The reconciliation now compares
`TextEncoder().encode(body).byteLength` with the existing 4 MiB contract limit.
A regression test proves that a Unicode payload below 4 MiB by `string.length`
but above it in UTF-8 is rejected before `fetch`.

### Idempotency, retry, and document boundaries

- The intent fingerprint is a SHA-256 hash of the normalized request and is not
  persisted. The UUID key is held in component state only; no local/session
  storage or raw PII console logging is used.
- Network failure, 5xx, or malformed 2xx is an unknown/retry outcome and
  retains the same intent key. Editing the request produces a new key.
- 409 does not auto-retry; the parent reloads/reconciles. Busy state blocks a
  second concurrent submit.
- Full-profile JSON contains no CCCD file bytes, base64, checksum, or storage
  metadata. CCCD controls use server-returned entry IDs; before document status
  is known, the UI says `Chưa tải trạng thái` rather than inventing a count.
- Browser acceptance uses synthetic interception only. No database write,
  R2 call, or real document upload was made.
