## 6. Can T1A begin R3B after integration?

**YES**, subject to the following contract reconciliations that T1A must perform:

1. Build a new `worker-profile-paste-to-rpc.ts` mapper (or equivalent) that converts the R3A `WorkerProfileRow` into T1B's `FullProfileRpcRow` shape:
   - Rename `worker` → `worker_details`.
   - Resolve `project_label` → `project_id` via `direct_entry_input_catalog.projects`.
   - Resolve `recruiter_label` → `recruiter_id` via `direct_entry_input_catalog.recruiters`.
   - Resolve `bank_label` → `bank_id` via `direct_entry_input_catalog.banks` (when `payment.account_number` is `provided`).
   - Drop all `derived` fields (validation-only).
   - Drop `sourceRow`.
2. Use the new API route `POST /api/direct-entry/batches/full-profile` with:
   - Header `Idempotency-Key: <UUID v1–v8>`.
   - Header `Content-Type: application/json`.
   - Origin must match Host (browser preflight only; same-origin guard applies).
3. Handle the response shape `{ok, submission_id, state: "DRAFT", version, entry_ids}` and any 4xx codes (`BATCH_INVALID, BANK_NOT_ACTIVE, EMPLOYEE_CODE_DUPLICATE, NATIONAL_ID_DUPLICATE, …`).
4. For idempotent replay: same `(key, payload)` returns `{ok, submission_id, ..., replayed: true}` with 200; same key with different payload returns 409 `IDEMPOTENCY_CONFLICT`.

These are R3B implementation tasks, not T1B defects. R3A already enforces the right shape on its preview side; R3B just needs the projection.
