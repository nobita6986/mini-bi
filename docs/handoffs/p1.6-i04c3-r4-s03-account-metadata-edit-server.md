## API and authority behavior

The existing `PATCH /api/direct-entry/entries/{entryId}/payment` endpoint
accepts either its existing legacy `payment` payload or an exact
`account_metadata` replacement containing all three keys:
`account_number`, `bank_name`, and `account_holder_name`. Each value must be a
string or `null`; blank strings normalize to `null`. All-null metadata clears
the account fields and sets the payment state to `omitted`; any non-empty
field sets it to `provided`. Account numbers remain text, preserving leading
zeroes. The metadata path makes no bank-catalog request and writes `bank_id`
as `null`.

The legacy catalog-backed payload and `direct_entry_update_payment` RPC
signature remain available. Legacy writes still validate a supplied bank ID;
when an older payload updates a provided payment, an existing text `bank_name`
is preserved rather than silently discarded. An all-null metadata replacement
clears the legacy bank ID as well.

The existing access helper, draft ownership/scope, submitted-entry
`payment_edit` authority, optimistic versions, idempotency key and payload
hash, reason, revision, and audit behavior remain unchanged. The RPC still
returns only entry/payment versions and does not return account values.
Projections retain `payment_view` gating: without it, the account number is
masked and bank name/account holder are omitted. Revision and audit evidence
contains no raw account metadata.
