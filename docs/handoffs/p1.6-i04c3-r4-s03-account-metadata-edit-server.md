## Explicit metadata contract

The API accepts `account_metadata` only when it contains the three exact fields and each field is exactly one of:

```json
{
  "account_number": { "op": "keep" },
  "bank_name": { "op": "set", "value": "Synthetic Bank" },
  "account_holder_name": { "op": "clear" }
}
```

- TypeScript validates exact keys, trims SET values, requires ASCII digits for account-number SET, rejects masks/control characters, and rejects all-KEEP.
- The API passes operation objects unchanged to the existing repository/RPC path; it does not flatten them to replacement values or require/send the current raw account number for KEEP.
- The trusted SQL boundary independently validates operation shape and values, rejects all-KEEP and masked STK, resolves KEEP from the locked current payment row, and applies all fields in the same transaction.
- Account-number SET preserves leading zeroes. CLEAR affects only its named field. Clear-all sets the state to `omitted`.
- `bank_name` KEEP preserves `bank_id`; SET or CLEAR clears `bank_id`.
- Legacy catalog-backed payment requests remain a separate compatibility path.

The PGlite regression confirms an actor with exactly `payment_edit` and no `payment_view` can safely KEEP the existing raw account while updating the bank name. Read projections remain masked for actors without `payment_view`. RPC responses do not echo account values.

Idempotency remains keyed by the existing payment-update action and hashes the exact operation payload: same key/same operations replay; same key/different operations conflict. Stale entry/payment versions conflict. Failed requests roll back payment, entry version, revision, audit, and idempotency state. Synthetic checks confirm revisions, audit events, reason rows, and idempotency rows do not contain protected account values.
