# P1.7-W02-R1 — Wire the spreadsheet grid into Direct Entry live

**Status:** `P1.7-W02_SPREADSHEET_GRID_UI_LOCAL_PASS_FAST_TRACK`

The W02 spreadsheet grid is now wired into `direct-entry-live.tsx` and drives real staged rows,
direct Excel paste, inline validation, one-level undo and an atomic full-profile batch save.

This handoff does not claim W03, Production UI acceptance, P1.7 PASS, deployment or Production
readiness. Owner-only UI UAT is still pending in J01.

## 2. Wiring in `direct-entry-live.tsx`

The orchestrator was **not** rewritten. A single new section, its state and its callbacks were
added; the existing persisted-draft grid, drawer, submissions, change requests, CCCD manager,
payment editor, document editor and mobile cards are all left in place and still render.

Added:

- staged state — `stagedModel` initialised from `createSpreadsheetRowModel()` (30 client-only
  rows), plus notice/message/rejection/busy/undo state, an intent-key ref, an undo-snapshot ref
  and an in-flight ref;
- `stagedCatalogSource` / `stagedCatalogOptions` — catalog lookup by effective date, mapped from
  the existing `catalogs` cache;
- `stagedValidation` — `buildSpreadsheetValidation` over the staged rows, with the existing
  drafts passed as `existing` identity;
- `spreadsheetRows` — persisted drafts plus staged rows in one controlled row list;
- `onSpreadsheetCellsChange`, `onStagedPaste`, `onStagedPasteRejected`, `onStagedUndo`,
  `onStagedClear`, `onStagedDelete`, `onStagedDuplicate`, `onStagedSave`;
- one rendered `<section>` containing `<DirectEntrySpreadsheetGrid />`, the paste-rejection
  alert, the `Đi tới lỗi đầu tiên` control and the paste banner.

`clientRowId` is never mixed with `entry_id`: persisted rows keep `row.rowId`, staged rows keep
the row-model ID, and the two sets are concatenated only for rendering.

### 2.1 Persisted rows stay inside the P1.6 boundary

Persisted rows are rendered through the same grid but their `editableFields` are limited to the
six fields that already have a safe mutation path (`employee_code`, `first_work_date`,
`display_name`, `project_id`, `recruiter_id`, `labor_type`). Optional full-profile fields are
**not** made editable, because no safe server mutation exists for them. A row whose state is
`saving`/`conflict` or which is not `isRowEditable` against the submission list gets an empty
`editableFields`, so REVIEW/SUBMITTED rows remain read-only.

### 2.2 Row-model addition

`ensureSpreadsheetRowCount(model, minimumRowCount)` was added to `spreadsheet-row-model.ts`. It
is required so a paste anchored near the bottom edge has rows to write into; it only appends
client placeholders, never shrinks, never recycles IDs, and does not count against the 100 data
row limit. This was a genuine gap in W01B for spec §8.1 item 8 ("paste bắt đầu từ hàng cuối tự
thêm hàng").

## 3. Direct paste

Paste is captured by the grid's native `onCellPaste`, so the anchor comes from the real event
cell. The handler:

1. captures a one-level undo snapshot over the mapping's write cells;
2. grows the model with `ensureSpreadsheetRowCount` so the whole matrix fits;
3. groups write cells by target row and applies them through `updateSpreadsheetRowCells`;
4. sets the banner `Đã dán N hàng × M cột` and enables `Hoàn tác`.

Overflow is rejected before any cell is applied, so a rejected paste cannot partially mutate
state. Internal blank cells and alignment across validate-only/ignore columns are preserved by
the W01 mapper. The paste handler contains **no** `fetch`, **no** storage access and **no**
Clipboard permission API, and no cell value is logged.

## 4. Validation

`buildSpreadsheetValidation` runs over the staged rows only; blank rows are never validated and
never produce an issue. Issues are mapped to the exact `clientRowId` + column key, rendered as a
cell error state with the sanitized contract message as the tooltip, and summarised as an error
row count. `Đi tới lỗi đầu tiên` reports the first error's row position and column key.

**Accepted limitation:** the button reports the position rather than scrolling the grid to the
cell, because the pinned `react-data-grid` build exposes no stable imperative focus API in the
shape used here. Adding one would mean a new grid abstraction, which is out of scope for this
slice. No PII is echoed: messages come from `workerProfileIssueMessage` and contain no values.

## 5. Save, retry and OCC behaviour

- Primary control: `Lưu các dòng đã nhập (N)` where N is the count of non-empty staged rows.
- Only non-empty staged rows are converted, via the existing `buildFullProfileRequestBody` over
  `stagedValidation.preview.rows`.
- Transport is the existing `postFullProfileBatch` → `POST /api/direct-entry/batches/full-profile`.
  No endpoint, payload or header was invented.
- One request per batch; `stagedInFlight` plus the busy flag block a double submit.
- Intent key follows the existing `resolveIntentKey` / `clearIntentKey` pattern with
  `fullProfileIntentDigest`; no automatic retry is scheduled anywhere.
- `kind === "retry"` (network/5xx, and a malformed 2xx projection) keeps the key and returns, so a
  manual retry reuses the same intent.
- 409 is not retried; the key is cleared and the sanitized conflict message is shown.
- Staged state is cleared **only** inside the `saved` branch, after the server returned a valid
  projection, and `reloadDrafts()` is awaited. No optimistic "saved" state is shown.

## 6. Copy and row actions

- Copy uses the pinned grid's `onCellCopy` and serializes the **active cell** as TSV through the
  W01 serializer. **Accepted limitation:** multi-cell/range copy is not implemented, because the
  pinned build emits copy per active cell and a range selection engine would be a new
  abstraction beyond this slice.
- Clear / delete / duplicate act only on staged rows; a persisted row's action buttons route to
  the existing CCCD manager only. No delete API was invented for persisted rows.

## 7. W03 dependency (unchanged)

Reload after a successful save reuses the existing drafts projection, which carries the six core
fields. Optional full-profile fields (identity detail, employment, account metadata) are **not**
projected back into the grid yet, so a reloaded draft shows the core fields only.

Per the P1.7 constraint this is handled by doing nothing risky: no per-entry detail call, no N+1
fetch, and no synthesized values — a source test asserts the staged region issues no fetch at
all. Showing the remaining optional fields requires the W03 list-projection extension.

## 10. Transitional state and remaining work

The page now shows two entry surfaces: the new spreadsheet grid (staged rows, direct paste,
atomic batch save) and the pre-existing persisted-draft grid with its drawer. They were kept
separate deliberately so that no P1.6 flow could regress in a change that cannot be verified in a
browser here. P1.7 §12 requires that competing entry experiences converge before P2 opens.

Still pending:

- Owner-only Production UI UAT in J01 (direct paste, cell edit, inline errors, atomic save,
  reload, CCCD manager on a saved row);
- W03 list projection so reloaded rows show optional full-profile fields;
- multi-cell copy and grid focus-to-cell navigation (both recorded as accepted limitations).

No API route, repository, server contract, migration, database, auth/capability authority,
`package.json`, lockfile, environment variable, flag, R2 setting or Production state was touched.
`e791208` was not amended; this is a separate commit.
