# P1.6-W04-S04B-S02B1 handoff

**Status:** `P1.6-W04-S04B-S02B1_WORKER_BOUNDARY_DEV_PASS_FAST_TRACK`

This checkpoint establishes a server-only worker boundary and an authenticated, atomic document lifecycle callback. It does not connect Drive/n8n or authorize a production rollout.

## Boundary and protocol

The existing multipart admission path validates type, size, file signature, actor and scope before calling the configured worker adapter. Missing or invalid worker configuration returns `DOCUMENT_STORAGE_UNAVAILABLE` before reservation. No local, in-memory or public-URL fallback exists.

The adapter sends a bounded HTTPS POST through the shared pinned outbound guard. The worker host must exactly match the configured server-side allowlist; DNS answers are checked and pinned; private/metadata addresses, TLS failures and cross-origin redirects are rejected. Timeout is 30 seconds, request ceiling is 15 MiB (including Base64 expansion), and response ceiling is 4 KiB. No live worker request was made in this checkpoint.

| Direction | Contract |
| --- | --- |
| App → worker | Bearer-authenticated JSON protocol v1 with opaque document ID/version/type, attempt/event sequence, server-generated storage object reference, checksum/size/MIME, idempotency key and Base64 bytes. Browser filename and public URL are absent. |
| Worker → app | `202` plus the exact acknowledgement shape `{ "accepted": true, "job_id": "opaque-id" }`. Other status/body shapes fail closed. This acknowledges worker admission only; it does not mark the document ready. |
| Worker → callback | `POST application/json`, signed over the exact raw body with HMAC-SHA256 in `x-direct-entry-signature: sha256=<hex>`. The strict payload contains only callback/document IDs, version, event sequence, attempt, opaque object reference, server-known content metadata and upload/scan outcomes. |
| Callback → worker | Sanitized lifecycle projection including the resulting event sequence. If scanning remains pending, a later scan callback must use that returned sequence. No checksum, object reference, storage key, public URL, actor authority or provider error is returned. |

Callback IDs provide replay protection through the existing RPC idempotency table: identical replay returns the saved outcome; the same ID with changed payload conflicts. The raw-body signature comparison uses constant-time equality. Authentication and payload validation complete before the database RPC is called.

## Lifecycle and database

The callback RPC appends transitions using the existing event vocabulary. It is `SECURITY DEFINER` with `search_path = pg_catalog, public`; only `service_role` can execute it. It writes events, revision, audit and callback idempotency in one transaction. A callback cannot set actor, role, capability, scope, `READY`, `CLEAN`, or a public URL.

| Callback outcome | Result |
| --- | --- |
| Upload success + clean scan | Existing event progression ends at `READY` / `CLEAN`. |
| Upload success + scan pending | Remains quarantined/pending; a follow-up scan result may complete using the returned sequence. |
| Infected or suspicious scan | Quarantined/rejected; excluded from current-document projection. |
| Transient upload failure | `FAILED` and retryable up to three attempts; the next attempt must be monotonic. |
| Duplicate, stale, out-of-order or changed replay | Exact duplicate is idempotent; changed payload conflicts; stale sequence cannot overwrite newer state. |
| Pending/quarantined replacement | Latest eligible `READY` / `CLEAN` version remains current until the replacement qualifies. |

The forward-only migration is `20261004010000_p1_6_w04_s04b_s02b1_worker_callback.sql`. It also adds lifecycle-derived document `updated_at` to the restricted projection and keeps revision snapshots free of checksum/storage internals. No table DML grants or RLS policies were added or loosened.
