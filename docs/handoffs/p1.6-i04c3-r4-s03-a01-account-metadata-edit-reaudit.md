## F-00 — Destructive-by-default full-replacement with masked account

### Summary

The metadata edit contract is full-replacement: every key in
`{account_number, bank_name, account_holder_name}` is required, every
value is normalized (trimmed), and every field's normalized value
overwrites the column in the SQL `insert on conflict do update`.

There is **no KEEP operation**. The only way to indicate "do not
change" is to send the **current** value, but the read projection
never returns the raw STK when `payment_view` is not granted.

**Consequence**: an actor with `payment_edit` but not `payment_view`
sees only the masked `••••••••0056` style STK. To edit another field
(e.g. `bank_name`) without changing the STK, they have only two
options:

1. Send `null` for `account_number` → destructive clear of the STK.
2. Send the masked value → destructive corruption of the STK
   (persists `••••••••0056` as the canonical `account_number`).

There is **no third option** in the current contract. This is the
BLOCKER.

### Concrete destructive scenario

**Setup**:
- Entry `e1` with payment row
  `(state='provided', account_number='000012340056', bank_id=null,
  bank_name='Old Bank', account_holder_name='Holder', version=1)`.
- Actor `u1` with capabilities `['entry_own', 'payment_edit']` (no
  `payment_view`).

**Read**: `direct_entry_read_projection(u1, e1)` returns
`{payment: {state: 'provided', account_number: '••••••••0056',
version: 1}}`.

**Intent**: change `bank_name` from `'Old Bank'` to `'New Bank'`
while preserving everything else.

**Outcome (current contract)**:
- `account_number: null, account_holder_name: null` ⇒ STK cleared
  to NULL.
- `account_number: "••••••••0056"` ⇒ masked value persisted as
  canonical STK (corruption).
- No safe option exists.

**Outcome (after T0-locked repair)**:
```json
{
  "account_metadata": {
    "account_number":      { "op": "keep" },
    "bank_name":           { "op": "set", "value": "New Bank" },
    "account_holder_name": { "op": "keep" }
  }
}
```
Server reads `account_number` and `account_holder_name` from the
locked row inside the SQL transaction. STK is preserved unchanged.
The actor never sees the raw STK.

## T0-locked repair design (per-field explicit operations)

### 3.1 Body shape (semantic example)

```jsonc
{
  "expected_entry_version": 3,
  "expected_payment_version": 2,
  "reason": "Edit bank name",
  "idempotency_key": "<uuid>",

  "account_metadata": {
    "account_number":      { "op": "keep" },
    "bank_name":           { "op": "set",  "value": "Ngân hàng Á Châu" },
    "account_holder_name": { "op": "clear" }
  }
}
```

Each field is an object with `op` ∈ `{"keep", "set", "clear"}`. SET
requires `value`. KEEP and CLEAR reject extra keys.

### 3.2 Required behaviors (17 rules)

1. Each field must have an explicit operation. Omitted field ⇒ 400.
2. `op: "keep"` reads current value from the locked row inside the SQL
   transaction. Raw STK is **never** returned to the client.
3. `op: "clear"` sets the field to NULL. No `value` allowed.
4. `op: "set"` overwrites with the supplied `value`. Validation
   unchanged: digits `1..64` for STK; text `1..256` for the others.
5. All-KEEP rejected as no-op (no increment, no audit).
6. `op: "set" / "clear"` for `bank_name` ⇒ `bank_id = NULL`.
7. `op: "keep"` for `bank_name` ⇒ preserve `bank_name` and `bank_id`.
8. Clear-all = three CLEARs + `bank_id = NULL` + state = `'omitted'`.
9. OCC / idempotency fingerprint includes operation map and SET values.
10. Same payload + same ops + same key ⇒ idempotent replay.
11. Same key + different ops or different SET values ⇒ conflict.
12. Audit / revision remain free of raw values.
13. Capability model unchanged (`payment_view / payment_edit`
    compatibility only; no requirement to grant `payment_view` for
    `payment_edit`-only actors).
14. Banks=0 compatibility preserved; KEEP `bank_name` does not re-
    validate active bank status.
15. `op: "set"` for `account_number` requires digits-only
    `^[0-9]{1,64}$` (closes F-03 — masked STK cannot be persisted).
16. KEEP for STK requires existing row (entry must have a payment row
    already).
17. Response projection unchanged (`{entry_id, entry_version,
    payment_version}`).

### 3.3 Test matrix (17 cases must add)

The T1B PGlite test (`scripts/p1.6-i04c3-r4-s03-db.test.mjs`) must add
17 cases:

1. KEEP all three fields → preserved unchanged.
2. SET `bank_name` only, KEEP STK and holder → STK preserved.
3. CLEAR `account_number` only, KEEP `bank_name` and holder.
4. SET `account_number` (digits-only), KEEP `bank_name` and holder.
5. SET all three fields.
6. CLEAR all three fields → state = `omitted`, `bank_id = NULL`.
7. All-KEEP → 400 no-op.
8. `op: "set"` without `value` → 400.
9. `op: "keep"` with `value` → 400.
10. `op: "clear"` with `value` → 400.
11. SET `bank_name` clears `bank_id` (was non-null before).
12. KEEP `bank_name` preserves `bank_id` (was non-null before).
13. SET `account_number: "••••••••0056"` → 400 (F-03 close).
14. Replay (same key, same ops + SET) → idempotent.
15. Replay (same key, different op) → 409 conflict.
16. Audit / revision contain no raw STK / `bank_name` / holder.
17. Banks=0 with KEEP `bank_name` (no active-bank re-validation).

### 3.5 TS contract delta

`src/lib/direct-entry/payment-contract.ts`:

- Replace `AccountMetadataInput` with a discriminated union:
  ```ts
  export type AccountMetadataField =
    | { op: "keep" }
    | { op: "set"; value: string }
    | { op: "clear" };
  export type AccountMetadataOperation = {
    account_number: AccountMetadataField;
    bank_name: AccountMetadataField;
    account_holder_name: AccountMetadataField;
  };
  ```
- Replace `projectAccountMetadataInput` with
  `projectAccountMetadataOperation`:
  - Requires exact 3 keys.
  - For each field, requires `op` ∈ `{"keep", "set", "clear"}`.
  - For `op: "set"`, validates the value:
    - `account_number`: digits-only `^\d{1,64}$` (closes F-03).
    - `bank_name` / `account_holder_name`: text 1..256, no control
      chars, trim Unicode whitespace.
  - Rejects `op: "set"` without `value`; rejects `op: "keep" /
    "clear"` with extra keys.

- Update `projectRequest` to require the new operation-based body
  shape.
- No change to authority, CSRF, content-type, idempotency-key, OCC, or
  conflict sanitization.

`src/lib/direct-entry/write-repository.ts`:

- Widen the `updatePayment` input union to
  `PaymentInput | AccountMetadataOperation`.
- No new RPC; existing RPC carries the operation map as jsonb.
