### A.5 Lock/atomicity pattern that W03 must reuse

W01D's atomic mutation RPC (`direct_entry_apply_team_leader_mutation`, #71:1075–1640) is the canonical lock-order template for any mutation that touches a leader aggregate. The exact order, with line numbers, is:

1. **Team aggregate row** — `select t.* into v_team from public.teams t where t.team_id = p_team_id for update` (#71:1081). W03 mutations that do not touch a team aggregate do not lock this row.
2. **Idempotency lookup** — read-only `select` on `direct_entry_rpc_idempotency` (#71:1102); no lock.
3. **Idempotency payload hash + version check** — `v_team.version <> p_expected_version` raises `40001 'team version conflict'` (#71:1119). W03 mutations compare OCC on the relevant aggregate (app-user `version` for W03A; no aggregate version is required for W03B/C because the partial unique indexes and overlap triggers are the OCC).
4. **App-user row lock** — `perform u.app_user_id from public.direct_entry_app_users u where u.app_user_id = any(v_actor_ids) order by u.app_user_id for update` (#71:1170–1173). W03 mutations must lock the affected app users in the same `order by u.app_user_id` (a stable UUID order). W03A locks exactly one app user (the one being enabled / disabled); W03B / W03C lock the affected app user.
5. **Scope grant row locks** — `perform s.grant_id from public.direct_entry_scope_grants s where s.app_user_id = any(v_actor_ids) and s.scope_kind = 'team' order by s.app_user_id, s.grant_id for update` (#71:1181–1185). W03B scope mutation locks the same way. The leader path filters on `scope_kind = 'team'`; a W03B scope mutation on `own` or `all` must use the matching filter.
6. **Capability grant row locks** — `perform g.grant_id from public.direct_entry_capability_grants g where g.app_user_id = any(v_actor_ids) and g.capability = 'team_manager_assign' order by g.app_user_id, g.grant_id for update` (#71:1186–1190). W03B capability mutation locks the same way; W03A locks every open capability row of the app user (the W03A RPC does not filter on capability, it locks all rows of the app user in `(app_user_id, grant_id)` order).
7. **Advisory locks, in lexical `order by key`** — `for v_lock_key in select distinct key from unnest(array['capability:…','scope:…','recruiter-link:…']) as keys(key) where key is not null order by key loop perform pg_advisory_xact_lock(hashtextextended(v_lock_key, 0));` (#71:1191–1210). W03 mutations use the same keys for the same tables and the same `order by key` lexical order. The `recruiter-link:<app_user_id>` key is the same one the foundation `direct_entry_guard_effective_interval` trigger uses at `:517`; locking it ahead of any link write serialises against any concurrent link writer.
8. **Link row lock (link path only)** — `perform l.link_id from public.direct_entry_app_user_recruiter_links l where l.app_user_id = p_target_leader_app_user_id order by l.link_id for update` (#71:1213–1216). W03C link lifecycle locks the same way.
9. **Recruiter row lock (link path only)** — `select r.active into v_recruiter_active from public.recruiters r where r.recruiter_id = v_recruiter_id for update` (#71:1228–1230). W03C link lifecycle locks the same way.
10. **Advisory locks for provider / team-membership** — `for v_lock_key in select key from unnest(array['provider:<recruiter_id>','team-membership:<recruiter_id>']) as keys(key) order by key loop perform pg_advisory_xact_lock(hashtextextended(v_lock_key, 0));` (#71:1234–1240). W03C link lifecycle does not need to lock the provider / team-membership keys for verified-link creation (it has no provider / team-membership write), but if a future W03C variant needs to read a provider / team-membership row, it must use the same keys in the same lexical order.
11. **Provider membership row lock and team membership row lock (link path only)** — `perform m.membership_id from public.recruiter_provider_memberships m where m.recruiter_id = v_recruiter_id order by m.membership_id for update` (#71:1242–1246), then the team-membership equivalent. W03C does not lock these for verified-link creation.

**R1 correction 2 (mandatory after #71) — W03 grant/scope/link mutations must reuse the same lock order and advisory keys, not introduce a parallel helper with a different order.** A W03 mutation that locks the scope row before the capability row, or that skips the advisory lock on `recruiter-link:<app_user_id>`, or that locks a different set of rows, can deadlock with a concurrent W01D leader designate / revoke RPC. The shared order is the only correctness guarantee; the tests must observe no deadlock in the tested paths within a bounded timeout. R2 does **not** claim the W03 mutations make deadlocks "impossible" or that waits are strictly "FIFO" — both claims are unprovable from the source. The contract is: deterministic shared order, bounded-time concurrency regression, no deadlock in the tested paths.

**Authority on the link side.** The advisory key `recruiter-link:<app_user_id>` is the same one the foundation overlap trigger acquires (foundation `:517`). A W03C link write that takes the same advisory lock ahead of its `insert` / `update` serialises against any concurrent `direct_entry_guard_effective_interval` trigger execution and against any other W03C / W01D link writer; a W03C link write that **does not** take the advisory lock races the trigger and may produce a `23P01` it should have prevented.

**R1 correction 3 (mandatory after #71) — the marker GUC `direct_entry.team_leader_marker` is exclusively owned by the W01D leader lifecycle.** On `main` at `1189c8a`, the only callsite of `set_config('direct_entry.team_leader_marker', 'on', true)` is the W01D leader apply helper at #71:1384. W03A, W03B and W03C do **not** call `set_config('direct_entry.team_leader_marker', 'on', true)` and do **not** set any sibling flag. W03A does not cascade the disable into capability / scope / link closure (see §C.1); W03B same-day cancellation of a non-leader capability / scope is locked fail-closed with `22023` (see §C.2); W03C link lifecycle does not write zero-length markers on the link table and does not insert a fresh row on link closure — the link CHECK is still strict (`valid_to > valid_from`) on `main` and a W03C link closure updates the current link row's `valid_to` rather than opening a new interval. R3 removes every R1 / R2 mention of W03A setting the GUC, every R1 / R2 mention of a W03B / W03C fresh-row-after-revoke pattern, and every R1 / R2 mention of a W03B / W03C same-day marker path; the locked fail-closed policy is stated explicitly in §C.1, §C.2 and §C.3.

### A.6 The leader-owned authority bundle

The atomic leader bundle is a tuple of three rows written in one transaction by the W01D `direct_entry_apply_team_leader_mutation` RPC:

1. `direct_entry_team_leader_assignments` row keyed by `team_id` (and the partial-open `team_open_uidx`).
2. `direct_entry_scope_grants` row: `app_user_id = leader, scope_kind = 'team', team_id = <team>`, coextensive on `(valid_from, valid_to)` with the assignment row.
3. `direct_entry_capability_grants` row: `app_user_id = leader, capability = 'team_manager_assign', valid_from = <valid_from>`, coextensive on `(valid_from, valid_to)` with the assignment row.

The bundle's invariants, all enforced by the W01D postcondition block at #71:1418–1490, are:

- Exactly one current leader per team (`v_post_team_assignment_count = 1`).
- Exactly one current team-scope row for the current leader in the team (`v_post_target_team_scope_count = 1`).
- Exactly one current `team_manager_assign` row for the current leader (`v_post_capability_count = 1`).
- The assignment's `(valid_from, valid_to)` is `IS NOT DISTINCT FROM` the scope's and capability's `(valid_from, valid_to)` (coextensivity). The postcondition queries assert `s.valid_from = a.valid_from and s.valid_to is not distinct from a.valid_to` (and the same for capability), so a leader-bundle row whose dates drift from the assignment row fails `55000`.
- Replace closes the outgoing bundle atomically (one `team_leader_assignment` close + one `team_manager_assign` close + one `team` scope close) and opens the incoming bundle in the same transaction; the W01D `55000 'team leader mutation postcondition failed'` postcondition is the only safety net if any of the three rows is mis-shaped.
- Revoke closes the bundle atomically (one close on each of the three rows) and creates a zero-length marker on each interval to record the closure; the transaction-local `direct_entry.team_leader_marker` GUC is on for the duration of the close write.

**R1 correction 3 (mandatory after #71) — leader bundle cannot be partially mutated by a generic W03 grant/scope/link RPC.** A W03 grant/scope/link mutation that:

- Inserts a `team_manager_assign` capability outside the W01D designate RPC, or
- Inserts/updates a `team` scope row whose `(valid_from, valid_to)` does not match an existing leader assignment row, or
- Closes only the capability row (or only the scope row) of an existing leader bundle,

must fail closed. The marker trigger's transaction-local flag is the W01D mechanism; W03 generic mutations must not set that flag. The legacy W05A seed `direct_entry_seed_team_scope_grants()` exists and is verified by the W01D self-check to still be present, but it has been **revoked from every role** (`public, anon, authenticated, service_role`) at #71:1969–1970 and is not a runtime grant path. The W03 design must treat the leader bundle as owned by the W01D RPCs; W03 generic mutations may grant/revoke other capabilities (`recruiter_master_manage`, `audit_view`, `entry_restore`, `pii_view`, `pii_export`, etc.) and other scopes (`own`, `all`) but must not touch the leader bundle except through the W01D RPC.

## C. Locked mutation contracts

Every W03 mutation RPC must satisfy every row below, **simultaneously**. The W03 lanes in §F assert each row for each W03 slice.

### C.1 App-user aggregate (W03A — required schema delta)

**Contract.** `direct_entry_app_users` must carry enough state for concurrent account-status changes to use optimistic concurrency control and to be auditable. **The W03A mutation touches only the `direct_entry_app_users` row, the new `direct_entry_app_user_revisions` row, the `direct_entry_restricted_reasons` row, the `direct_entry_rpc_idempotency` row and the `direct_entry_audit_events` row. W03A does not mutate any capability grant, scope grant, verified link or leader assignment row.** When a user is disabled, the open capability / scope / link / leader rows remain in the database unchanged; the disabled state is enforced by the next actor resolution (W08A `direct_entry_resolve_actor_context` already returns `enabled = false` and the W03A lane must assert the same fail-closed path). When the user is re-enabled, the open intervals are effective again without re-write. The "what happens to a leader who is disabled mid-assignment" question is a **product decision** that W03A does not make; a permanent deprovision that closes the leader bundle is a separate, larger RPC and is **out of W03A scope**.

Minimum schema delta (the W03A migration must add, append-only, and the W03A self-check must assert):

- `version integer not null default 1 check (version >= 1)` — same shape as `recruiters.version` and `teams.version`. Every enable/disable RPC reads, compares, increments and writes `version` in a single transaction.
- `updated_at timestamptz not null default now()` — bumped on every status change.
- A new `direct_entry_app_user_revisions` table mirroring `direct_entry_team_leader_revisions`: `(revision_id uuid pk, app_user_id uuid fk, version integer, actor_user_id uuid, action text check in ('enable','disable','capability_grant','capability_revoke','scope_grant','scope_revoke','link_create','link_revoke'), before_snapshot jsonb, after_snapshot jsonb, reason_id uuid fk, created_at timestamptz default now(), check (version >= 1), unique(app_user_id, version))`. This eight-verb CHECK is exact: it equals every action W03A/B/C actually writes — no `create`, no `app_user_enable`, no extra verb. Forced RLS, no privilege to any role, internal `SECURITY DEFINER` writer.
- One reason + one audit event per `version` increment. The audit event is the W01D `direct_entry_audit_events` row: `action in ('enable','disable')` for W03A (and `capability_grant/revoke`, `scope_grant/revoke`, `link_create/revoke` for W03B/C per §C.2/§C.3), `capability = 'entry_admin'` (the audit records the authority the Full Admin triple has exercised, not a non-existent token), `outcome = 'APPLIED'`, `changed_fields = array['enabled']` (W03A), `app_user_revision_id = <new app-user revision>` (never `revision_id`). **W03A does not add a new capability token.** The audit `capability` column already accepts the existing 23-token vocabulary (`direct_entry_audit_events.capability` is free-form text constrained to `length(action) between 1 and 96` and the 23-token CHECK on `direct_entry_capability_grants.capability` does not apply to audit rows); W03A writes `'entry_admin'` to record the Full Admin authority that gated the mutation. If Owner/T0 later decide to introduce a new token (e.g., to make the audit `capability` semantic instead of authority-derived), that is a separate capability-vocabulary delta to be reviewed against the W01A 23-token contract, not a W03A scope expansion.

**W03A mutation RPCs (service-role-only, `search_path = pg_catalog, public`, EXECUTE to `service_role` only):**

- `direct_entry_enable_app_user(p_auth_subject, p_actor_app_user_id, p_target_app_user_id, p_expected_app_user_version integer, p_reason text, p_idempotency_key text)` — locks the **distinct** actor and target `direct_entry_app_users` rows in UUID order (one row if `actor = target`), then re-evaluates the actor authority under lock (the W03A helper per §C.2.1: recheck `enabled` + Full Admin triple + effective `all`). W03A takes no child-row locks and no advisory locks — it writes no child rows and has no overlap-trigger race to serialise. Asserts `p_target_app_user_id.enabled = false`, asserts `p_expected_app_user_version = current`, writes `enabled = true`, `version = current + 1`, `updated_at = now()`. Appends one `direct_entry_app_user_revisions` row (`action = 'enable'`, `before_snapshot`/`after_snapshot` = `{target_app_user_id, changed: {enabled}, interval: null, actor_app_user_id}` with fixed keys only — no `auth_subject`/email/PII). Appends one `direct_entry_audit_events` row (`app_user_id = actor`, `resource_ref = <target aggregate reference>`, `capability = 'entry_admin'`, `action = 'enable'`, `app_user_revision_id = <new revision>`, never `revision_id`). Appends one reason and one idempotency record. Returns `{app_user_id, version, revision_id, change = 'enable'}`.
- `direct_entry_disable_app_user(p_auth_subject, p_actor_app_user_id, p_target_app_user_id, p_expected_app_user_version integer, p_reason text, p_idempotency_key text)` — Symmetric. Same distinct-row lock-then-recheck, no child/advisory locks. Asserts `p_target_app_user_id.enabled = true`, asserts `p_expected_app_user_version = current`, writes `enabled = false`, `version = current + 1`, `updated_at = now()`. **Does not cascade to capability, scope, link or leader rows.** Appends one `direct_entry_app_user_revisions` row (`action = 'disable'`, envelope `{target_app_user_id, changed: {enabled}, interval: null, actor_app_user_id}` fixed keys), one `direct_entry_audit_events` row (`app_user_id = actor`, `resource_ref = <target aggregate reference>`, `capability = 'entry_admin'`, `action = 'disable'`, `app_user_revision_id = <new revision>`, never `revision_id`), one reason, one idempotency record. The disabled state is enforced by the next actor resolution (W08A) and by every W03 / W01D RPC that reads `enabled`. The `disabled` actor is rejected at the next request even if capability / scope / link intervals are still live.

**W03A atomicity / authority (R4 lock).** Lock order follows §A.5 with the team-aggregate step omitted and without any child or advisory lock: (a) `for update` on the **distinct** actor and target `direct_entry_app_users` rows in UUID order — one row when `actor = target`; (b) the read-only idempotency lookup; (c) the OCC `version` compare (raises `40001 'app user version conflict'` on mismatch); (d) the W03A `direct_entry_assert_actor_app_user_admin(p_auth_subject, p_actor_app_user_id)` helper (lock-then-recheck per §C.2.1) enforcing actor `enabled` + the Full Admin triple + effective `all` scope under the held locks. **Why W03A needs no child/advisory locks:** W03A writes only the `direct_entry_app_users` row; it writes no capability / scope / link / assignment row, so it never races the `direct_entry_guard_effective_interval()` advisory keys (`capability:…`, `scope:…`, `recruiter-link:…`) and never contends for a child `for update`. The app-user row lock plus the post-lock authority recheck is sufficient for W03A's only invariant. W03B / W03C do write child rows and therefore keep the canonical §A.5 row + advisory order compatible with W01D (§C.7). W03A does **not** set `set_config('direct_entry.team_leader_marker', 'on', true)`.

**W03A is the OCC root for W03A / W03B / W03C (R3 lock).** Every W03A / W03B / W03C mutation takes the target's `expected_app_user_version` as a parameter. The RPC locks the target `direct_entry_app_users` row, compares the live `version` against `expected_app_user_version`, raises `40001 'app user version conflict'` on mismatch, and on success bumps `version + 1` and `updated_at = now()`. The same transaction appends exactly one `direct_entry_app_user_revisions` row, one `direct_entry_audit_events` row, and one `direct_entry_rpc_idempotency` row. A replay (same `p_idempotency_key`) returns the original result without bumping version twice. The unique indexes and overlap triggers are invariant / concurrency guards and are **not** substitutes for the OCC `version` check; a parallel mutation that bypasses the version check is still caught by the index / trigger, but the OCC check is what surfaces the conflict as `40001` instead of a raw `23505` / `23P01`.

**Audit FK linkage (R4 lock).** W03A adds the column `direct_entry_audit_events.app_user_revision_id uuid references public.direct_entry_app_user_revisions(revision_id) on delete restrict` so the W03A / B / C audit rows point at the right revision. The existing `direct_entry_audit_events.revision_id` (FK to `direct_entry_revisions` of Direct Entry entries) is **not** used for the app-user revision; the W01A submission / change-request / leader revision FKs continue to be used for their respective surfaces. The single vocabulary rule: **revision `action` and audit `action` for W03A/B/C use the same eight short verbs** `('enable','disable','capability_grant','capability_revoke','scope_grant','scope_revoke','link_create','link_revoke')` — never `app_user_enable`/`app_user_disable`, never DB-object prefixes (`direct_entry_grant_*`, `direct_entry_link_*`); `entry_restore` is audit-only and belongs to W03E, never to an app-user revision. The `capability = 'entry_admin'` on the audit row records only the exercised Full Admin authority; the target mutation data (which capability/scope/link, which interval) lives in the revision snapshot. The revision envelope has exactly four fixed keys — `target_app_user_id`, `changed`, `interval`, `actor_app_user_id` — where `changed` names the mutation (`{enabled}`, `{capability, valid_from}` / `{scope_kind, team_id, valid_from}` / `{recruiter_id, valid_from}`, closed to `{valid_to}` on revoke) and `interval` carries `{valid_from, valid_to}`; the envelope has no `auth_subject`, no email, no secret, no raw PII; exact-key tests pin it.

**W03A closed scope.** The W03A migration does **not** add an invitation/initial-password/forced-reset/MFA path; it does not add a `direct_entry_invite` table, a `direct_entry_password_reset` table or a `direct_entry_mfa` table; the `direct_entry_app_users.display_name` change is a separate `change_request` path; the PII / email / phone change is the `change_request` path; the `auth.users` row is owned by Supabase Auth and is out of scope; **cascading deprovision of capability / scope / link / leader rows is out of W03A scope** and is a separate product decision. **P3.2 owns invitations, initial passwords, forced resets, MFA and account recovery.**

### C.2 Capability and scope interval mutations (W03B)

**Contract (R4 lock).** Capability and scope intervals are effective-dated, audited, reason-stamped, OCC-locked and idempotency-keyed. They are written by RPCs that follow the W01D lock order (see §A.5). The capability CHECK and scope CHECK are widened to `valid_to >= valid_from` by #71 §1; raw zero-length marker DML outside an audited RPC is still rejected with `23514` by `direct_entry_team_leader_marker()`. The partial marker-excluding unique index `direct_entry_capability_grants_open_start_uidx` rejects a duplicate open start with `23505`; the overlap trigger `direct_entry_capability_grant_no_overlap` rejects a non-duplicate open overlap with `23P01`. A unique index is **not** an exclusion constraint; `23P01` is reserved for the overlap trigger. **Cancellation (R4): every W03B revoke RPC accepts any `effective_date`.** When `effective_date > current.valid_from` the RPC closes normally (`valid_to = effective_date`); when `effective_date <= current.valid_from` (same-day cancellation, or cancellation of a scheduled-not-yet-started interval) the RPC closes as a zero-length inert marker (`valid_to = current.valid_from`) **inside the same audited revoke transaction** — same Full Admin authority, same target OCC compare, same reason, same app-user revision (`capability_revoke` / `scope_revoke`), same audit row, same idempotency. The marker row is inert on every date (live path = `valid_to IS NULL OR valid_to > valid_from`, so a `valid_to = valid_from` row never counts as effective), kept, and never re-dated — exactly the W01D marker semantics, reused by W03 through one shared trigger-function pattern, not a second framework. The W03 revoke RPC sets the marker GUC only around its own audited close (the W03B migration wires the existing `direct_entry_team_leader_marker()` trigger function onto its own audited path; it never touches the W01D leader-bundle rows). Revoke never hard-deletes: history is the closed/marker interval row plus the app-user revision plus the audit event. W03B never inserts a fresh row on revoke; W03B only UPDATEs the current row's `valid_to`. The W01D leader bundle stays W01D-owned: W03B still rejects `team_manager_assign` and leader-bundle `team` scope mutations with `42501`, and the W03B cancellation path never updates a leader-bundle row.

**Capability and scope are separate RPCs.** A W03B capability mutation RPC does not take `scope_kind` / `team_id`; a W03B scope mutation RPC does. The two surfaces do not share an RPC and never co-write a row in the same transaction.

**Signatures (R4 lock).** Every W03A / W03B / W03C mutation RPC takes `(p_auth_subject, p_actor_app_user_id, p_target_app_user_id, …)`. The actor identity is server-session-derived; the client business payload cannot override the actor (`p_actor_app_user_id` is resolved by the helper from `p_auth_subject` and is rejected if it disagrees with the session). The Full Admin triple + effective `all` scope is checked against the **actor**, not the target. The target is the app user whose state is being changed. If `p_actor_app_user_id = p_target_app_user_id`, the distinct set of rows to lock has one member and the row is locked **once**, not twice (§C.2.1 step 2).

**Revoke semantics (R4 lock).** Revoke is an **update** of the existing live interval row. When `p_effective_date > current.valid_from`: `update … set valid_to = p_effective_date, updated_at = now()` (normal close). When `p_effective_date <= current.valid_from` (same-day or scheduled-future cancellation): `update … set valid_to = current.valid_from, updated_at = now()` (zero-length inert marker, recorded under the shared marker trigger which the audited RPC has enabled for its own transaction). Revoke **does not insert** a new capability / scope / link row. Revoke **does not** re-issue the same capability / scope / link at `effective_date`. Revoke never hard-deletes. History is the closed/marker interval row plus the target app-user aggregate revision (envelope §C.1) plus the audit event. Exact behavior, SQLSTATE, OCC, idempotency, revision/audit and tests are locked per case:

- **current** (`p_effective_date > valid_from`, interval already effective): normal close; bump target `version + 1`; one revision + one audit (`app_user_revision_id`) + one idempotency; replay with same key returns the stored result without bumping twice.
- **same-day** (`p_effective_date = valid_from`): marker close (`valid_to = valid_from`); same authority + OCC + reason + revision + audit + idempotency as current; the marker row is inert on every date including the cancellation date itself; never re-dated.
- **scheduled-future** (`valid_from > today`, grant cancelled before it ever becomes effective): marker close (`valid_to = valid_from`); identical audited envelope to same-day; the interval never becomes effective at any date.
- **replay** (same `p_idempotency_key`, same request hash): returns the original result byte-identically; no second version bump, no second revision, no second audit row. A reused key with a different hash raises the idempotency conflict (`23505` → `409 duplicate`).
- Stale `expected_app_user_version` → `40001` with zero residue; missing/empty reason or idempotency key → `22023` with zero residue; non-Full-Admin actor after lock → `42501` with zero residue; raw marker DML outside the audited RPC → `23514`.

If the same target needs a new live interval after a revoke, the caller must issue a separate `grant_*` / `create_*` RPC; that RPC is a new write, not a continuation of the revoke.

**Same-day / scheduled-not-yet-started / future cancellation (R4 lock).** The W03B / W03C revoke RPCs accept any `effective_date` and never return `22023 'same-day cancellation is open'`. `effective_date > current.valid_from` closes normally (`valid_to = effective_date`); `effective_date <= current.valid_from` closes as the audited zero-length inert marker (`valid_to = current.valid_from`) inside the same Full Admin + OCC + reason + revision + audit + idempotency transaction. The marker reuses the shared `direct_entry_team_leader_marker()` trigger-function pattern — one inert-marker mechanism, one vocabulary: the marker row is `valid_to = valid_from`, inert on every date including the cancellation date itself, kept, and never re-dated. Raw marker DML outside the audited RPC is rejected with `23514`. No per-W03 GUC fork: the W03 revoke enables the shared marker path only around its own audited close. The link table (still `CHECK valid_to > valid_from` on `main`) needs the minimal delta in §C.3 to support this path; capability/scope tables already have it from #71.

**W03B capability mutation RPCs (service-role-only, `search_path = pg_catalog, public`, EXECUTE to `service_role` only):**

- `direct_entry_grant_capability(p_auth_subject, p_actor_app_user_id, p_target_app_user_id, p_capability, p_valid_from date, p_expected_app_user_version integer, p_reason text, p_idempotency_key text)`. Full Admin triple + effective `all` scope is required for the **actor** (see helper below). Asserts the `capability` is in the 23-token vocabulary (the DB CHECK rejects unknown with `23514`). Asserts no overlap on a live interval (the partial marker-excluding unique index `direct_entry_capability_grants_open_start_uidx` rejects a duplicate open start with `23505`; the overlap trigger `direct_entry_capability_grant_no_overlap` rejects a non-duplicate open overlap with `23P01`). Asserts the **target** app user is currently enabled (raises `42501 'target app user is not enabled'` otherwise). Locks the distinct actor and target app-user rows in UUID order, locks the actor's `direct_entry_scope_grants` rows before the actor's capability rows, takes the canonical advisory locks, then re-evaluates the actor authority under lock (§C.2.1). **Compares** the target's current `version` against `p_expected_app_user_version`; raises `40001 'app user version conflict'` on mismatch. Inserts one capability row, one target app-user revision (`action = 'capability_grant'`, envelope `{target_app_user_id, changed: {capability, valid_from}, interval: {valid_from, valid_to}, actor_app_user_id}` fixed keys), one reason, one audit event (audit `app_user_id = actor`, `resource_ref = <target aggregate reference>`, `capability = 'entry_admin'`, `action = 'capability_grant'`, `app_user_revision_id = <new revision>`), one idempotency record. Bumps the target's `version + 1` and `updated_at = now()`. **Rejects** the capability `team_manager_assign` with `42501 'security mutation is owned by the leader lifecycle RPC'` regardless of the actor's authority.
- `direct_entry_revoke_capability(p_auth_subject, p_actor_app_user_id, p_target_app_user_id, p_capability, p_effective_date date, p_expected_app_user_version integer, p_reason text, p_idempotency_key text)`. Same actor authority. Asserts the target is currently enabled. Asserts the target currently holds a live capability interval for `p_capability` (the partial unique index lookup returns 0 rows on miss; raises `42501 'capability is not effective'`). Accepts any `p_effective_date`: `p_effective_date > valid_from` closes normally, `p_effective_date <= valid_from` closes as the audited zero-length inert marker (`valid_to = valid_from`); never `22023`. Locks the distinct actor and target app-user rows in UUID order, locks the actor's scope rows before capability rows, takes the canonical advisory locks, then re-evaluates the actor authority under lock (§C.2.1). **Compares** the target's current `version` against `p_expected_app_user_version` (raises `40001` on mismatch). **Updates** the current row (`valid_to = p_effective_date` or the marker `valid_to = valid_from`, plus `updated_at = now()`). **Does not insert** a new capability row. **Does not** re-issue the capability. Never hard-deletes. Bumps the target's `version + 1` and `updated_at = now()`. Appends one target app-user revision (`action = 'capability_revoke'`, envelope `{target_app_user_id, changed: {capability, valid_from}, interval: {valid_from, valid_to}, actor_app_user_id}` fixed keys), one reason, one audit event (audit `app_user_id = actor`, `resource_ref = <target aggregate reference>`, `capability = 'entry_admin'`, `action = 'capability_revoke'`, `app_user_revision_id = <new revision>`), one idempotency record. **Rejects** `capability = 'team_manager_assign'` with `42501 'security mutation is owned by the leader lifecycle RPC'` regardless of the actor's authority.

**W03B scope mutation RPCs (service-role-only, `search_path = pg_catalog, public`, EXECUTE to `service_role` only):**

- `direct_entry_grant_scope(p_auth_subject, p_actor_app_user_id, p_target_app_user_id, p_scope_kind check in ('own','team','all'), p_team_id null when p_scope_kind <> 'team', p_valid_from date, p_expected_app_user_version integer, p_reason text, p_idempotency_key text)`. Same Full Admin authority for the **actor**. Asserts the target is currently enabled. Asserts the target does not currently hold a leader-bundle `team` scope (see leader-bundle denial below). Rejects any `team` scope whose `team_id` is the `__system_vendor__` reserved team (`23514`, same as #71:1086). Locks the distinct actor and target `direct_entry_app_users` rows in UUID order, locks actor `direct_entry_scope_grants` rows before actor capability rows, and locks the target's existing scope rows of the same `(scope_kind, team_id)`. **Compares** the target's current `version` against `p_expected_app_user_version` (raises `40001` on mismatch). Inserts one scope row, one target app-user revision (`action = 'scope_grant'`, envelope `{target_app_user_id, changed: {scope_kind, team_id, valid_from}, interval: {valid_from, valid_to}, actor_app_user_id}` fixed keys), one reason, one audit event (audit `app_user_id = actor`, `resource_ref = <target aggregate reference>`, `capability = 'entry_admin'`, `action = 'scope_grant'`, `app_user_revision_id = <new revision>`), one idempotency record. Bumps the target's `version + 1` and `updated_at = now()`. Leader-bundle `team` scope rule: the RPC checks whether a current `team_manager_assign` capability exists for `p_target_app_user_id` at the same `p_valid_from` or an open `team_manager_assign` at `p_valid_from <= today`; if so, raises `42501 'team scope mutation is owned by the leader lifecycle RPC'`.
- `direct_entry_revoke_scope(p_auth_subject, p_actor_app_user_id, p_target_app_user_id, p_scope_kind, p_team_id, p_effective_date date, p_expected_app_user_version integer, p_reason text, p_idempotency_key text)`. Same actor authority. Asserts the target is currently enabled. Asserts the target currently holds a live scope interval for the given `(scope_kind, team_id)` (raises `42501 'scope is not effective'` on miss). Accepts any `p_effective_date`: `p_effective_date > valid_from` closes normally, `p_effective_date <= valid_from` closes as the audited marker (`valid_to = valid_from`); never `22023`. Rejects leader-bundle `team` scopes with `42501`. Locks per §A.5. **Compares** the target's `version` (raises `40001` on mismatch). **Updates** the current scope row (`valid_to = p_effective_date` or marker `valid_to = valid_from`, plus `updated_at = now()`). Bumps the target's `version + 1`. Appends one target app-user revision (`action = 'scope_revoke'`, envelope `{target_app_user_id, changed: {scope_kind, team_id, valid_from}, interval: {valid_from, valid_to}, actor_app_user_id}` fixed keys), one reason, one audit event (audit `app_user_id = actor`, `resource_ref = <target aggregate reference>`, `capability = 'entry_admin'`, `action = 'scope_revoke'`, `app_user_revision_id = <new revision>`), one idempotency record. Never hard-deletes.

**Authority helper.** A new helper `direct_entry_assert_actor_app_user_admin(p_auth_subject, p_actor_app_user_id)` enforces the **Full Admin triple** (`entry_admin` AND `recruiter_master_manage` AND `team_master_manage` at effective `all` scope) for the **actor**. The helper is called **after** the actor and target app-user rows are locked (R3 lock-then-recheck, see §C.7). The helper returns the exercised authority (`'entry_admin'`) only after the triple is satisfied under lock; if a token is missing, if the actor is not currently `enabled`, or if the actor's effective scopes do not include `all`, the helper raises `42501 'actor is not a Full Admin'` and the W03B RPC rolls back. The helper does **not** evaluate authority outside the transaction and does **not** skip the re-evaluation under lock.

**W03B explicitly does not write:** any row of the W01D leader bundle (the W01D designate/replace/revoke RPCs own `team_manager_assign`, the leader `team` scope and `direct_entry_team_leader_assignments`); any row on `direct_entry_app_user_recruiter_links` (W03C owns the link table). A W03B RPC that detects a leader-bundle violation raises `42501 'security mutation is owned by the leader lifecycle RPC'` and rolls back, so the W03B cancellation path can never close a leader-bundle row.

### C.2.1 Lock-then-recheck actor authority (R4, applies to every W03A / W03B / W03C mutation)

The R2 claim that "a parallel disable / revoke between the lock and the helper cannot happen because the helper itself is the first write step after the lock" is rejected. A parallel session can change the actor's effective authority between the moment the helper begins and the moment the helper commits. R4 therefore locks the actor and target first, then re-evaluates actor authority under lock, then validates, then writes. The order is canonical and applies uniformly to `direct_entry_enable_app_user`, `direct_entry_disable_app_user`, `direct_entry_grant_capability`, `direct_entry_revoke_capability`, `direct_entry_grant_scope`, `direct_entry_revoke_scope`, `direct_entry_create_verified_link`, `direct_entry_revoke_verified_link` (W03C reuses the same §A.5 lock order without the team-aggregate step, plus the link advisory lock), and `direct_entry_restore_entry` (W03E reuses the same order with the actor-authority recheck on the actor's own security rows, never on the target entry).

1. **Resolve actor mapping.** The RPC body resolves the actor from `p_auth_subject` (server session) and `p_actor_app_user_id` (param). If the param disagrees with the session-derived mapping, the RPC raises `42501 'actor identity is not derived from the session'` and rolls back. The client business payload cannot override the actor.
2. **Lock app-user rows in UUID order.** The RPC takes `for update` on the **distinct** `direct_entry_app_users` rows of actor and target (`select … where u.app_user_id = any(v_actor_ids) order by u.app_user_id for update`). If `actor = target`, the distinct set has one member and the row is locked **once** — this holds for every W03A/B/C RPC, including W03A; there is no "single target row" phrasing and no second lock.
3. **Lock actor scope rows before actor capability rows.** Per W01D #71 step order, the actor's `direct_entry_scope_grants` rows are locked before the actor's `direct_entry_capability_grants` rows. The W03B scope RPC also locks the target's existing scope rows of the same `(scope_kind, team_id)`.
4. **Lock target child rows.** W03B capability RPC locks the target's `direct_entry_capability_grants` rows of `p_capability`. W03B scope RPC locks the target's `direct_entry_scope_grants` rows of `(p_scope_kind, p_team_id)`. W03C link RPC locks the target's `direct_entry_app_user_recruiter_links` rows in `link_id` order. W03A locks **no** child rows (steps 3–4 and 5 do not apply to W03A — see §C.1 for why).
5. **Take canonical advisory locks in lexical order.** W03B takes the same advisory keys W01D uses for the same tables, in lexical `order by key`; W03C takes `recruiter-link:<app_user_id>` ahead of any link write. W03A takes none. The W01D leader-bundle advisory locks are not taken by W03 because W03 does not write leader-bundle rows.
6. **Recheck actor authority under lock.** After the applicable row locks and advisory locks are held, the helper `direct_entry_assert_actor_app_user_admin` re-reads the actor's `enabled` flag, re-evaluates the Full Admin triple (`entry_admin` AND `recruiter_master_manage` AND `team_master_manage`), and re-evaluates the actor's effective scopes (must include `all`). The helper returns the exercised authority only if all three are satisfied. A parallel disable / revoke / scope change that lands after the lock is caught here: the re-read sees the new value and the helper raises `42501 'actor is not a Full Admin'`. The RPC rolls back.
7. **Validate and mutate target.** Only after the actor authority has been re-evaluated under lock does the RPC validate the target's enabled flag, the target's `expected_app_user_version`, and the new interval's invariants (including the cancellation rule: normal close vs audited marker). The mutation runs to completion with the target's app-user version bumped by exactly one, the corresponding app-user revision appended, the reason / audit / idempotency rows written, and the transaction committing. A replay (same `p_idempotency_key`) returns the original result without bumping version twice.

If any step fails, the entire transaction rolls back with zero residue (no partial revision, no partial audit, no partial idempotency). The actor authority recheck is a hard requirement, not an optional optimization.

### C.3 Verified link lifecycle (W03C)

**Contract (R4 lock).** On `main` at `1189c8a` the link table is strict half-open (`CHECK (valid_to is null or valid_to > valid_from)`, foundation `:62`), so it cannot hold an audited same-day cancellation. The cardinality guard for verified links is the existing foundation trigger `direct_entry_recruiter_link_no_overlap` at foundation `:555–556`, calling `direct_entry_guard_effective_interval()` at `:516–528`, which acquires the advisory lock `recruiter-link:<app_user_id>` and asserts no overlap on every other verified row of the same `app_user_id` with `23P01` on conflict. **W03C does not add a partial unique index for "verified effective today"** — partial unique indexes cannot be conditioned on the current date; the trigger is the cardinality guard. The W01D designate write additionally requires `count(*) = 1 verified effective link` as defense-in-depth at runtime (`42501`, #71:1217). W03C adds lifecycle RPCs, audit, reason, OCC and idempotency, and reuses the existing trigger and the existing per-`(app_user_id, recruiter_id, valid_from)` unique key (foundation `:71`). The overlap trigger raises `23P01`; the unique key raises `23505` if a duplicate `(app_user_id, recruiter_id, valid_from)` is inserted. A unique key is **not** an exclusion constraint; `23P01` is reserved for the overlap trigger.

**W03C minimal schema delta (required, R4).** To support audited cancellation on links (FIX 1) with the smallest possible change and no second marker framework, the W03C migration performs exactly three append-only DDL steps and nothing else on this table:

1. `alter table public.direct_entry_app_user_recruiter_links drop constraint <link_interval_check>;` and `add constraint <link_interval_check> check (valid_to is null or valid_to >= valid_from)` — the same widening #71 §1 applied to capability and scope.
2. `create trigger direct_entry_link_marker_guard before insert or update of valid_from, valid_to on public.direct_entry_app_user_recruiter_links for each row execute function public.direct_entry_team_leader_marker();` — reuses the **existing** W01D trigger function (same `SECURITY DEFINER`, same `23514`, same GUC guard); no new function, no new GUC, no forked semantics.
3. The `valid_to = valid_from` marker row must stay out of the verified-cardinality path. The existing `direct_entry_recruiter_link_no_overlap` trigger already uses `daterange(l.valid_from, l.valid_to, '[)')`, which is empty for a zero-length interval, so a marker never overlaps and never counts as a verified effective link; no extra partial index is needed on this table (W03C still adds none).

Every other aspect of the link table — columns, the per-`(app_user_id, recruiter_id, valid_from)` unique key, the no-overlap trigger, forced RLS, revoked grants — is byte-stable across W03. The W03C self-check asserts the widened CHECK, the installed marker trigger, and that no `delete`/`hard delete` path exists. Raw zero-length DML from any non-audited path remains rejected with `23514`.

**W03C mutation RPCs (service-role-only, `search_path = pg_catalog, public`, EXECUTE to `service_role` only):**

- `direct_entry_create_verified_link(p_auth_subject, p_actor_app_user_id, p_target_app_user_id, p_recruiter_id, p_valid_from date, p_expected_app_user_version integer, p_reason text, p_idempotency_key text)`. — the Full Admin triple + effective `all` scope is required. Asserts the recruiter is active. Asserts the app user is enabled (`42501 'app user is not enabled'`). Asserts the `app_user_id` does not currently hold a different verified effective link (the foundation trigger raises `23P01`; the RPC catches the trigger error and re-raises `42501 'app user already has a verified link'`). Takes the advisory lock `recruiter-link:<app_user_id>` ahead of the `insert` (§A.5 step 7). Inserts one link row (`verified = true`), bumps the target `version + 1`, appends one target app-user revision (`action = 'link_create'`, envelope `{target_app_user_id, changed: {recruiter_id, valid_from}, interval: {valid_from, valid_to}, actor_app_user_id}`), one reason, one audit event (`action = 'link_create'`, `capability = 'entry_admin'`, `app_user_revision_id = <new revision>`), one idempotency record.
- `direct_entry_revoke_verified_link(p_auth_subject, p_actor_app_user_id, p_target_app_user_id, p_recruiter_id, p_effective_date date, p_expected_app_user_version integer, p_reason text, p_idempotency_key text)`. — Same actor authority. Asserts the link is currently verified-effective. **Accepts any `p_effective_date`**: `p_effective_date > valid_from` closes normally (`valid_to = p_effective_date`); `p_effective_date <= valid_from` closes as the audited zero-length inert marker (`valid_to = valid_from`) — same-day cancellation and cancellation of a scheduled-not-yet-started link are both supported and never return `22023`. **Updates** the current link row (`valid_to = p_effective_date` or the marker `valid_to = valid_from`, plus `updated_at = now()` where the column exists). **Does not insert** a new link row, **does not** hard-delete, **does not** re-issue the link. Bumps the target's `version + 1`. Appends one target app-user revision (`action = 'link_revoke'`, envelope `{target_app_user_id, changed: {recruiter_id, valid_from}, interval: {valid_from, valid_to}, actor_app_user_id}`), one reason, one audit event (audit `app_user_id = actor`, `resource_ref = <target aggregate reference>`, `capability = 'entry_admin'`, `action = 'link_revoke'`, `app_user_revision_id = <new revision>`), one idempotency record. The W01D leader-read path is **not** affected because leader-read joins on the persisted `a.leader_recruiter_id` FK, not on the link (per the W01D A2 server contract survey R4–R5).

**W03C atomicity.** Follows §A.5 steps 1 (team — only if the link is being changed for a current leader; W03C does not lock the team for an ordinary create / revoke), 2 (distinct actor + target app-user rows in UUID order), 4 (app-user), 7 (advisory lock `recruiter-link:<app_user_id>`), 8 (link row in `link_id` order, when revoking), 9 (recruiter row, when revoking), then the post-lock actor-authority recheck (§C.2.1 step 6). W03C does **not** take the W01D capability / scope advisory locks because W03C does not write capability / scope rows. W03C enables the shared marker path only around its own audited close; it never writes a leader-bundle row.

### C.4 Bounded audit projection by mode (W03D)

**Contract.** `direct_entry_read_audit(...)` is too broad for a browser W03 contract (it returns the raw row including `auth_subject`, reason references, revision FKs and changed_fields). W03D adds a new service-role RPC `direct_entry_read_security_audit(auth_subject, app_user_id, mode, page, page_size)` where `mode ∈ {'full','catalog','own_manager'}`. The RPC returns a JSONB list of bounded event rows, exactly the fields the W03 UI needs:

- `event_id` (uuid), `created_at` (timestamptz), `action` (text), `capability` (text or null), `scope_kind` (text or null), `scope_team_id` (uuid or null), `outcome` (text), `changed_fields` (text[]), `team_id_or_resource_ref` (text, the bounded opaque reference — never the actor's `auth_subject`).
- The mode `full` is Admin-only (`entry_admin + recruiter_master_manage + team_master_manage` triple + effective `all`) and returns the full bounded set.
- The mode `catalog` is `catalog_master_manage@all` and is filtered by an **explicit exact `action` allowlist** (R4), not by `capability`. The allowlist covers catalog and worker events only and **excludes** every security action regardless of the audit `capability` field: the full Security slice (`enable`, `disable`, `capability_grant`, `capability_revoke`, `scope_grant`, `scope_revoke`, `link_create`, `link_revoke`, `entry_restore`) is excluded by action. The filter is `audit.action = ANY(<allowlist>)`; it never uses `LIKE` or `*` wildcards; it never uses `audit.capability` as the primary classifier. The catalog mode also strips the `auth_subject`, the actor `app_user_id` (other than the caller), the reason text, and any PII before the projection is returned.
- The mode `own_manager` (R4 lock) is a `team_manager_assign@team` actor whose projection may **only** surface the manager-assignment events the team leader is entitled to see. The correct allowlist is exactly `('project_manager_assignment_assign','project_manager_assignment_unassign')` — the W02 lifecycle audit verbs — plus the W02 scheduled-cancel action **only if W02 actually writes one** (at `1189c8a` no such action exists in the W02 source; a future scheduled-cancel verb joins this allowlist only after its writer lands and by Owner/T0 decision — it is never inferred). The `own_manager` projection filters `action = ANY(<that allowlist>) AND scope_team_id = caller.effective_team_id`, where `scope_team_id` is the `app_user_id`'s effective team. **W02 writers must record `scope_kind = 'team'` and `scope_team_id = <leader team>` whenever the exercised authority is `team_manager_assign@team`; the `all` authority path (W02 `entry_admin@all` assigns) keeps `scope_kind = 'all'`.** The allowlist never contains `team_leader_designate`/`team_leader_replace`/`team_leader_revoke` (those are the W01D team-leader bundle, not a manager assignment). Cross-team `own_manager` reads are rejected with `42501`. Full Admin `full` and Accounting `catalog` modes are unchanged.

**Forbidden in the bounded projection (W03D RPC).** `auth_subject`, `app_user_id` (other than the caller's), `reason_id`, raw reason text, credential/token, storage key, raw DB error, any PII (email, phone, name, CCCD), any UUID that would identify a real person outside the W03 audit policy.

**W03D also adds** a new `direct_entry_read_security_audit_self_check()` (internal) that the W03D migration self-check runs to assert: every returned column is in the allowlist; no `auth_subject` is serialised; the SQLSTATE 42501 fires for any non-Full-Admin caller asking for `mode = 'full'`; the SQLSTATE 42501 fires for any non-`catalog_master_manage@all` caller asking for `mode = 'catalog'`; the SQLSTATE 42501 fires for any non-`team_manager_assign@team` actor asking for `mode = 'own_manager'` and not owning the team id.

**W03D does not** add a "fetch all then hide client-side" path. The bounded set is enforced server-side at the SQL level. The page is request-time and never cached.

### C.5 Admin-only `entry_restore` (W03E) — locked scope, locked policy, locked contract bump (R3)

**Contract (R3 lock).** T0 has decided that `entry_restore` requires the actor to hold effective `all` scope. The `entry_restore` capability alone is **not** sufficient. The W03E RPC therefore requires (a) the `entry_restore` capability on the actor, (b) the Full Admin triple on the actor, (c) effective `all` scope on the actor, (d) a non-empty `reason`, (e) the target's `expected_entry_version`, and (f) a unique `idempotency_key`. The `direct-entry-auth` contract version bumps from `direct-entry-auth/1.3` to `direct-entry-auth/1.4` at the W03E implementation time; the W01A v1.3 compatibility fixture remains green. R3 also adds `entry_restore: "all"` to the `REQUIRED_SCOPE_KIND` map in `src/lib/auth/direct-entry-v2.ts:193` (the map row joins the existing `entry_admin: "all"` row). The two R2 "open decisions" are therefore no longer open at R3; the policy is locked.

**W03E resource scope (R4 lock).** P3.1 only locks the `entry_restore` need. **Other restore surfaces (`submission`, `change_request`, `document`, `leader`) are out of P3.1 and out of W03E.** R4 does not introduce a `restore_kind` enumeration; the W03E RPC is a single `direct_entry_restore_entry(p_auth_subject, p_actor_app_user_id, p_entry_id, p_expected_entry_version integer, p_reason text, p_idempotency_key text)` that restores a soft-deleted Direct Entry entry only. **There is no `p_target_app_user_id` parameter** — the entry is the only target, so the RPC never names or touches a target app user.

**W03E restore surface (R3 lock).** The W03E RPC only operates on a **single Direct Entry row** that satisfies all of: (a) the row's `deleted_at IS NOT NULL` (the row is currently soft-deleted), (b) the row's parent submission is still `DRAFT` (a non-DRAFT submission rejects with `42501 'entry is not in a restorable submission state'`), (c) the row is a `direct_entry` row and not a submission / change-request / document / leader row (any non-`direct_entry` row rejects with `P0002 'target not found / unavailable by contract'`). The RPC sets `deleted_at = NULL` and bumps the entry's `version + 1`; the entry's `expected_entry_version` is compared before the write and a mismatch returns `40001`. The mutation does **not** rollback the latest `direct_entry_revisions.after_snapshot`; the latest revision is preserved as a historical record. The mutation does **not** overwrite worker / payment / document / employment fields, does **not** restore submission / change-request / document / leader, and does **not** mutate capability / scope / link / leader rows of the affected app user. The mutation does **not** lock capability / scope / link / leader rows of the affected entry; the only locks are the actor's app-user row and the target entry row (the actor authority recheck is the only recheck, on actor scope / capability rows per §C.2.1).

**W03E appends:** one `direct_entry_revisions` row (`action = 'restore'`, `before_snapshot = the soft-deleted state with deleted_at non-null`, `after_snapshot = the same state with deleted_at = NULL and version = version + 1`); one `direct_entry_audit_events` row (`app_user_id = actor`, `resource_ref = <target entry reference>`, `capability = 'entry_restore'`, `action = 'entry_restore'`, `revision_id = <new revision>`); one `direct_entry_rpc_idempotency` row.

**W03E does not:** revert a W01D leader revoke, revert a W03A disable, revert a W03B capability / scope revoke, or revert a W03C link revoke — it never writes to those tables, so no such postcondition exists and **R4 deletes the R3 `55000` row, the §F matrix row and the mutation-check that described it**. The latest `after_snapshot` may be the soft-deleted state, but the W03E RPC does not use it as a `before_snapshot` for restore; the `before_snapshot` is the row's pre-restore state (with `deleted_at IS NOT NULL`) and the `after_snapshot` is the post-restore state (`deleted_at IS NULL`, `version = version + 1`, all other fields unchanged).

**W03E closed scope.** Submission, change-request, document and leader restore are explicitly out of P3.1 and explicitly out of W03E. The scope-kind addition (`entry_restore: "all"`) and the contract-bump (`direct-entry-auth/1.4`) are locked at R3.

### C.6 Combined session-revocation regression (W03F / J01)

**Contract (R4 lock).** W03F is the lane that asserts the W08A invariants hold after W03A–E. The W08A closure memo and `src/lib/auth/p3-w08a-session-revocation-cache.test.mjs` already cover: no in-memory actor cache, concurrent resolves of the same actor cannot return mixed stale/fresh state, cookie refresh does not skip the live check, and the actor resolver is service-role-only. W03F adds: a mutation that disables an app user while a parallel resolve is in flight must make the second resolve see `enabled = false`; a mutation that revokes a capability (normal close **or** audited marker close) while a parallel resolve is in flight must make the second resolve not see the capability; a mutation that revokes a verified link (normal close **or** audited marker close) while a parallel resolve is in flight must make the second resolve not see the link; the `getDirectEntryActor` call site returns the same denial for the disabled/revoked actor as it would for an actor that was disabled/revoked before the page request started.

W03F does not introduce a parallel session framework; it adds regression cases to the W08A lane. J01 is the readiness audit that signs off W03A–F together.

### G.0 Error taxonomy (R4 lock)

The error taxonomy is locked at R4 and applies uniformly to every W03 RPC. Raw DB messages never reach the UI or the log; the API layer sanitizes them.

| DB SQLSTATE | DB meaning | API HTTP | API body | Where it is raised |
|---|---|---|---|---|
| `22023` | invalid parameter / format / range | `400` | `{ "code": "bad_input", "field": "<p_...>" }` | Missing / empty `reason`, missing `idempotency_key`, missing `expected_app_user_version`, `valid_from > today + 30` ceiling, unknown `capability` token, unknown `scope_kind`, `team_id` set when `scope_kind != 'team'`, `team_id` not set when `scope_kind = 'team'`, `__system_vendor__` `team_id`, W03E entry not soft-deleted / submission not DRAFT / target not a `direct_entry` row. **Not** for same-day or scheduled-future revokes — those are audited marker closes, not `22023`. |
| `40001` | serialization failure (OCC `expected_app_user_version` / `expected_entry_version` mismatch) | `409` | `{ "code": "version_conflict" }` | every W03A / B / C mutation (target `expected_app_user_version` mismatch); W03E (target `expected_entry_version` mismatch). |

| `P0002` | target not found / unavailable by contract | `404` | `{ "code": "target_unavailable" }` | target `app_user_id` / `entry_id` / `recruiter_id` does not exist, soft-deleted entry not in `DRAFT`, target is submission / change-request / document / leader row when W03E was called. |
| `55000` | postcondition failure (internal invariant violated) | `500` | `{ "code": "internal" }` | reserved for internal invariants the RPC must re-check after a write (e.g. assert the new revision's `version = target.version + 1` after the bump; the W03 RPCs do not currently rely on `55000` and should not introduce new uses; R4 deletes the `55000 'restore would re-introduce a revoked security state'` check). |

Rules:

- Data conflicts (`40001`, `23505`, `23P01`) are **never** mapped to `42501`; the policy layer (the helper `direct_entry_assert_actor_app_user_admin`) runs **before** the data layer and would not raise `42501` on a data conflict. The W03 RPCs catch the data-layer SQLSTATE in the data layer and re-raise it as a sanitized API code.
- `42501` is reserved for authorization / policy denial. The helper raises `42501` with a short stable reason code (`'actor is not a Full Admin'`, `'actor is not enabled'`, `'actor scope is not all'`, `'target app user is not enabled'`, `'team_manager_assign is owned by the leader lifecycle RPC'`, `'team scope mutation is owned by the leader lifecycle RPC'`, `'target app user already has a verified link'`, `'app user is not in a restorable submission state'`, etc.). The short codes are part of the contract surface; the long text is not.
- `P0002` is reserved for "target not found / unavailable by contract". The API returns `404` with a stable code; the body never leaks the target UUID.
- The API never returns a raw DB message in the response body or in the structured log. The structured log records `{ rpc, p_action, p_actor_app_user_id, sqlstate, short_code }`; the log does not record the reason text, the `auth_subject`, the email, or any other PII.
- The W03 RPCs use a single `direct_entry_security_failure(p_short_code text, p_detail jsonb)` helper for the policy / policy-mapping errors. The helper raises the right SQLSTATE (`42501` for policy, `P0002` for unavailable target, `22023` for bad input) and returns the short code in the `detail` jsonb. The API layer maps the SQLSTATE to the HTTP code and the short code to the response body's `code` field.

## I. Risks, blockers and the P3.2 boundary

### I.1 Risks (R1-confirmed; carries forward the prior survey's risk list, updated for #71)

1. **No app-user OCC today.** `direct_entry_app_users` has no `version`, no `updated_at`, no per-account revision, no per-account audit. Concurrent status, grant and link work cannot safely share a stale client snapshot until W03A lands. **W03A schema delta is the minimum required.**
2. **Bootstrap is privileged operational code, not lifecycle API.** `scripts/p3-first-owner-bootstrap.mjs` and `scripts/p2-5-accounting-project-admin-provision.mjs` are operator scripts, not runtime lifecycle endpoints. The W01A lane notes the bootstrap is "not lifecycle API"; W03A–E will not turn these scripts into a general lifecycle path. Their post-bootstrap restriction is a separate, explicitly-reviewed decision; W03 does not assume one.
3. **Legacy Accounting grant.** The provisioning script still grants `entry_admin@all` to support existing project operations. W03 must deny its use for security administration without breaking catalog / project behavior; the Accounting transition (grant `catalog_master_manage@all`, verify, revoke legacy `entry_admin@all`) belongs to the controlled W02 transition, not to W03.
4. **W05A seed is not lifecycle.** It derives scope from `personnel_position`, hard-codes seven leaders and grants no `team_manager_assign`. It ran as a one-time seed. W01D has **revoked its `EXECUTE` from every role**; the W01D self-check asserts the revoke; W03A–E will not rerun the seed. W03D's audit-projection lane must assert the seed is revoked.
5. **Audit RPC is too broad for a browser contract.** Existing `direct_entry_read_audit` returns a raw row set that includes `auth_subject` and other internal references. W03D's `direct_entry_read_security_audit` is the bounded, mode-aware replacement; the raw RPC remains a service-role internal helper.
6. **Marker support is asymmetric; W03C must close the link gap (R4).** Membership markers were introduced by #70 for cancellation; capability / scope markers were widened by #71 (W01D section 1, lines 31–66); **the link interval is still strict** (`CHECK (valid_to is null or valid_to > valid_from)`, foundation `:62`) with no marker trigger installed on `direct_entry_app_user_recruiter_links`. R4 resolves this: W03C carries the minimal delta (widen the link CHECK to `valid_to >= valid_from`, install the **existing** `direct_entry_team_leader_marker()` function as `direct_entry_link_marker_guard`) so audited cancellation works uniformly; no new trigger function, no second framework. The W03B / W03C cancel path enables the shared marker mechanism only around its own audited close; raw zero-length DML elsewhere stays `23514`. R4 also retires the R3 `22023 'same-day cancellation is open'` rejection: same-day and scheduled-future cancels are now supported audited marker closes (§C.2 revoke semantics).
7. **Link cardinality is fully constrained today (FIX 2 correction).** The foundation `direct_entry_recruiter_link_no_overlap` trigger at `20261002170000:555–556`, calling `direct_entry_guard_effective_interval()` at `:516–528`, acquires the advisory lock `recruiter-link:<app_user_id>` and, when `new.verified = true`, asserts no overlap on every other verified row of the same `app_user_id` with `23P01` on conflict. **R1 was wrong** to claim the schema permits multiple verified effective links per app user; the trigger is the cardinality guard. W03C does **not** add a per-`(app_user_id)` partial verified-effective unique index — partial unique indexes cannot be conditioned on the current date, and the trigger already enforces the cardinality. The W01D designate write additionally requires `count(*) = 1 verified effective link` as defense-in-depth at runtime (`42501`, #71:1217). W03C adds lifecycle RPCs, audit, reason, OCC and idempotency, and reuses the existing trigger and the existing per-`(app_user_id, recruiter_id, valid_from)` unique key.
8. **PII / account identification remains bounded.** The exact account-list fields needed to let an Admin identify an existing login are not locked here. The W03 design will not expose `auth.users.email`; the smallest Owner-approved identifier (e.g., the app user `display_name` + `app_user_id`) is the only identification surface, and the W03D audit projection strips `auth_subject`.
9. **No migration numbers or Production facts are assigned here.** Migration-slot boundary is "W03A uses the next available migration number at the time of implementation; W03B–E do not reserve fixed numbers". Row counts, actual Accounting holders, `entry_restore` holders, mapping anomalies and audit integrity are unknown until the W03F / J01 preflight runs.
