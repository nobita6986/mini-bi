### A.5 Lock/atomicity pattern that W03 must reuse

W01D's atomic mutation RPC (`direct_entry_apply_team_leader_mutation`, #71:1075–1640) is the canonical lock-order template for any mutation that touches a leader aggregate. The exact order, with line numbers, is:

1. **Team aggregate row** — `select t.* into v_team from public.teams t where t.team_id = p_team_id for update` (#71:1081). **W03 mutations never lock the team aggregate row** (R6 FIX F): W03A writes no team / leader row, W03B writes no team / leader row, and W03C writes no team / leader row. Even when the W03C link-revoke leader-bundle precheck (FIX 5) finds a current / scheduled leader, the W03C RPC does not enter the W01D pipeline; it does not take the team row lock, and it does not cascade into `direct_entry_team_leader_assignments`. Serialisation against a concurrent W01D leader mutation is provided by the shared `direct_entry_app_users` row lock (step 4) — both the W03C and the W01D pipeline lock the same `direct_entry_app_users` row in UUID order, so only one of the two can hold the lock at a time. W03C's precheck (FIX 5) is the only mechanism that decides whether the mutation is allowed; if the link is a current / scheduled leader basis, the W03C raises `42501 'security mutation is owned by leader lifecycle RPC'` and the Admin must cancel / replace the leader via W01D first.
2. **Idempotency lookup** — read-only `select` on `direct_entry_rpc_idempotency` (#71:1102); no lock.
3. **Idempotency payload hash + version check** — `v_team.version <> p_expected_version` raises `40001 'team version conflict'` (#71:1119). W03 mutations compare OCC on the relevant aggregate. **W03A / W03B / W03C all compare on the target `direct_entry_app_users.version`** (R3 / R4 lock — the app-user aggregate is the OCC root for every W03A / B / C mutation). W03E compares on the target entry's `version` instead.
4. **App-user row lock** — `perform u.app_user_id from public.direct_entry_app_users u where u.app_user_id = any(v_actor_ids) order by u.app_user_id for update` (#71:1170–1173). W03 mutations must lock the affected app users in the same `order by u.app_user_id` (a stable UUID order). W03A locks the **distinct** actor + target app-user rows in UUID order (one row when `actor = target`); W03B / W03C lock the same way. **W03A takes no child-row lock and no advisory lock** (R6 FIX E): the only W03A row lock is this `direct_entry_app_users` lock on the distinct actor + target set, the post-lock actor-authority recheck is taken under that lock, and W03A has no overlap-trigger race to serialise because it writes no child row.
5. **Scope grant row locks** — `perform s.grant_id from public.direct_entry_scope_grants s where s.app_user_id = any(v_actor_ids) and s.scope_kind = 'team' order by s.app_user_id, s.grant_id for update` (#71:1181–1185). W03B scope mutation locks the same way. The leader path filters on `scope_kind = 'team'`; a W03B scope mutation on `own` or `all` must use the matching filter.
6. **Capability grant row locks** — `perform g.grant_id from public.direct_entry_capability_grants g where g.app_user_id = any(v_actor_ids) and g.capability = 'team_manager_assign' order by g.app_user_id, g.grant_id for update` (#71:1186–1190). W03B capability mutation locks the same way. **W03A does not lock any child row** (R6 FIX E: the §A.5 step 4 lock on the distinct actor + target `direct_entry_app_users` rows is the only W03A row lock; W03A writes no child row, so it has no child-row lock to take, and it has no overlap-trigger race to serialise via the canonical advisory keys).
7. **Advisory locks, in lexical `order by key`** — `for v_lock_key in select distinct key from unnest(array['capability:…','scope:…','recruiter-link:…']) as keys(key) where key is not null order by key loop perform pg_advisory_xact_lock(hashtextextended(v_lock_key, 0));` (#71:1191–1210). W03 mutations use the same keys for the same tables and the same `order by key` lexical order. The `recruiter-link:<app_user_id>` key is the same one the foundation `direct_entry_guard_effective_interval` trigger uses at `:517`; locking it ahead of any link write serialises against any concurrent link writer.
8. **Link row lock (link path only) — by immutable id (R5 FIX 2; R6 FIX B + FIX D).** `direct_entry_revoke_verified_link` locks the target's `direct_entry_app_user_recruiter_links` row by `p_link_id` (R5 replaces the by-`app_user_id` lookup with the by-`grant_id` / `link_id` lookup so a scheduled / historical row is never re-closed by accident and the lookup is unambiguous). The shape is `select l.* from public.direct_entry_app_user_recruiter_links l where l.link_id = p_link_id for update`. The RPC then asserts `l.app_user_id = p_target_app_user_id` and `l.verified = true` and **the date-aware leader-basis predicate** (R6 FIX A: `a.valid_from <= current_date and (a.valid_to is null or current_date < a.valid_to)` — see step "Leader-bundle precheck" below). **Closed / marker row** (l row is found, owned by the target, kind matches, but the row's `valid_to` already equals its `valid_from` or is non-null and `<= current_date`) raises `23514 'row is already closed'` with the stable short code `state_conflict` (R6 FIX B: state conflict, not policy denial; the row exists, the id is well-formed, the target owns it, the kind is correct, the row is just in a terminal state). **Id missing / wrong owner** (no row at all, or `l.app_user_id <> p_target_app_user_id`) raises `P0002 'target_unavailable'` (R6 FIX B: the row genuinely does not exist, or the requested resource type is wrong). **Revoke signatures are minimum-precise** (R6 FIX D): `direct_entry_revoke_capability`, `direct_entry_revoke_scope` and `direct_entry_revoke_verified_link` take only the immutable id (`p_grant_id` / `p_link_id`); the capability / scope_kind / team_id / recruiter_id is read from the locked row, never compared against a redundant param. W01D's own leader-apply helper still uses the by-`app_user_id` order-by-`link_id` lookup at #71:1213–1216 because the leader mutation has a different contract (it picks the live verified link to attach the leader to); W03C's mutation does not.
9. **Recruiter row lock (link path only)** — `select r.active into v_recruiter_active from public.recruiters r where r.recruiter_id = v_recruiter_id for update` (#71:1228–1230). W03C link lifecycle locks the same way.
10. **Advisory locks for provider / team-membership** — `for v_lock_key in select key from unnest(array['provider:<recruiter_id>','team-membership:<recruiter_id>']) as keys(key) order by key loop perform pg_advisory_xact_lock(hashtextextended(v_lock_key, 0));` (#71:1234–1240). W03C link lifecycle does not need to lock the provider / team-membership keys for verified-link creation (it has no provider / team-membership write), but if a future W03C variant needs to read a provider / team-membership row, it must use the same keys in the same lexical order.
11. **Provider membership row lock and team membership row lock (link path only)** — `perform m.membership_id from public.recruiter_provider_memberships m where m.recruiter_id = v_recruiter_id order by m.membership_id for update` (#71:1242–1246), then the team-membership equivalent. W03C does not lock these for verified-link creation.

**R1 correction 2 (mandatory after #71) — W03 grant/scope/link mutations must reuse the same lock order and advisory keys, not introduce a parallel helper with a different order.** A W03 mutation that locks the scope row before the capability row, or that skips the advisory lock on `recruiter-link:<app_user_id>`, or that locks a different set of rows, can deadlock with a concurrent W01D leader designate / revoke RPC. ### A.6 The leader-owned authority bundle

The atomic leader bundle is a tuple of three rows written in one transaction by the W01D `direct_entry_apply_team_leader_mutation` RPC:

1. `direct_entry_team_leader_assignments` row keyed by `team_id` (and the partial-open `team_open_uidx`).
2. `direct_entry_scope_grants` row: `app_user_id = leader, scope_kind = 'team', team_id = <team>`, coextensive on `(valid_from, valid_to)` with the assignment row.
3. `direct_entry_capability_grants` row: `app_user_id = leader, capability = 'team_manager_assign', valid_from = <valid_from>`, coextensive on `(valid_from, valid_to)` with the assignment row.

The bundle's invariants, all enforced by the W01D postcondition block at #71:1418–1490, are:

- Exactly one current leader per team (`v_post_team_assignment_count = 1`).
- Exactly one current team-scope row for the current leader in the team (`v_post_target_team_scope_count = 1`).
- Exactly one current `team_manager_assign` row for the current leader (`v_post_capability_count = 1`).
- The assignment's `(valid_from, valid_to)` is `IS NOT DISTINCT FROM` the scope's and capability's `(valid_from, valid_to)` (coextensivity). The postcondition queries assert `s.valid_from = a.valid_from and s.valid_to is not distinct from a.valid_to` (and the same for capability), so a leader-bundle row whose dates drift from the assignment row fails `55000`.
- Replace closes the outgoing bundle atomically (one `team_leader_assignment` close + one `team_manager_assign` close + one `team` scope close) and opens the incoming bundle in the same transaction; the W01D `55000 'team leader mutation postcondition failed'` postcondition is the only safety net if any of the three rows is mis-shaped.
- Revoke closes the bundle atomically (one close on each of the three rows) and creates a zero-length marker on each interval to record the closure; the transaction-local `direct_entry.team_leader_marker` GUC is on for the duration of the close write.

**R1 correction 3 (mandatory after #71) — leader bundle cannot be partially mutated by a generic W03 grant/scope/link RPC.** A W03 grant/scope/link mutation that:

- Inserts a `team_manager_assign` capability outside the W01D designate RPC, or
- Inserts/updates a `team` scope row whose `(valid_from, valid_to)` does not match an existing leader assignment row, or
- Closes only the capability row (or only the scope row) of an existing leader bundle,

must fail closed. The marker trigger's transaction-local flag is the W01D mechanism; W03 generic mutations must not set that flag. The legacy W05A seed `direct_entry_seed_team_scope_grants()` exists and is verified by the W01D self-check to still be present, but it has been **revoked from every role** (`public, anon, authenticated, service_role`) at #71:1969–1970 and is not a runtime grant path. The W03 design must treat the leader bundle as owned by the W01D RPCs; W03 generic mutations may grant/revoke other capabilities (`recruiter_master_manage`, `audit_view`, `entry_restore`, `pii_view`, `pii_export`, etc.) and other scopes (`own`, `all`) but must not touch the leader bundle except through the W01D RPC.

### C.1 App-user aggregate (W03A — required schema delta)

**Contract.** `direct_entry_app_users` must carry enough state for concurrent account-status changes to use optimistic concurrency control and to be auditable. **The W03A mutation touches only the `direct_entry_app_users` row, the new `direct_entry_app_user_revisions` row, the `direct_entry_restricted_reasons` row, the `direct_entry_rpc_idempotency` row and the `direct_entry_audit_events` row. The "what happens to a leader who is disabled mid-assignment" question is a **product decision** that W03A does not make; a permanent deprovision that closes the leader bundle is a separate, larger RPC and is **out of W03A scope**.

Forced RLS, no privilege to any role, internal `SECURITY DEFINER` writer.

### C.2 Capability and scope interval mutations (W03B)

**Contract (R4 lock).** Capability and scope intervals are effective-dated, audited, reason-stamped, OCC-locked and idempotency-keyed. They are written by RPCs that follow the W01D lock order (see §A.5). The capability CHECK and scope CHECK are widened to `valid_to >= valid_from` by #71 §1; raw zero-length marker DML outside an audited RPC is still rejected with `23514` by `direct_entry_team_leader_marker()`. The partial marker-excluding unique index `direct_entry_capability_grants_open_start_uidx` rejects a duplicate open start with `23505`; the overlap trigger `direct_entry_capability_grant_no_overlap` rejects a non-duplicate open overlap with `23P01`. A unique index is **not** an exclusion constraint; `23P01` is reserved for the overlap trigger. **Cancellation (R5 three-branch contract).** Every W03B / W03C revoke RPC takes an immutable interval id (`p_grant_id` / `p_link_id`, see R5 FIX 2) and applies exactly one of three branches against the row's `valid_from`. (a) **`effective_date < interval.valid_from`** is an **invalid backdate** — the RPC raises `22023 'effective_date is before valid_from'` and rolls back with zero residue. Backdate is **never** a marker; the row is byte-untouched and no audit is written. (b) **`effective_date = interval.valid_from`** is a **same-day cancellation** — the RPC closes the row as an audited zero-length inert marker (`valid_to = valid_from`) inside the same Full Admin + OCC + reason + revision + audit + idempotency transaction; the marker is inert on every date, kept, never re-dated. (c) **`effective_date > interval.valid_from`** is a **normal close** — `valid_to = effective_date`. The live path remains `valid_to IS NULL OR valid_to > valid_from`, so a `valid_to = valid_from` marker never counts as effective. **Scheduled cancellation** is the cancel-before-start case (`interval.valid_from > today`): the caller identifies the scheduled row by its immutable id and applies branch (b) with the same envelope. The W03B / W03C revoke RPC sets the marker GUC only around its own audited close (the existing `direct_entry_team_leader_marker()` trigger function is reused — one shared marker mechanism, no second framework, no per-W03 GUC fork). The W03B / W03C revoke RPC **refuses** to enable the GUC for a row that is the basis of a current or scheduled leader assignment (see R5 FIX 5 in §C.3) — the marker is only set for the row itself. Revoke never hard-deletes: history is the closed/marker interval row plus the app-user aggregate revision plus the audit event. W03B / W03C never `INSERT` a fresh row on revoke; the only write is `UPDATE valid_to` on the existing child row, **without** any child `updated_at` column write (no child table has `updated_at`; see R5 FIX 3). The W01D leader bundle stays W01D-owned: W03B still rejects `team_manager_assign` and leader-bundle `team` scope mutations with `42501 'security mutation is owned by the leader lifecycle RPC'`, and the W03 cancellation path never updates a leader-bundle row.

**Capability and scope are separate RPCs.** A W03B capability mutation RPC does not take `scope_kind` / `team_id`; a W03B scope mutation RPC does. The two surfaces do not share an RPC and never co-write a row in the same transaction.

**Signatures (R4 lock).** Every W03A / W03B / W03C mutation RPC takes `(p_auth_subject, p_actor_app_user_id, p_target_app_user_id, …)`. The actor identity is server-session-derived; the client business payload cannot override the actor (`p_actor_app_user_id` is resolved by the helper from `p_auth_subject` and is rejected if it disagrees with the session). The Full Admin triple + effective `all` scope is checked against the **actor**, not the target. The target is the app user whose state is being changed. If `p_actor_app_user_id = p_target_app_user_id`, the distinct set of rows to lock has one member and the row is locked **once**, not twice (§C.2.1 step 2).

**Revoke semantics (R5 lock).** Revoke is an **update** of the existing live interval row, identified by its immutable id (`p_grant_id` / `p_link_id` — R5 FIX 2). Revoke **does not insert** a new capability / scope / link row. Revoke **does not** re-issue the same capability / scope / link at `effective_date`. Revoke never hard-deletes. Revoke never writes `valid_from` and never writes a child `updated_at` column (no child table has `updated_at`; the only `updated_at` write is on the OCC aggregate root `direct_entry_app_users` per R5 FIX 3). The branch applied to the row is determined by `p_effective_date` against the locked row's `valid_from` (R5 FIX 1 three-branch rule). History is the closed/marker interval row plus the target app-user aggregate revision (envelope §C.1) plus the audit event. Exact behavior, SQLSTATE, OCC, idempotency, revision/audit and tests are locked per case:

- **current** (`p_effective_date > valid_from`, interval already effective): normal close; bump target `version + 1`; one revision + one audit (`app_user_revision_id`) + one idempotency; replay with same key returns the stored result without bumping twice.
- **same-day** (`p_effective_date = valid_from`): marker close (`valid_to = valid_from`); same authority + OCC + reason + revision + audit + idempotency as current; the marker row is inert on every date including the cancellation date itself; never re-dated.
- **scheduled-future** (`valid_from > today`, grant cancelled before it ever becomes effective): marker close (`valid_to = valid_from`); identical audited envelope to same-day; the interval never becomes effective at any date.
- **replay** (same `p_idempotency_key`, same request hash): returns the original result byte-identically; no second version bump, no second revision, no second audit row. A reused key with a different hash raises the idempotency conflict (`23505` → `409 duplicate`).
- Stale `expected_app_user_version` → `40001` with zero residue; missing/empty reason or idempotency key → `22023` with zero residue; non-Full-Admin actor after lock → `42501` with zero residue; raw marker DML outside the audited RPC → `23514`.

If the same target needs a new live interval after a revoke, the caller must issue a separate `grant_*` / `create_*` RPC; that RPC is a new write, not a continuation of the revoke.

**Same-day / scheduled / future cancellation (R5 three-branch lock).** The W03B / W03C revoke RPCs accept any `effective_date` and never return `22023 'same-day cancellation is open'`. The three-branch rule (R5 FIX 1) is: `effective_date < row.valid_from` → `22023 'effective_date is before valid_from'`, zero residue, no marker, no audit, no row write; `effective_date = row.valid_from` → audited zero-length inert marker (`valid_to = valid_from`), inside the same Full Admin + OCC + reason + revision + audit + idempotency transaction; `effective_date > row.valid_from` → normal close (`valid_to = effective_date`). The marker reuses the shared `direct_entry_team_leader_marker()` trigger-function pattern — one inert-marker mechanism, one vocabulary: the marker row is `valid_to = valid_from`, inert on every date including the cancellation date itself, kept, and never re-dated. Raw marker DML outside the audited RPC is rejected with `23514`. No per-W03 GUC fork: the W03 revoke enables the shared marker path only around its own audited close, and only for rows that are not the basis of a current / scheduled leader assignment (R5 FIX 5). The link table (widened by the W03C migration to `CHECK valid_to >= valid_from` and equipped with the shared `direct_entry_team_leader_marker()` trigger) supports all three branches.

### C.2.1 Lock-then-recheck actor authority (R5, applies to every W03A / W03B / W03C mutation)

The R2 claim that "a parallel disable / revoke between the lock and the helper cannot happen because the helper itself is the first write step after the lock" is rejected. A parallel session can change the actor's effective authority between the moment the helper begins and the moment the helper commits. R4 therefore locks the actor and target first, then re-evaluates actor authority under lock, then validates, then writes. The order is canonical and applies uniformly to `direct_entry_enable_app_user`, `direct_entry_disable_app_user`, `direct_entry_grant_capability`, `direct_entry_revoke_capability`, `direct_entry_grant_scope`, `direct_entry_revoke_scope`, `direct_entry_create_verified_link`, `direct_entry_revoke_verified_link` (W03C reuses the same §A.5 lock order without the team-aggregate step, plus the link advisory lock), and `direct_entry_restore_entry` (W03E reuses the same order with the actor-authority recheck on the actor's own security rows, never on the target entry).

1. **Resolve actor mapping.** The RPC body resolves the actor from `p_auth_subject` (server session) and `p_actor_app_user_id` (param). If the param disagrees with the session-derived mapping, the RPC raises `42501 'actor identity is not derived from the session'` and rolls back. The client business payload cannot override the actor.
2. **Lock app-user rows in UUID order.** The RPC takes `for update` on the **distinct** `direct_entry_app_users` rows of actor and target (`select … where u.app_user_id = any(v_actor_ids) order by u.app_user_id for update`). If `actor = target`, the distinct set has one member and the row is locked **once** — this holds for every W03A/B/C RPC, including W03A; there is no "single target row" phrasing and no second lock. **W03A locks the same distinct set** (R6 FIX E): W03A locks the actor + target `direct_entry_app_users` rows in UUID order, takes no child-row lock (no capability / scope / link / assignment row), and takes no advisory lock. The W03A OCC + post-lock actor-authority recheck is sufficient for W03A's only invariant.
3. **Lock actor scope rows before actor capability rows.** Per W01D #71 step order, the actor's `direct_entry_scope_grants` rows are locked before the actor's `direct_entry_capability_grants` rows. The W03B scope RPC also locks the target's existing scope rows of the same `(scope_kind, team_id)`.
4. **Lock target child rows (R5 by-id; R6 FIX D).** W03B capability RPC locks the target's `direct_entry_capability_grants` row by `p_grant_id` (`select … where grant_id = p_grant_id for update`) and asserts `app_user_id = p_target_app_user_id` (R6 FIX D: the row's `capability` is read from the locked row and is used to identify a leader-bundle row, not compared against a redundant `p_capability` param; a kind mismatch is impossible because the caller named the row by id, not by kind). The closed / marker check is **the date-aware row-state predicate** (R6 FIX B): a row whose `valid_to = valid_from` (zero-length inert marker) or whose `valid_to <= current_date` (closed historical) is a terminal row and is rejected with `23514 'row is already closed'` (`state_conflict`). A row whose `valid_to is null` or `current_date < valid_to` (current or scheduled) is the only row the W03B revoke accepts; the W03B revoke applies the three-branch rule (FIX 1) to that row's `valid_from`. W03B scope RPC locks the target's `direct_entry_scope_grants` row by `p_grant_id` and asserts `app_user_id = p_target_app_user_id` (the row's `scope_kind` and `team_id` are read from the locked row, never compared against redundant `p_scope_kind` / `p_team_id` params per FIX D); the same date-aware row-state predicate applies. W03C link RPC locks the target's `direct_entry_app_user_recruiter_links` row by `p_link_id` and asserts `app_user_id = p_target_app_user_id` (the row's `verified = true` and `recruiter_id` are read from the locked row, never compared against a redundant `p_recruiter_id` param per FIX D); the same date-aware row-state predicate applies. W03A locks **no** child rows (steps 3–4 and 5 do not apply to W03A — see §C.1 for why).
5. **Take canonical advisory locks in lexical order.** W03B takes the same advisory keys W01D uses for the same tables, in lexical `order by key`; W03C takes `recruiter-link:<app_user_id>` ahead of any link write. W03A takes none. The W01D leader-bundle advisory locks are not taken by W03 because W03 does not write leader-bundle rows.
6. **Recheck actor authority under lock.** After the applicable row locks and advisory locks are held, the helper `direct_entry_assert_actor_app_user_admin` re-reads the actor's `enabled` flag, re-evaluates the Full Admin triple (`entry_admin` AND `recruiter_master_manage` AND `team_master_manage`), and re-evaluates the actor's effective scopes (must include `all`). The helper returns the exercised authority only if all three are satisfied. A parallel disable / revoke / scope change that lands after the lock is caught here: the re-read sees the new value and the helper raises `42501 'actor is not a Full Admin'`. The RPC rolls back.
7. **Validate and mutate target.** Only after the actor authority has been re-evaluated under lock does the RPC validate the target's `expected_app_user_version`, the locked child row's invariants (immutable id matches, ownership matches, kind matches, row is not closed — R5 FIX 2), and the three-branch cancellation rule (R5 FIX 1: backdate → `22023`, same-day → audited marker, normal close → `valid_to = p_effective_date`). **For the `grant_*` / `create_*` path, the RPC also validates the target's `enabled = true` (R5 FIX 4 — grant into a disabled account is `42501 'target app user is not enabled'`). For the `revoke_*` / close-only path, the target's `enabled` flag is **not** required** — a Full Admin can close the intervals of a disabled account. The mutation runs to completion with the target's app-user `version` bumped by exactly one, the corresponding app-user revision appended, the reason / audit / idempotency rows written, and the transaction committing. A replay (same `p_idempotency_key`) returns the original result without bumping version twice. **No child table has `updated_at`** (R5 FIX 3); only the OCC aggregate root `direct_entry_app_users` is bumped.

If any step fails, the entire transaction rolls back with zero residue (no partial revision, no partial audit, no partial idempotency). The actor authority recheck is a hard requirement, not an optional optimization.

### C.3 Verified link lifecycle (W03C)

**Contract (R5 lock).** On `main` at `1189c8a` the link table is strict half-open (`CHECK (valid_to is null or valid_to > valid_from)`, foundation `:62`), so it cannot hold an audited same-day cancellation until W03C widens it. The cardinality guard for verified links is the existing foundation trigger `direct_entry_recruiter_link_no_overlap` at foundation `:555–556`, calling `direct_entry_guard_effective_interval()` at `:516–528`, which acquires the advisory lock `recruiter-link:<app_user_id>` and asserts no overlap on every other verified row of the same `app_user_id` with `23P01` on conflict. **W03C does not add a partial unique index for "verified effective today"** — partial unique indexes cannot be conditioned on the current date; the trigger is the cardinality guard. The W01D designate write additionally requires `count(*) = 1 verified effective link` as defense-in-depth at runtime (`42501`, #71:1217). W03C adds lifecycle RPCs, audit, reason, OCC and idempotency, and reuses the existing trigger and the existing per-`(app_user_id, recruiter_id, valid_from)` unique key (foundation `:71`). The overlap trigger raises `23P01`; the unique key raises `23505` if a duplicate `(app_user_id, recruiter_id, valid_from)` is inserted. A unique key is **not** an exclusion constraint; `23P01` is reserved for the overlap trigger. **Per R5 FIX 7 the W03C RPC re-raises the data-layer SQLSTATE (`23P01` or `23505`) and does not translate it to `42501`; the API layer maps the SQLSTATE to the sanitized `409` `overlap` / `duplicate` body.**

**W03C minimal schema delta (required, R5).** To support audited cancellation on links (FIX 1) with the smallest possible change and no second marker framework, the W03C migration performs exactly three append-only DDL steps and nothing else on this table:

1. `alter table public.direct_entry_app_user_recruiter_links drop constraint <link_interval_check>;` and `add constraint <link_interval_check> check (valid_to is null or valid_to >= valid_from)` — the same widening #71 §1 applied to capability and scope.
2. `create trigger direct_entry_link_marker_guard before insert or update of valid_from, valid_to on public.direct_entry_app_user_recruiter_links for each row execute function public.direct_entry_team_leader_marker();` — reuses the **existing** W01D trigger function (same `SECURITY DEFINER`, same `23514`, same GUC guard); no new function, no new GUC, no forked semantics.
3. The `valid_to = valid_from` marker row must stay out of the verified-cardinality path. The existing `direct_entry_recruiter_link_no_overlap` trigger already uses `daterange(l.valid_from, l.valid_to, '[)')`, which is empty for a zero-length interval, so a marker never overlaps and never counts as a verified effective link; no extra partial index is needed on this table (W03C still adds none).

Every other aspect of the link table — columns, the per-`(app_user_id, recruiter_id, valid_from)` unique key, the no-overlap trigger, forced RLS, revoked grants — is byte-stable across W03. The W03C self-check asserts the widened CHECK, the installed marker trigger, and that no `delete`/`hard delete` path exists. Raw zero-length DML from any non-audited path remains rejected with `23514`.

If such a row exists, the RPC raises `42501 'security mutation is owned by leader lifecycle RPC'` and rolls back. **Historical** (closed before today) leader assignments do not block the revoke: the persisted `a.leader_recruiter_id` survives the link change, and the historical leader row is read by the persisted FK (W01D A2 server contract R4–R5), not by joining the live link table. **R6 FIX F**: the W03C revoke does **not** lock the team aggregate row; it does not enter the W01D pipeline. Serialisation against a concurrent W01D leader mutation is provided by the shared `direct_entry_app_users` row lock (actor + target) — both the W03C and the W01D pipeline lock the same `direct_entry_app_users` row in UUID order, so only one of the two can hold the lock at a time. Applies the three-branch rule (FIX 1) on the locked link row's `valid_from`: `p_effective_date < row.valid_from` → `22023 'effective_date is before valid_from'`, zero residue; `p_effective_date = row.valid_from` → audited marker (`valid_to = valid_from`), GUC enabled only for this write and only for this row (FIX 5 refuses to enable the GUC on a row that is the basis of a current / scheduled leader assignment, so this branch can only fire when the link is not a leader-bundle basis); `p_effective_date > row.valid_from` → normal close (`valid_to = p_effective_date`). The UPDATE is `set valid_to = …` only — **no `updated_at` write** (no child `updated_at` column exists; R5 FIX 3). **Does not insert** a new link row, **does not** hard-delete, **does not** re-issue the link, **does not** mutate `valid_from` or the business key. Bumps the target's `version + 1` and `updated_at = now()`. Appends one target app-user revision (`action = 'link_revoke'`, envelope `{target_app_user_id, changed: {recruiter_id, valid_from}, interval: {valid_from, valid_to}, actor_app_user_id}`), one reason, one audit event (audit `app_user_id = actor`, `resource_ref = <target aggregate reference>`, `capability = 'entry_admin'`, `action = 'link_revoke'`, `app_user_revision_id = <new revision>`), one idempotency record.

**W03C atomicity (R5; R6 FIX F).** Follows §A.5 steps 2 (idempotency), 4 (distinct actor + target app-user rows in UUID order — this is the only W03C row lock that needs to serialise against a concurrent W01D leader mutation, since W03C and W01D both lock the same `direct_entry_app_users` row), 7 (advisory lock `recruiter-link:<app_user_id>`), 8 (link row by `p_link_id` in `link_id` order, when revoking — R5 FIX 2 replaces the by-business-key lookup with the by-id lookup), 9 (recruiter row, when revoking), then the post-lock actor-authority recheck (§C.2.1 step 6). **W03C does not lock the team aggregate row** (R6 FIX F): the W03C revoke is not the W01D pipeline, and the W03C precheck (FIX 5) is the only mechanism that decides whether the mutation is allowed. For `direct_entry_revoke_verified_link`, after step 8 the RPC performs the R5 FIX 5 leader-bundle precheck with the R6 FIX A date-aware predicate (`select 1 from public.direct_entry_team_leader_assignments a where a.leader_app_user_id = p_target_app_user_id and a.leader_recruiter_id = l.recruiter_id and a.valid_from <= current_date and (a.valid_to is null or current_date < a.valid_to)`); if it returns a row, the RPC raises `42501 'security mutation is owned by leader lifecycle RPC'`. W03C does **not** take the W01D capability / scope advisory locks because W03C does not write capability / scope rows. W03C enables the shared marker path only around its own audited close and only for the locked link row (FIX 5 forbids enabling the GUC for a leader-bundle basis row); it never writes a leader-bundle row, never writes a capability / scope row, and never writes a child-table `updated_at` (R5 FIX 3 — no such column on the link table).

### C.4 Bounded audit projection by mode (W03D)

**Contract.** `direct_entry_read_audit(...)` is too broad for a browser W03 contract (it returns the raw row including `auth_subject`, reason references, revision FKs and changed_fields). W03D adds a new service-role RPC `direct_entry_read_security_audit(auth_subject, app_user_id, mode, page, page_size)` where `mode ∈ {'full','catalog','own_manager'}`. The RPC returns a JSONB list of bounded event rows, exactly the fields the W03 UI needs:

- `event_id` (uuid), `created_at` (timestamptz), `action` (text), `capability` (text or null), `scope_kind` (text or null), `scope_team_id` (uuid or null), `outcome` (text), `changed_fields` (text[]), `team_id_or_resource_ref` (text, the bounded opaque reference — never the actor's `auth_subject`).
- The mode `full` is Admin-only (`entry_admin + recruiter_master_manage + team_master_manage` triple + effective `all`) and returns the full bounded set.
- The mode `catalog` is `catalog_master_manage@all` and is filtered by an **explicit exact `action` allowlist** (R4), not by `capability`. The allowlist covers catalog and worker events only and **excludes** every security action regardless of the audit `capability` field: the full Security slice (`enable`, `disable`, `capability_grant`, `capability_revoke`, `scope_grant`, `scope_revoke`, `link_create`, `link_revoke`, `entry_restore`) is excluded by action. The filter is `audit.action = ANY(<allowlist>)`; it never uses `LIKE` or `*` wildcards; it never uses `audit.capability` as the primary classifier. The catalog mode also strips the `auth_subject`, the actor `app_user_id` (other than the caller), the reason text, and any PII before the projection is returned.
- The mode `own_manager` (R4 lock) is a `team_manager_assign@team` actor whose projection may **only** surface the manager-assignment events the team leader is entitled to see. The correct allowlist is exactly `('project_manager_assignment_assign','project_manager_assignment_unassign')` — the W02 lifecycle audit verbs — plus the W02 scheduled-cancel action **only if W02 actually writes one** (at `1189c8a` no such action exists in the W02 source; a future scheduled-cancel verb joins this allowlist only after its writer lands and by Owner/T0 decision — it is never inferred). The `own_manager` projection filters `action = ANY(<that allowlist>) AND scope_team_id = caller.effective_team_id`, where `scope_team_id` is the `app_user_id`'s effective team. **W02 writers must record `scope_kind = 'team'` and `scope_team_id = <leader team>` whenever the exercised authority is `team_manager_assign@team`; the `all` authority path (W02 `entry_admin@all` assigns) keeps `scope_kind = 'all'`.** The allowlist never contains `team_leader_designate`/`team_leader_replace`/`team_leader_revoke` (those are the W01D team-leader bundle, not a manager assignment). Cross-team `own_manager` reads are rejected with `42501`. Full Admin `full` and Accounting `catalog` modes are unchanged.

**Forbidden in the bounded projection (W03D RPC).** `auth_subject`, `app_user_id` (other than the caller's), `reason_id`, raw reason text, credential/token, storage key, raw DB error, any PII (email, phone, name, CCCD), any UUID that would identify a real person outside the W03 audit policy.

**W03D also adds** a new `direct_entry_read_security_audit_self_check()` (internal) that the W03D migration self-check runs to assert: every returned column is in the allowlist; no `auth_subject` is serialised; the SQLSTATE 42501 fires for any non-Full-Admin caller asking for `mode = 'full'`; the SQLSTATE 42501 fires for any non-`catalog_master_manage@all` caller asking for `mode = 'catalog'`; the SQLSTATE 42501 fires for any non-`team_manager_assign@team` actor asking for `mode = 'own_manager'` and not owning the team id.

**W03D does not** add a "fetch all then hide client-side" path. The bounded set is enforced server-side at the SQL level. The page is request-time and never cached.

### C.5 Admin-only `entry_restore` (W03E) — locked scope, locked policy, locked contract bump (R5)

**Contract (R5 lock).** T0 has decided that `entry_restore` requires the actor to hold effective `all` scope. The `entry_restore` capability alone is **not** sufficient. The W03E RPC therefore requires (a) the `entry_restore` capability on the actor, (b) the Full Admin triple on the actor, (c) effective `all` scope on the actor, (d) a non-empty `reason`, (e) the target's `expected_entry_version`, and (f) a unique `idempotency_key`. The `direct-entry-auth` contract version bumps from `direct-entry-auth/1.3` to `direct-entry-auth/1.4` at the W03E implementation time; the W01A v1.3 compatibility fixture remains green. R3 adds `entry_restore: "all"` to the `REQUIRED_SCOPE_KIND` map in `src/lib/auth/direct-entry-v2.ts:193` (the map row joins the existing `entry_admin: "all"` row). R5 keeps the policy lock; R5 FIX 6 unifies the error taxonomy (see §G.0).

**W03E resource scope (R4 lock).** P3.1 only locks the `entry_restore` need. **Other restore surfaces (`submission`, `change_request`, `document`, `leader`) are out of P3.1 and out of W03E.** R4 does not introduce a `restore_kind` enumeration; the W03E RPC is a single `direct_entry_restore_entry(p_auth_subject, p_actor_app_user_id, p_entry_id, p_expected_entry_version integer, p_reason text, p_idempotency_key text)` that restores a soft-deleted Direct Entry entry only. **There is no `p_target_app_user_id` parameter** — the entry is the only target, so the RPC never names or touches a target app user.

**W03E restore surface (R5 lock).** The W03E RPC only operates on a **single Direct Entry row** that satisfies all of: (a) the row's `deleted_at IS NOT NULL` (the row is currently soft-deleted — if not, the RPC raises `23514 state_conflict`, R5 FIX 6), (b) the row's parent submission is still `DRAFT` (a non-DRAFT submission raises `23514 state_conflict`, R5 FIX 6), (c) the row is a `direct_entry` row and not a submission / change-request / document / leader row (any non-`direct_entry` row raises `P0002 'target not found / unavailable by contract'` — wrong resource type, not state conflict, per R5 FIX 6). The RPC sets `deleted_at = NULL` and bumps the entry's `version + 1`; the entry's `expected_entry_version` is compared before the write and a mismatch returns `40001 version_conflict`. The mutation does **not** rollback the latest `direct_entry_revisions.after_snapshot`; the latest revision is preserved as a historical record. The mutation does **not** overwrite worker / payment / document / employment fields, does **not** restore submission / change-request / document / leader, and does **not** mutate capability / scope / link / leader rows of the affected app user. The mutation does **not** lock capability / scope / link / leader rows of the affected entry; the only locks are the actor's app-user row and the target entry row (the actor authority recheck is the only recheck, on actor scope / capability rows per §C.2.1). The W03E RPC does **not** raise `42501 'app user is not in a restorable submission state'` (R4 wording, removed in R5) and does **not** raise `P0002 'soft-deleted entry not in DRAFT'` (R4 wording, removed in R5).

**W03E appends:** one `direct_entry_revisions` row (`action = 'restore'`, `before_snapshot = the soft-deleted state with deleted_at non-null`, `after_snapshot = the same state with deleted_at = NULL and version = version + 1`); one `direct_entry_audit_events` row (`app_user_id = actor`, `resource_ref = <target entry reference>`, `capability = 'entry_restore'`, `action = 'entry_restore'`, `revision_id = <new revision>`); one `direct_entry_rpc_idempotency` row.

**W03E does not:** revert a W01D leader revoke, revert a W03A disable, revert a W03B capability / scope revoke, or revert a W03C link revoke — it never writes to those tables, so no such postcondition exists and **R4 deletes the R3 `55000` row, the §F matrix row and the mutation-check that described it**. The latest `after_snapshot` may be the soft-deleted state, but the W03E RPC does not use it as a `before_snapshot` for restore; the `before_snapshot` is the row's pre-restore state (with `deleted_at IS NOT NULL`) and the `after_snapshot` is the post-restore state (`deleted_at IS NULL`, `version = version + 1`, all other fields unchanged).

**W03E closed scope.** Submission, change-request, document and leader restore are explicitly out of P3.1 and explicitly out of W03E. The scope-kind addition (`entry_restore: "all"`) and the contract-bump (`direct-entry-auth/1.4`) are locked at R3.

### C.6 Combined session-revocation regression (W03F / J01)

**Contract (R5 lock).** W03F is the lane that asserts the W08A invariants hold after W03A–E. The W08A closure memo and `src/lib/auth/p3-w08a-session-revocation-cache.test.mjs` already cover: no in-memory actor cache, concurrent resolves of the same actor cannot return mixed stale/fresh state, cookie refresh does not skip the live check, and the actor resolver is service-role-only. W03F adds: a mutation that disables an app user while a parallel resolve is in flight must make the second resolve see `enabled = false`; a mutation that revokes a capability (normal close **or** audited marker close) while a parallel resolve is in flight must make the second resolve not see the capability; a mutation that revokes a verified link (normal close **or** audited marker close, on an **enabled** or **disabled** target per R5 FIX 4) while a parallel resolve is in flight must make the second resolve not see the link; the `getDirectEntryActor` call site returns the same denial for the disabled/revoked actor as it would for an actor that was disabled/revoked before the page request started.

W03F does not introduce a parallel session framework; it adds regression cases to the W08A lane. J01 is the readiness audit that signs off W03A–F together.

Rules:

- **R5 FIX 7 (data conflicts are not policy denial).** Data conflicts (`40001`, `23505`, `23P01`) are **never** mapped to `42501`. The W03 RPCs catch the data-layer SQLSTATE in the data layer and **re-raise it as the same SQLSTATE**; the API layer maps the SQLSTATE to the sanitized `409` body. `42501` is reserved for actor / authority / owned-by-leader-lifecycle policy denial. F-matrix rows that previously re-raised `23505` / `23P01` to `42501 'capability grant conflict'` / `42501 'verified link conflict'` / `42501 'app user already has a verified link'` are corrected in R5 to keep the data-conflict SQLSTATE.
- `42501` is reserved for authorization / policy denial. The helper raises `42501` with a short stable reason code (`'actor is not a Full Admin'`, `'actor is not enabled'`, `'actor scope is not all'`, `'target_app_user_not_enabled'` for grant / create into a disabled target, `'team_manager_assign is owned by the leader lifecycle RPC'`, `'team scope mutation is owned by the leader lifecycle RPC'`, `'security mutation is owned by leader lifecycle RPC'` for the W03C link-revoke leader-bundle case, etc.). The short codes are part of the contract surface; the long text is not. **R6 FIX B**: `'row_already_closed'` is **not** a `42501` short code — closed / marker row is `23514 state_conflict` (HTTP 409), and the W03B / W03C revoke RPCs raise `23514 'row is already closed'` with that stable short code, never `42501`.
- **R5 FIX 6 (state_conflict).** W03E `entry_restore` raises `23514` with the stable short code `state_conflict` when the row exists but the state forbids the restore; the API returns `409 state_conflict`. W03E never returns `42501 'app user is not in a restorable submission state'` for the "submission not DRAFT" case (R4 wording, deleted in R5) and never returns `P0002 'soft-deleted entry not in DRAFT'` for it (R4 wording, deleted in R5). Missing reason / expected_entry_version / idempotency_key is `22023 bad_input`; stale `expected_entry_version` is `40001 version_conflict`.
- **R6 FIX A (date-aware leader-history predicate).** A leader assignment `a` is a current / scheduled basis of a W03C link revoke iff `a.valid_from <= current_date and (a.valid_to is null or current_date < a.valid_to)` — i.e., the assignment is open on today's date. Historical (closed before today, `valid_to <= current_date` with `valid_to > valid_from`) and pure-marker (any date, `valid_to = valid_from`) leader rows are not a basis; the W03C revoke precheck skips them and the revoke is allowed. The earlier R5 predicate `(a.valid_to is null or a.valid_to > a.valid_from)` is removed (R6 FIX A: it matched every closed historical row and turned every historical leader into a "basis" of the current link, which would block revoke of any current link that ever backed any leader in the past).
- **R6 FIX B (closed / marker row is state conflict, not policy denial).** A W03B / W03C revoke that finds a row by immutable id and the row's `valid_to` already equals its `valid_from` (zero-length inert marker) or is non-null and `<= current_date` (closed historical) raises `23514 'row is already closed'` with the stable short code `state_conflict` (HTTP 409). The id-missing / wrong-owner case (no row at all, or `row.app_user_id <> p_target_app_user_id`) raises `P0002 'target_unavailable'` (HTTP 404). `42501` is **never** used for closed / marker row; `42501` is strictly for actor / authority / owned-by-leader-lifecycle policy denial.
- **R6 FIX C (concurrency expectations are OCC-first, data-conflicts-second).** Two parallel W03A / W03B / W03C mutations of the same target are serialised by the target's `direct_entry_app_users` row lock. The OCC loser (same `expected_app_user_version`, different actual version on the loser) sees `40001 'app user version conflict'` (HTTP 409 `version_conflict`); the data-layer `23505` / `23P01` SQLSTATEs are not reachable for the same-target case. `23505` and `23P01` are reserved for **pre-existing** data conflicts in a single transaction: a same-`valid_from` insert into the partial marker-excluding unique index raises `23505`; a different-`valid_from` insert whose `daterange` overlaps an existing open row raises `23P01` from the overlap trigger. Tests must use seed data that triggers the SQLSTATE the row claims to test (a `40001` test must have the same `expected_app_user_version` for both sessions and a different actual version on the loser; a `23505` test must seed a same-`valid_from` open row; a `23P01` test must seed a different-`valid_from` overlapping open row).
- **R6 FIX D (revoke signatures are minimum-precise).** `direct_entry_revoke_capability`, `direct_entry_revoke_scope`, and `direct_entry_revoke_verified_link` take only the immutable id (`p_grant_id` / `p_link_id`); the `capability` / `scope_kind` / `team_id` / `recruiter_id` / `verified = true` is read from the locked row, never compared against a redundant param. A kind mismatch is impossible because the caller named the row by id, not by kind. The §A.5 step 8 footnote, the §C.2 / §C.3 RPC bodies, and the F-matrix revoke row are aligned with this contract.
- **R6 FIX E (W03A locks distinct actor + target app-user rows only).** Every W03A RPC locks the **distinct** actor and target `direct_entry_app_users` rows in UUID order (one row when `actor = target`), takes no child-row lock, and takes no advisory lock. The §A.5 step 4 / step 6 wording, the §C.1 W03A atomicity, the §C.2.1 step 2 / step 4, and the §E W03A self-check are aligned with this contract. The previous R5 sentence "W03A locks every open capability row of the app user" is removed (R6 FIX E: it contradicted the no-child-row requirement, and the row lock on the distinct actor + target set is sufficient for W03A's only invariant).
- **R6 FIX F (W03C does not lock the team).** W03C `direct_entry_revoke_verified_link` does **not** lock the team aggregate row. Serialisation against a concurrent W01D leader mutation is provided by the shared `direct_entry_app_users` row lock (actor + target) — both the W03C and the W01D pipeline lock the same `direct_entry_app_users` row in UUID order, so only one of the two can hold the lock at a time. The W03C precheck (FIX 5; R6 FIX A date-aware predicate) is the only mechanism that decides whether the mutation is allowed; if the link is a current / scheduled leader basis, the W03C raises `42501 'security mutation is owned by leader lifecycle RPC'` and the Admin must cancel / replace the leader via W01D first. The §A.5 step 1 footnote, the §C.3 atomicity, the F-matrix leader-bundle row, and the §G mutation-check plan are aligned with this contract.
- `P0002` is reserved for "target not found / unavailable by contract" — the row genuinely does not exist, or the requested resource type is wrong (e.g. W03E called on a submission / change-request / document / leader row). The API returns `404` with a stable code; the body never leaks the target UUID.
- The API never returns a raw DB message in the response body or in the structured log. The structured log records `{ rpc, p_action, p_actor_app_user_id, sqlstate, short_code }`; the log does not record the reason text, the `auth_subject`, the email, or any other PII.
- The W03 RPCs use a single `direct_entry_security_failure(p_short_code text, p_detail jsonb)` helper for the policy / policy-mapping errors. The helper raises the right SQLSTATE (`42501` for policy, `P0002` for unavailable target, `22023` for bad input, `23514` with `state_conflict` for W03E state conflicts) and returns the short code in the `detail` jsonb. The API layer maps the SQLSTATE to the HTTP code and the short code to the response body's `code` field.

## I. Risks, blockers and the P3.2 boundary

### I.1 Risks (R1-confirmed; carries forward the prior survey's risk list, updated for #71 and R5)

1. **No app-user OCC today.** `direct_entry_app_users` has no `version`, no `updated_at`, no per-account revision, no per-account audit. Concurrent status, grant and link work cannot safely share a stale client snapshot until W03A lands. **W03A schema delta is the minimum required.**
2. **Bootstrap is privileged operational code, not lifecycle API.** `scripts/p3-first-owner-bootstrap.mjs` and `scripts/p2-5-accounting-project-admin-provision.mjs` are operator scripts, not runtime lifecycle endpoints. The W01A lane notes the bootstrap is "not lifecycle API"; W03A–E will not turn these scripts into a general lifecycle path. Their post-bootstrap restriction is a separate, explicitly-reviewed decision; W03 does not assume one.
3. **Legacy Accounting grant.** The provisioning script still grants `entry_admin@all` to support existing project operations. W03 must deny its use for security administration without breaking catalog / project behavior; the Accounting transition (grant `catalog_master_manage@all`, verify, revoke legacy `entry_admin@all`) belongs to the controlled W02 transition, not to W03.
4. **W05A seed is not lifecycle.** It derives scope from `personnel_position`, hard-codes seven leaders and grants no `team_manager_assign`. It ran as a one-time seed. W01D has **revoked its `EXECUTE` from every role**; the W01D self-check asserts the revoke; W03A–E will not rerun the seed. W03D's audit-projection lane must assert the seed is revoked.
5. **Audit RPC is too broad for a browser contract.** Existing `direct_entry_read_audit` returns a raw row set that includes `auth_subject` and other internal references. W03D's `direct_entry_read_security_audit` is the bounded, mode-aware replacement; the raw RPC remains a service-role internal helper.
6. **Marker support is asymmetric; W03C closes the link gap; R5 narrows the same-day backdate to its own error code.** Membership markers were introduced by #70 for cancellation; capability / scope markers were widened by #71 (W01D section 1, lines 31–66); the link interval is widened by W03C and equipped with the shared `direct_entry_team_leader_marker()` trigger function. R5 narrows the cancellation contract further: `effective_date < valid_from` is a `22023 'effective_date is before valid_from'` rejection (never a marker), `effective_date = valid_from` is the audited zero-length inert marker, `effective_date > valid_from` is the normal close. R5 also locks the W03C link revoke contract: the revoke identifies the row by its immutable `p_link_id`, asserts the row belongs to the target and is `verified = true` and not closed, asserts no current / scheduled `direct_entry_team_leader_assignments` row keys on `(p_target_app_user_id, p_recruiter_id)` (otherwise `42501 'security mutation is owned by leader lifecycle RPC'`), and only then applies the three-branch rule. **R6 narrows the closed / marker row taxonomy further**: a revoke on a closed / marker row raises `23514 'row is already closed'` with the stable short code `state_conflict` (HTTP 409), **not** `42501` (R6 FIX B — `42501` is strictly for actor / authority / owned-by-leader-lifecycle policy denial). The id-missing / wrong-owner case is `P0002 'target_unavailable'` (HTTP 404). **R6 also tightens the leader-history predicate**: a leader assignment `a` is a current / scheduled basis of the W03C link revoke iff `a.valid_from <= current_date and (a.valid_to is null or current_date < a.valid_to)` (R6 FIX A — historical closed and pure-marker leader rows are not a basis, only an assignment that is open on today's date blocks the link revoke). The W03B / W03C cancel path enables the shared marker mechanism only around its own audited close and only for the row being closed (R5 FIX 5 forbids enabling the GUC for a leader-bundle basis row); raw zero-length DML elsewhere stays `23514`.
7. **Link cardinality is fully constrained today (FIX 2 correction).** The foundation `direct_entry_recruiter_link_no_overlap` trigger at `20261002170000:555–556`, calling `direct_entry_guard_effective_interval()` at `:516–528`, acquires the advisory lock `recruiter-link:<app_user_id>` and, when `new.verified = true`, asserts no overlap on every other verified row of the same `app_user_id` with `23P01` on conflict. **R1 was wrong** to claim the schema permits multiple verified effective links per app user; the trigger is the cardinality guard. W03C does **not** add a per-`(app_user_id)` partial verified-effective unique index — partial unique indexes cannot be conditioned on the current date, and the trigger already enforces the cardinality. The W01D designate write additionally requires `count(*) = 1 verified effective link` as defense-in-depth at runtime (`42501`, #71:1217). W03C adds lifecycle RPCs, audit, reason, OCC and idempotency, and reuses the existing trigger and the existing per-`(app_user_id, recruiter_id, valid_from)` unique key.
8. **PII / account identification remains bounded.** The exact account-list fields needed to let an Admin identify an existing login are not locked here. The W03 design will not expose `auth.users.email`; the smallest Owner-approved identifier (e.g., the app user `display_name` + `app_user_id`) is the only identification surface, and the W03D audit projection strips `auth_subject`.
9. **No migration numbers or Production facts are assigned here.** Migration-slot boundary is "W03A uses the next available migration number at the time of implementation; W03B–E do not reserve fixed numbers". Row counts, actual Accounting holders, `entry_restore` holders, mapping anomalies and audit integrity are unknown until the W03F / J01 preflight runs.

**Locked in R6** (superseding the R5 items named below): (1) the date-aware leader-history predicate — a leader assignment `a` is a current / scheduled basis of the W03C link revoke iff `a.valid_from <= current_date and (a.valid_to is null or current_date < a.valid_to)`;
