### A.5 Lock/atomicity pattern that W03 must reuse

W01D's atomic mutation RPC (`direct_entry_apply_team_leader_mutation`, #71:1075–1640) is the canonical lock-order template for any mutation that touches a leader aggregate. The exact order, with line numbers, is:

1. **Team aggregate row** — `select t.* into v_team from public.teams t where t.team_id = p_team_id for update` (#71:1081). W03 mutations that do not touch a team aggregate do not lock this row.
2. **Idempotency lookup** — read-only `select` on `direct_entry_rpc_idempotency` (#71:1102); no lock.
3. **Idempotency payload hash + version check** — `v_team.version <> p_expected_version` raises `40001 'team version conflict'` (#71:1119). W03 mutations compare OCC on the relevant aggregate (app-user `version` for W03A; no aggregate version is required for W03B/C because the partial unique indexes and overlap triggers are the OCC).
4. **App-user row lock** — `perform u.app_user_id from public.direct_entry_app_users u where u.app_user_id = any(v_actor_ids) order by u.app_user_id for update` (#71:1170–1173). W03 mutations must lock the affected app users in the same `order by u.app_user_id` (a stable UUID order). W03A locks exactly one app user (the one being enabled / disabled); W03B / W03C lock the affected app user.
5. **Scope grant row locks** — `perform s.grant_id from public.direct_entry_scope_grants s where s.app_user_id = any(v_actor_ids) and s.scope_kind = 'team' order by s.app_user_id, s.grant_id for update` (#71:1181–1185). W03B scope mutation locks the same way. The leader path filters on `scope_kind = 'team'`; a W03B scope mutation on `own` or `all` must use the matching filter.
6. **Capability grant row locks** — `perform g.grant_id from public.direct_entry_capability_grants g where g.app_user_id = any(v_actor_ids) and g.capability = 'team_manager_assign' order by g.app_user_id, g.grant_id for update` (#71:1186–1190). W03B capability mutation locks the same way; W03A locks every open capability row of the app user (the W03A RPC does not filter on capability, it locks all rows of the app user in `(app_user_id, grant_id)` order).
7. **Advisory locks, in lexical `order by key`** — `for v_lock_key in select distinct key from unnest(array['capability:…','scope:…','recruiter-link:…']) as keys(key) where key is not null order by key loop perform pg_advisory_xact_lock(hashtextextended(v_lock_key, 0));` (#71:1191–1210). W03 mutations use the same keys for the same tables and the same `order by key` lexical order. The `recruiter-link:<app_user_id>` key is the same one the foundation `direct_entry_guard_effective_interval` trigger uses at `:517`; locking it ahead of any link write serialises against any concurrent link writer.
8. **Link row lock (link path only)** — `perform l.link_id from public.direct_entry_app_user_recruiter_links l where l.app_user_id = p_target_leader_app_user_id order by l.link_id for update` (#71:1213–1216). W03C link lifecycle locks the same way.
9. **Recruiter row lock (link path only)** — `select r.active into v_recruiter_active from public.recruiters r where r.recruiter_id = v_recruiter_id for update` (#71:1228–1230). W03C link lifecycle locks the same way.
10. **Advisory locks for provider / team-membership** — `for v_lock_key in select key from unnest(array['provider:<recruiter_id>','team-membership:<recruiter_id>']) as keys(key) order by key loop perform pg_advisory_xact_lock(hashtextextended(v_lock_key, 0));` (#71:1234–1240). W03C link lifecycle does not need to lock the provider / team-membership keys for verified-link creation (it has no provider / team-membership write), but if a future W03C variant needs to read a provider / team-membership row, it must use the same keys in the same lexical order.
11. **Provider membership row lock and team membership row lock (link path only)** — `perform m.membership_id from public.recruiter_provider_memberships m where m.recruiter_id = v_recruiter_id order by m.membership_id for update` (#71:1242–1246), then the team-membership equivalent. W03C does not lock these for verified-link creation.

**R1 correction 2 (mandatory after #71) — W03 grant/scope/link mutations must reuse the same lock order and advisory keys, not introduce a parallel helper with a different order.** A W03 mutation that locks the scope row before the capability row, or that skips the advisory lock on `recruiter-link:<app_user_id>`, or that locks a different set of rows, can deadlock with a concurrent W01D leader designate / revoke RPC. The shared order is the only correctness guarantee; the tests must observe no deadlock in the tested paths within a bounded timeout. R2 does **not** claim the W03 mutations make deadlocks "impossible" or that waits are strictly "FIFO" — both claims are unprovable from the source. The contract is: deterministic shared order, bounded-time concurrency regression, no deadlock in the tested paths.

**Authority on the link side.** The advisory key `recruiter-link:<app_user_id>` is the same one the foundation overlap trigger acquires (foundation `:517`). A W03C link write that takes the same advisory lock ahead of its `insert` / `update` serialises against any concurrent `direct_entry_guard_effective_interval` trigger execution and against any other W03C / W01D link writer; a W03C link write that **does not** take the advisory lock races the trigger and may produce a `23P01` it should have prevented.

**R1 correction 3 (mandatory after #71) — the marker GUC `direct_entry.team_leader_marker` is exclusively owned by the W01D leader lifecycle.** On `main` at `1189c8a`, the only callsite of `set_config('direct_entry.team_leader_marker', 'on', true)` is the W01D leader apply helper at #71:1384. W03A, W03B and W03C do **not** call `set_config('direct_entry.team_leader_marker', 'on', true)` and do **not** set any sibling flag. W03A does not cascade the disable into capability / scope / link closure (see §C.1); W03B same-day cancellation of a non-leader capability / scope remains an **open** decision (see §C.2); W03C link lifecycle does not write zero-length markers on the link table — the link CHECK is still strict (`valid_to > valid_from`) on `main` and a W03C link closure writes a fresh row with the new `valid_to` rather than a marker. R2 removes every R1 mention of W03A setting the GUC and every R1 mention of a W03B / W03C same-day marker path; the open decisions are stated explicitly in §C.1 and §C.2.

### A.6 The leader-owned authority bundle

The atomic leader bundle is a tuple of three rows written in one transaction by the W01D `direct_entry_apply_team_leader_mutation` RPC:

1. `direct_entry_team_leader_assignments` row keyed by `team_id` (and the partial-open `team_open_uidx`).
2. `direct_entry_scope_grants` row: `app_user_id = leader, scope_kind = 'team', team_id = <team>`, coextensive on `(valid_from, valid_to)` with the assignment row.
3. `direct_entry_capability_grants` row: `app_user_id = leader, capability = 'team_manager_assign', valid_from = <valid_from>`, coextensive on `(valid_from, valid_to)` with the assignment row.

The bundle's invariants, all enforced by the W01D postcondition block at #71:1418–1490, are:

- Exactly one current leader per team (`v_post_team_assignment_count = 1`).
- Exactly one current team-scope row for the current leader in the team (`v_post_target_team_scope_count = 1`).
- Exactly one current `team_manager_assign` row for the current leader (`v_post_capability_count = 1`).
- The assignment's `(valid_from, valid_to)` is `IS NOT DISTINCT FROM` the scope's and capability's `(valid_from, valid_to)` (coextensivity). The postcondition queries assert `s.valid_from = a.valid_from and s.valid_to is not distinct from a.valid_to` (and the same for capability), so a leader-bundle row whose dates drift from the assignment row fails `55000`.
- Replace closes the outgoing bundle atomically (one `team_leader_assignment` close + one `team_manager_assign` close + one `team` scope close) and opens the incoming bundle in the same transaction; the W01D `55000 'team leader mutation postcondition failed'` postcondition is the only safety net if any of the three rows is mis-shaped.
- Revoke closes the bundle atomically (one close on each of the three rows) and creates a zero-length marker on each interval to record the closure; the transaction-local `direct_entry.team_leader_marker` GUC is on for the duration of the close write.

**R1 correction 3 (mandatory after #71) — leader bundle cannot be partially mutated by a generic W03 grant/scope/link RPC.** A W03 grant/scope/link mutation that:

- Inserts a `team_manager_assign` capability outside the W01D designate RPC, or
- Inserts/updates a `team` scope row whose `(valid_from, valid_to)` does not match an existing leader assignment row, or
- Closes only the capability row (or only the scope row) of an existing leader bundle,

must fail closed. The marker trigger's transaction-local flag is the W01D mechanism; W03 generic mutations must not set that flag. The legacy W05A seed `direct_entry_seed_team_scope_grants()` exists and is verified by the W01D self-check to still be present, but it has been **revoked from every role** (`public, anon, authenticated, service_role`) at #71:1969–1970 and is not a runtime grant path. The W03 design must treat the leader bundle as owned by the W01D RPCs; W03 generic mutations may grant/revoke other capabilities (`recruiter_master_manage`, `audit_view`, `entry_restore`, `pii_view`, `pii_export`, etc.) and other scopes (`own`, `all`) but must not touch the leader bundle except through the W01D RPC.

## C. Locked mutation contracts

Every W03 mutation RPC must satisfy every row below, **simultaneously**. The W03 lanes in §F assert each row for each W03 slice.

### C.1 App-user aggregate (W03A — required schema delta)

**Contract.** `direct_entry_app_users` must carry enough state for concurrent account-status changes to use optimistic concurrency control and to be auditable. **The W03A mutation touches only the `direct_entry_app_users` row, the new `direct_entry_app_user_revisions` row, the `direct_entry_restricted_reasons` row, the `direct_entry_rpc_idempotency` row and the `direct_entry_audit_events` row. W03A does not mutate any capability grant, scope grant, verified link or leader assignment row.** When a user is disabled, the open capability / scope / link / leader rows remain in the database unchanged; the disabled state is enforced by the next actor resolution (W08A `direct_entry_resolve_actor_context` already returns `enabled = false` and the W03A lane must assert the same fail-closed path). When the user is re-enabled, the open intervals are effective again without re-write. The "what happens to a leader who is disabled mid-assignment" question is a **product decision** that W03A does not make; a permanent deprovision that closes the leader bundle is a separate, larger RPC and is **out of W03A scope**.

Minimum schema delta (the W03A migration must add, append-only, and the W03A self-check must assert):

- `version integer not null default 1 check (version >= 1)` — same shape as `recruiters.version` and `teams.version`. Every enable/disable RPC reads, compares, increments and writes `version` in a single transaction.
- `updated_at timestamptz not null default now()` — bumped on every status change.
- A new `direct_entry_app_user_revisions` table mirroring `direct_entry_team_leader_revisions`: `(revision_id uuid pk, app_user_id uuid fk, version integer, actor_user_id uuid, action text check in ('create','enable','disable'), before_snapshot jsonb, after_snapshot jsonb, reason_id uuid fk, created_at timestamptz default now(), check (version >= 1), unique(app_user_id, version))`. Forced RLS, no privilege to any role, internal `SECURITY DEFINER` writer.
- One reason + one audit event per `version` increment. The audit event is the W01D `direct_entry_audit_events` row: `action in ('app_user_enable','app_user_disable')`, `capability = 'entry_admin'` (the audit records the authority the Full Admin triple has exercised, not a non-existent token), `outcome = 'APPLIED'`, `changed_fields = array['enabled']`, `revision_id = <new revision>`. **W03A does not add a new capability token.** The audit `capability` column already accepts the existing 23-token vocabulary (`direct_entry_audit_events.capability` is free-form text constrained to `length(action) between 1 and 96` and the 23-token CHECK on `direct_entry_capability_grants.capability` does not apply to audit rows); W03A writes `'entry_admin'` to record the Full Admin authority that gated the mutation. If Owner/T0 later decide to introduce a new token (e.g., to make the audit `capability` semantic instead of authority-derived), that is a separate capability-vocabulary delta to be reviewed against the W01A 23-token contract, not a W03A scope expansion.

**W03A mutation RPCs (service-role-only, `search_path = pg_catalog, public`, EXECUTE to `service_role` only):**

- `direct_entry_enable_app_user(auth_subject, app_user_id, expected_version, reason text, idempotency_key text)` — asserts the Full Admin triple is currently effective at the caller's auth_subject (see §C.2 for the helper); asserts `app_user_id.enabled = false`, `expected_version = current`; writes `enabled = true`, `version = current + 1`, `updated_at = now()`; appends one revision; writes one reason; writes one audit event; writes one idempotency record. Returns `{app_user_id, version, revision_id, change = 'enable'}`.
- `direct_entry_disable_app_user(auth_subject, app_user_id, expected_version, reason text, idempotency_key text)` — symmetric. Writes the same row set with `enabled = false`. **Does not cascade to capability, scope, link or leader rows.** The disabled state is enforced by the next actor resolution (W08A) and by every W03 / W01D RPC that reads `enabled`. The `disabled` actor is rejected at the next request even if capability / scope / link intervals are still live.

**W03A atomicity / authority.** Lock order follows §A.5 with the team-aggregate step omitted (W03A does not touch a team): (a) `for update` on the single `direct_entry_app_users` row, (b) the read-only idempotency lookup, (c) the OCC `version` compare (raises `40001 'app user version conflict'` on mismatch), (d) the W03A `direct_entry_assert_app_user_admin(auth_subject)` helper enforces the full Admin triple + effective `all` scope (returns the authority `entry_admin` only after the triple is satisfied — never when a token is missing). W03A does **not** set `set_config('direct_entry.team_leader_marker', 'on', true)`. W03A does **not** take the W01D advisory lock set; it takes only the app-user row lock and the read-only idempotency lookup.

**W03A closed scope.** The W03A migration does **not** add an invitation/initial-password/forced-reset/MFA path; it does not add a `direct_entry_invite` table, a `direct_entry_password_reset` table or a `direct_entry_mfa` table; the `direct_entry_app_users.display_name` change is a separate `change_request` path; the PII / email / phone change is the `change_request` path; the `auth.users` row is owned by Supabase Auth and is out of scope; **cascading deprovision of capability / scope / link / leader rows is out of W03A scope** and is a separate product decision. **P3.2 owns invitations, initial passwords, forced resets, MFA and account recovery.**

### C.2 Capability and scope interval mutations (W03B)

**Contract.** Capability and scope intervals are effective-dated, audited, reason-stamped, OCC-locked and idempotency-keyed. They are written by RPCs that follow the W01D lock order (see §A.5). The capability CHECK and scope CHECK are widened to `valid_to >= valid_from` by #71 §1; raw zero-length marker DML is still rejected with `23514` by `direct_entry_team_leader_marker()` on the three interval tables. The only on-ramp for a zero-length marker is the W01D `set_config('direct_entry.team_leader_marker', 'on', true)` at #71:1384, which W03B does **not** call. W03B writes live intervals only. Same-day cancellation (a W03B revoke with `effective_date = current_valid_from`) is an **open product decision**; the conservative choice is to require `effective_date > valid_from` (i.e., the close write uses a date strictly after the existing start, so the close interval is non-empty). W03B does not pre-empt that decision; the W03B RPC accepts `effective_date > valid_from` and rejects `effective_date <= valid_from` with `22023 'same-day cancellation is open'` until Owner/T0 sign on the policy.

**Capability and scope are separate RPCs.** A W03B capability mutation RPC does not take `scope_kind` / `team_id`; a W03B scope mutation RPC does. The two surfaces do not share an RPC and never co-write a row in the same transaction.

**W03B capability mutation RPCs (service-role-only, `search_path = pg_catalog, public`, EXECUTE to `service_role` only):**

- `direct_entry_grant_capability(auth_subject, app_user_id, capability, valid_from date, reason text, idempotency_key text)` — the Full Admin triple + effective `all` scope is required (see helper below). Asserts the `capability` is in the 23-token vocabulary (the DB CHECK rejects unknown with `23514`). Asserts no overlap on a live interval (the partial unique index `direct_entry_capability_grants_open_start_uidx` rejects a duplicate open start with `23P01`; the overlap trigger rejects a non-duplicate open overlap with `23P01`). Inserts one row, one revision, one reason, one audit event, one idempotency record. **Rejects** the capability `team_manager_assign` with `42501 'security mutation is owned by the leader lifecycle RPC'` regardless of the caller's authority.
- `direct_entry_revoke_capability(auth_subject, app_user_id, capability, effective_date date, reason text, idempotency_key text)` — same authority; reads the current live interval, asserts `effective_date > current.valid_from` (raises `22023 'same-day cancellation is open'` on `effective_date <= current.valid_from`), updates the current row to `valid_to = effective_date`, then writes a fresh row with `valid_from = effective_date` (the new live interval is empty for the closed capability). **Rejects** `capability = 'team_manager_assign'` with `42501`. The W03B revoke never creates a zero-length marker; it creates a non-empty live interval and closes the previous one. The W01D leader apply helper (which writes zero-length markers on the leader bundle's three rows) is the only marker writer.

**W03B scope mutation RPCs (service-role-only, `search_path = pg_catalog, public`, EXECUTE to `service_role` only):**

- `direct_entry_grant_scope(auth_subject, app_user_id, scope_kind check in ('own','team','all'), team_id null when scope_kind <> 'team', valid_from date, reason text, idempotency_key text)` — same Full Admin authority. The W03B scope RPC **rejects** a `team` scope whose `(valid_from, valid_to)` would be the start of a leader bundle: the RPC checks whether a current `team_manager_assign` capability exists for this `app_user_id` at the same `valid_from` (or an open `team_manager_assign` at `valid_from <= today`) and, if so, raises `42501 'team scope mutation is owned by the leader lifecycle RPC'`. The W03B scope RPC also rejects any `team` scope whose `team_id` is the `__system_vendor__` reserved team (the same `23514` the W01D designate write raises at #71:1086).
- `direct_entry_revoke_scope(auth_subject, app_user_id, scope_kind, team_id, effective_date date, reason text, idempotency_key text)` — symmetric; rejects same-day with `22023`; rejects leader-bundle `team` scopes with `42501`; never writes a zero-length marker.

**Authority helper.** A new helper `direct_entry_assert_app_user_admin(auth_subject, app_user_id)` enforces the **Full Admin triple** (`entry_admin` AND `recruiter_master_manage` AND `team_master_manage` at effective `all` scope). The helper returns the exercised authority (`'entry_admin'`) **only after** the triple is satisfied. The helper does **not** return `entry_admin` when a token is missing; in that case it raises `42501 'app user admin triple is incomplete'` and the W03B RPC rolls back. The helper does **not** re-evaluate authority after a `for update` lock is taken (a parallel disable / revoke between the lock and the helper cannot happen because the helper itself is the first write step after the lock).

**W03B explicitly does not write:** a zero-length capability for `team_manager_assign` (the W01D designate/revoke RPC owns the leader bundle); a `team` scope row whose `(valid_from, valid_to)` is not `IS NOT DISTINCT FROM` a live leader assignment row; any row on `direct_entry_app_user_recruiter_links` (W03C owns the link table); the GUC `set_config('direct_entry.team_leader_marker', 'on', true)`; the W01D advisory lock set for the leader bundle (a W03B mutation that does not write a leader-bundle row does not need those locks). A W03B RPC that detects a leader-bundle violation raises `42501 'security mutation is owned by the leader lifecycle RPC'` and rolls back.

### C.3 Verified link lifecycle (W03C)

**Contract.** The link table is strict half-open (`valid_to > valid_from`, per foundation `:62`); **R2 removes the R1 plan to widen the link CHECK and to add a marker trigger on the link table.** The cardinality guard for verified links is the existing foundation trigger `direct_entry_recruiter_link_no_overlap` at foundation `:555–556`, calling `direct_entry_guard_effective_interval()` at `:516–528`, which acquires the advisory lock `recruiter-link:<app_user_id>` and asserts no overlap on every other verified row of the same `app_user_id` with `23P01` on conflict. **W03C does not add a partial unique index for "verified effective today"** — partial unique indexes cannot be conditioned on the current date; the trigger is the cardinality guard. The W01D designate write additionally requires `count(*) = 1 verified effective link` as defense-in-depth at runtime (`42501`, #71:1217). W03C adds lifecycle RPCs, audit, reason, OCC and idempotency, and reuses the existing trigger and the existing per-`(app_user_id, recruiter_id, valid_from)` unique key (foundation `:71`).

**W03C mutation RPCs (service-role-only, `search_path = pg_catalog, public`, EXECUTE to `service_role` only):**

- `direct_entry_create_verified_link(auth_subject, app_user_id, recruiter_id, valid_from date, reason text, idempotency_key text)` — the Full Admin triple + effective `all` scope is required. Asserts the recruiter is active. Asserts the app user is enabled (W03A path: if the user is disabled, the actor resolution has already failed and the RPC will not be called; an explicit `enabled` recheck is included for defense-in-depth and raises `42501 'app user is not enabled'`). Asserts the `app_user_id` does not currently hold a different verified effective link (the foundation trigger raises `23P01`; the RPC catches the trigger error and re-raises `42501 'app user already has a verified link'`). Takes the advisory lock `recruiter-link:<app_user_id>` ahead of the `insert` (§A.5 step 7). Inserts one link row (`verified = true`), one reason, one audit event, one idempotency record.
- `direct_entry_revoke_verified_link(auth_subject, app_user_id, recruiter_id, effective_date date, reason text, idempotency_key text)` — same authority. Asserts the link is currently verified-effective. Updates the current row to `valid_to = effective_date` (the link CHECK is `valid_to > valid_from`, so `effective_date > current.valid_from` is required; the RPC raises `22023 'same-day cancellation is open'` on `effective_date <= current.valid_from` until Owner/T0 sign on the policy). Writes a fresh row with `valid_from = effective_date` (the new interval is empty for the closed link). **W03C does not write a zero-length marker** — the link CHECK is strict and the W03C RPC stays inside the strict half-open contract. The W01D leader-read path is **not** affected because leader-read joins on the persisted `a.leader_recruiter_id` FK, not on the link (per the W01D A2 server contract survey R4–R5).

**W03C atomicity.** Follows §A.5 steps 1 (team — only if the link is being changed for a current leader; W03C does not lock the team for an ordinary create / revoke), 4 (app-user), 7 (advisory lock `recruiter-link:<app_user_id>`), 8 (link row in `link_id` order, when revoking), 9 (recruiter row, when revoking). W03C does **not** take the W01D capability / scope advisory locks because W03C does not write capability / scope rows. W03C does **not** set the `direct_entry.team_leader_marker` GUC.

### C.4 Bounded audit projection by mode (W03D)

**Contract.** `direct_entry_read_audit(...)` is too broad for a browser W03 contract (it returns the raw row including `auth_subject`, reason references, revision FKs and changed_fields). W03D adds a new service-role RPC `direct_entry_read_security_audit(auth_subject, app_user_id, mode, page, page_size)` where `mode ∈ {'full','catalog','own_manager'}`. The RPC returns a JSONB list of bounded event rows, exactly the fields the W03 UI needs:

- `event_id` (uuid), `created_at` (timestamptz), `action` (text), `capability` (text or null), `scope_kind` (text or null), `scope_team_id` (uuid or null), `outcome` (text), `changed_fields` (text[]), `team_id_or_resource_ref` (text, the bounded opaque reference — never the actor's `auth_subject`).
- The mode `full` is Admin-only (`entry_admin + recruiter_master_manage + team_master_manage` triple + effective `all`) and returns the full bounded set.
- The mode `catalog` is `catalog_master_manage@all` and returns only events whose `capability in ('catalog_master_manage','recruiter_master_manage','team_master_manage','employment_status.*','pii_view','pii_export','document_*')` and that are **not** in the security-admin allowlist (`entry_restore`, `app_user_enable`, `app_user_disable`, `direct_entry_grant_*`, `direct_entry_revoke_*`, `direct_entry_link_*`). The full Security slice is excluded for Accounting.
- The mode `own_manager` is a `team_manager_assign@team` actor and returns events whose `app_user_id = caller.app_user_id` AND `action in ('team_leader_designate','team_leader_replace','team_leader_revoke')` AND `scope_team_id = caller.team_id`. The leader must not see the actor's `auth_subject`, the reason text, or any other actor's events.

**Forbidden in the bounded projection (W03D RPC).** `auth_subject`, `app_user_id` (other than the caller's), `reason_id`, raw reason text, credential/token, storage key, raw DB error, any PII (email, phone, name, CCCD), any UUID that would identify a real person outside the W03 audit policy.

**W03D also adds** a new `direct_entry_read_security_audit_self_check()` (internal) that the W03D migration self-check runs to assert: every returned column is in the allowlist; no `auth_subject` is serialised; the SQLSTATE 42501 fires for any non-Full-Admin caller asking for `mode = 'full'`; the SQLSTATE 42501 fires for any non-`catalog_master_manage@all` caller asking for `mode = 'catalog'`; the SQLSTATE 42501 fires for any non-`team_manager_assign@team` actor asking for `mode = 'own_manager'` and not owning the team id.

**W03D does not** add a "fetch all then hide client-side" path. The bounded set is enforced server-side at the SQL level. The page is request-time and never cached.

### C.5 Admin-only `entry_restore` (W03E) — scope and contract-bump are open decisions

**Contract.** `entry_restore` is a capability in the 23-token list; it requires reason + expected version in the W01A `direct-entry-v2.ts` action map (`REASON_REQUIRED_ACTIONS` and `VERSION_REQUIRED_ACTIONS` at `direct-entry-v2.ts:168, :181`); the `REQUIRED_SCOPE_KIND` map at `direct-entry-v2.ts:193` does **not** assign it a scope kind on `main` at `1189c8a`. **R2 restates two open decisions as open**, not as locked:

- **Open decision 1: `entry_restore` scope kind.** Whether to add `entry_restore` to `REQUIRED_SCOPE_KIND` (with the canonical value `all` to match the W01A `catalog_master_manage = all` pattern) is an Owner/T0 call. The W03E plan recommends `all`, but the contract is at `1.3` today and the change is not yet made. W03E will land the scope change **and** the contract bump together, or neither.
- **Open decision 2: `direct-entry-auth` contract version.** If W03E lands the scope change, the contract bumps from `1.3` to `1.4`. The W01A focused lane asserted the v1.3 fixture must keep passing under v1.4; W03E is responsible for keeping the v1.3 fixture green.

**W03E resource scope.** P3.1 only locks the `entry_restore` need. **Other restore surfaces (`submission`, `change_request`, `document`, `leader`) are out of P3.1 and out of W03E.** R2 does not introduce a `restore_kind` enumeration; the W03E RPC is a single `direct_entry_restore_entry(auth_subject, app_user_id, entry_id, expected_version, reason text, idempotency_key text)` that restores a Direct Entry entry from its latest revision. The `entry_id` parameter is the Direct Entry entry UUID; the projection bounded by §A.3 stays the canonical envelope.

**Restore must not re-introduce a revoked security state.** The W03E RPC must `for update` the target entry row + the current revision row + the current capability / scope / link rows of the affected app user in the §A.5 order, must assert the current `enabled` flag, must assert the current capability set, and must raise `55000 'restore would re-introduce a revoked security state'` if the restore would re-introduce a `team_manager_assign`, a `team` scope, a `catalog_master_manage`, a `recruiter_master_manage` or a `team_master_manage` capability that is not currently effective. **Restore is not a way to re-open a W01D leader revoke, a W03A disable, a W03B capability revoke, or a W03C link revoke.**

**W03E closed scope.** Restore is a write that re-creates a historical state of a Direct Entry entry, and only of a Direct Entry entry. Submission, change-request, document and leader restore are explicitly out of P3.1. The scope-kind addition and the contract-bump are Owner/T0 decisions; W03E does not pre-empt them.

### C.6 Combined session-revocation regression (W03F / J01)

**Contract.** W03F is the lane that asserts the W08A invariants hold after W03A–E. The W08A closure memo and `src/lib/auth/p3-w08a-session-revocation-cache.test.mjs` already cover: no in-memory actor cache, concurrent resolves of the same actor cannot return mixed stale/fresh state, cookie refresh does not skip the live check, and the actor resolver is service-role-only. W03F adds: a mutation that disables an app user while a parallel resolve is in flight must make the second resolve see `enabled = false`; a mutation that revokes a capability while a parallel resolve is in flight must make the second resolve not see the capability; a mutation that revokes a verified link while a parallel resolve is in flight must make the second resolve not see the link; the `getDirectEntryActor` call site returns the same denial for the disabled/revoked actor as it would for an actor that was disabled/revoked before the page request started.

W03F does not introduce a parallel session framework; it adds regression cases to the W08A lane. J01 is the readiness audit that signs off W03A–F together.

## H. Production preflight (counts / booleans only; never UUIDs, names, emails, credentials, raw DB error)

The preflight runs read-only in a rollback-only transaction. It emits **counts and booleans**; it never returns a UUID that would identify a real account, never returns an email, name, `auth_subject`, credential, token, or raw DB error. The preflight is the W03F / J01 readiness step. It is **not** part of this R1 survey; it is the design that W03F / J01 must implement and run after T0 accepts the W03A–E package.

1. Migration ledger: applied count, pending count, mismatch count. Boolean: `pending_count = 0`; `mismatch_count = 0`. Required: `migration_count >= 72` (W03A must be at #72; the W01D R5 lane asserted the pre-#72 ledger is byte-stable).
2. Enabled / disabled app-user counts.
3. App-user version distribution. Boolean: `every_app_user_has_version >= 1`. Count: app users whose `version > 1` (the W03A mutations incremented).
4. Auth mapping integrity: app-user rows without an `auth.users` row; `auth.users` rows without a `direct_entry_app_users` row; duplicate or ambiguous `auth_subject` values. Booleans only.
5. Capability grant / scope grant integrity: capability token must be in the 23-token list (count only); scope kind must be in `{own, team, all}`; team scope rows must have a non-null `team_id`; non-team scope rows must have a null `team_id`; intervals must satisfy `valid_to is null or valid_to >= valid_from`; live intervals must satisfy the partial unique indexes (count violations). Booleans only.
6. Capability / scope overlap on live intervals. Count violations; boolean: `overlap_count = 0`.
7. Verified link integrity: app users with more than one effective verified link (count); verified links whose recruiter is inactive (count); orphan links. Booleans only.
8. Non-Full-Admin actors holding a security-admin capability combination. A security-admin combination is `entry_admin` AND `recruiter_master_manage` AND `team_master_manage` (the Full Admin triple) at effective `all` scope. Subset combinations (e.g., `entry_admin@all` alone, which is the Project Admin authority; or `catalog_master_manage@all`, which is the Accounting target authority) are not security-admin combinations and are not counted. Boolean: `non_full_admin_security_combination_holder_count = 0`. Count: legacy `entry_admin@all`-only holders (the Project Admin authority; the Accounting transition concern, separate from W03). The preflight must not print actor identities.
9. Leader-bundle coextensivity: count of leader rows whose `team` scope or `team_manager_assign` capability is not coextensive. Boolean: `coextensivity_violation_count = 0`.
10. Marker mechanism integrity (structural booleans only). The transaction-local GUC `direct_entry.team_leader_marker` is **not** persisted in any row and cannot be read historically; the preflight must not attempt to count "rows created when the GUC was off" — that number is uncomputable from current state. The preflight asserts the structural preconditions: (a) the trigger function `public.direct_entry_team_leader_marker()` exists, is `SECURITY DEFINER`, pins `search_path = pg_catalog, public`, and is revoked from every role; (b) the marker triggers `direct_entry_team_leader_assignment_marker_guard`, `direct_entry_scope_grant_marker_guard`, and `direct_entry_capability_grant_marker_guard` exist and are enabled; (c) the partial marker-excluding indexes (`direct_entry_capability_grants_open_start_uidx`, `direct_entry_scope_grants_start_uidx`, `direct_entry_team_leader_assignments_team_open_uidx`, `direct_entry_team_leader_assignments_leader_open_uidx`) exist with the correct `WHERE` clause. Boolean: `marker_mechanism_structural_ok`. Marker rows themselves are inert and excluded from the partial indexes; their presence is therefore allowed and uninteresting.
11. Audit/revision immutability (structural booleans only). The preflight asserts the immutable-trigger preconditions on `direct_entry_audit_events` and `direct_entry_revisions` (UPDATE / DELETE rejected by trigger). The preflight asserts `entry_restore_all_holder_count = 0` because the W01A `REQUIRED_SCOPE_KIND` map does **not** include `entry_restore` on `main` at `1189c8a`; no `entry_restore@all` holder is meaningful under the current contract. If W03E adds `entry_restore = all` and bumps the contract to `1.4`, the preflight will be updated to assert `entry_restore_all_holder_count <= full_admin_count` (Full Admin triple + effective `all`); until that decision is made, the count is asserted to be zero.

## I. Risks, blockers and the P3.2 boundary

### I.1 Risks (R1-confirmed; carries forward the prior survey's risk list, updated for #71)

1. **No app-user OCC today.** `direct_entry_app_users` has no `version`, no `updated_at`, no per-account revision, no per-account audit. Concurrent status, grant and link work cannot safely share a stale client snapshot until W03A lands. **W03A schema delta is the minimum required.**
2. **Bootstrap is privileged operational code, not lifecycle API.** `scripts/p3-first-owner-bootstrap.mjs` and `scripts/p2-5-accounting-project-admin-provision.mjs` are operator scripts, not runtime lifecycle endpoints. The W01A lane notes the bootstrap is "not lifecycle API"; W03A–E will not turn these scripts into a general lifecycle path. Their post-bootstrap restriction is a separate, explicitly-reviewed decision; W03 does not assume one.
3. **Legacy Accounting grant.** The provisioning script still grants `entry_admin@all` to support existing project operations. W03 must deny its use for security administration without breaking catalog / project behavior; the Accounting transition (grant `catalog_master_manage@all`, verify, revoke legacy `entry_admin@all`) belongs to the controlled W02 transition, not to W03.
4. **W05A seed is not lifecycle.** It derives scope from `personnel_position`, hard-codes seven leaders and grants no `team_manager_assign`. It ran as a one-time seed. W01D has **revoked its `EXECUTE` from every role**; the W01D self-check asserts the revoke; W03A–E will not rerun the seed. W03D's audit-projection lane must assert the seed is revoked.
5. **Audit RPC is too broad for a browser contract.** Existing `direct_entry_read_audit` returns a raw row set that includes `auth_subject` and other internal references. W03D's `direct_entry_read_security_audit` is the bounded, mode-aware replacement; the raw RPC remains a service-role internal helper.
6. **Marker support is asymmetric and the GUC is exclusively W01D.** Membership markers were introduced by #70 for cancellation; capability / scope markers were widened by #71 (W01D section 1, lines 31–66); **link markers are not widened** — the link CHECK stays strict (`valid_to > valid_from`, foundation `:62`) and no marker trigger is installed on `direct_entry_app_user_recruiter_links`. The transaction-local `direct_entry.team_leader_marker` GUC is exclusively owned by the W01D leader apply helper (#71:1384); W03A / W03B / W03C do not set the GUC. Same-day cancellation of a non-leader capability / scope and same-day link revocation are **open product decisions** that the W03B / W03C RPCs currently reject with `22023 'same-day cancellation is open'`.
7. **Link cardinality is fully constrained today (FIX 2 correction).** The foundation `direct_entry_recruiter_link_no_overlap` trigger at `20261002170000:555–556`, calling `direct_entry_guard_effective_interval()` at `:516–528`, acquires the advisory lock `recruiter-link:<app_user_id>` and, when `new.verified = true`, asserts no overlap on every other verified row of the same `app_user_id` with `23P01` on conflict. **R1 was wrong** to claim the schema permits multiple verified effective links per app user; the trigger is the cardinality guard. W03C does **not** add a per-`(app_user_id)` partial verified-effective unique index — partial unique indexes cannot be conditioned on the current date, and the trigger already enforces the cardinality. The W01D designate write additionally requires `count(*) = 1 verified effective link` as defense-in-depth at runtime (`42501`, #71:1217). W03C adds lifecycle RPCs, audit, reason, OCC and idempotency, and reuses the existing trigger and the existing per-`(app_user_id, recruiter_id, valid_from)` unique key.
8. **PII / account identification remains bounded.** The exact account-list fields needed to let an Admin identify an existing login are not locked here. The W03 design will not expose `auth.users.email`; the smallest Owner-approved identifier (e.g., the app user `display_name` + `app_user_id`) is the only identification surface, and the W03D audit projection strips `auth_subject`.
9. **No migration numbers or Production facts are assigned here.** Migration-slot boundary is "W03A uses the next available migration number at the time of implementation; W03B–E do not reserve fixed numbers". Row counts, actual Accounting holders, `entry_restore` holders, mapping anomalies and audit integrity are unknown until the W03F / J01 preflight runs.

### I.2 Blockers (R1 restated)

- T0 must accept the W01D #71 surface as final (it is on `main` at `1189c8a`).
- W03A cannot land before the W01A capability contract is at `direct-entry-auth/1.3` (it is) and before the W01D marker trigger is in place (it is).
- W03B cannot land before the W01D `direct_entry_team_leader_marker()` trigger is installed on `direct_entry_capability_grants` and `direct_entry_scope_grants` (it is).
- W03C cannot land before the W01D designate write is the only writer of leader-bundle rows (it is) and before the W01D leader-read path is locked to the persisted-FK join (it is, per the W01D A2 server contract survey R4–R5).
- W03D cannot land before the W03A–C audit vocabulary is stable.
- W03E cannot land before the W01A `REQUIRED_SCOPE_KIND` map is at `entry_restore = undefined` and the contract is at `1.3`; W03E's plan is to add `entry_restore = all` and bump the contract to `1.4`, but **both changes are Owner/T0 decisions and W03E does not pre-empt them** (the W03E lane will land the scope change and the contract bump together, or neither). The R1 memo stated the bump as a current fact; R2 restates it as an open decision.
- W03F / J01 is the combined regression and readiness audit, run after T0 accepts W03A–E.

### I.3 P3.2 boundary (explicit, locked)

The following are **out of P3.1** and **out of W03**:

- Invitation workflow (email, link, code, expiry).
- Initial password / forced reset / self-service password change.
- MFA enrolment, challenge, recovery codes.
- Account recovery (lost-password, locked-out, deleted-account re-creation).
- The `auth.users.email` change workflow (it lives in Supabase Auth, not in Direct Entry).
- A "default password" of any kind (no `hrp@123` or any other shared default; W03 has no password surface at all).
- A new RBAC framework, a new ORM, a new generic CRUD engine, a parallel audit system.

The W03 design is a **read-only rebaseline** of the access/security surface that already exists on `main` at `1189c8a`. It does not invent a new auth system; it does not open a new invitation path; it does not change the Supabase Auth boundary; it does not add a PII export beyond the W01A `pii_view` / `pii_export` capabilities.
