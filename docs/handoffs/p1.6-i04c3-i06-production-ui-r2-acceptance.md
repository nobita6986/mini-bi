## 9. Appendix — superseded machine observation for T0 reconciliation

This appendix is **not** part of the Owner-attested classification above. It preserves a direct
machine measurement taken earlier in this same session, during an activation attempt that has
since been redeployed, so that T0 can reconcile it before J01. It is recorded rather than
deleted because the agent measured it directly.

During that earlier activation, a machine-driven UI run of the full-profile Excel save produced
**no HTTP request at all**: the paste preview was valid and the save control was enabled, yet no
`POST /api/direct-entry/batches/full-profile` was observed and the UI showed the retryable
network-failure message. A follow-up probe in the Production page context isolated the
mechanism:

| Call form | Result |
| --- | --- |
| `fetch(url, init)` | succeeds |
| `const f = fetch; f(url, init)` | succeeds |
| `obj = { fetchImpl: fetch }; obj.fetchImpl(url, init)` | throws `TypeError: Failed to execute 'fetch' on 'Window': Illegal invocation` |

Calling the global `fetch` as a property of a plain object makes the receiver that object
instead of a `Window`. The Direct Entry write transports inject the global `fetch` and then
invoke it in exactly that form — in the full-profile batch save, the legacy paste batch save and
the CCCD reserve/PUT transport. The read path that calls its injected parameter bare is not
affected.

**Reconciliation needed.** The Owner attestation in §6.2 records that preview and the atomic
batch save work, which this measurement does not reproduce. The agent did not re-run UI
automation after the correction and cannot resolve the difference from outside the UI. The two
records must be reconciled before J01; if the measurement is confirmed, a real-browser check of
each write path is needed, because the existing unit suites inject async mock functions and
therefore cannot cover the receiver-binding behaviour.
