## 6. Exact failed check

**F17 — the full-profile batch never dispatches a request.**

Observed in the real Production browser, with a valid preview
(`1 dòng 1 hợp lệ 0 lỗi 0 cảnh báo`, submit enabled):

- `POST /api/direct-entry/batches/full-profile` requests observed: **0** (CDP network
  events were verified working in the same session against a control request).
- UI outcome: the retryable message `Không gửi được yêu cầu. Chưa dòng nào được lưu; hãy
  bấm Thử lại.` — the `FULL_PROFILE_NETWORK` branch.
- Drafts after the attempt: **0**; submissions after the attempt: **0**.

Root cause, reproduced directly in the Production page context:

| Call form | Result |
| --- | --- |
| `fetch(url, init)` | 200 |
| `const f = fetch; f(url, init)` | 200 |
| `fetch.bind(window)(url, init)` | 200 |
| `obj = { fetchImpl: fetch }; obj.fetchImpl(url, init)` | **throws `TypeError: Failed to execute 'fetch' on 'Window': Illegal invocation`** |

Calling the global `fetch` as a property of a plain object makes `this` that object
rather than a `Window`, which Chrome rejects. The Direct Entry write transports inject
the global `fetch` and then invoke it exactly that way:

| Transport | Injected at | Invoked at |
| --- | --- | --- |
| Full-profile batch save | `src/components/direct-entry/direct-entry-worker-profile-paste-dialog.tsx` (`fetchImpl: fetch`) | `src/lib/direct-entry/full-profile-batch.ts` (`input.fetchImpl(...)`) |
| Legacy paste batch save | `src/components/direct-entry/direct-entry-live.tsx` (`fetchImpl: fetch`) | `src/lib/direct-entry/paste-batch-save.ts` (`input.fetchImpl(...)`) |
| CCCD reserve / PUT | `src/components/direct-entry/direct-entry-cccd-manager.tsx` (`fetchImpl: fetch`) | `src/lib/direct-entry/cccd-transport.ts` (`input.fetchImpl(...)`) |

All three Direct Entry write paths share the defect. The exception is caught by the
transport's network guard and surfaced as a retryable network failure, so the failure is
silent about its cause and no request, batch, entry, document or R2 object is created.

By contrast `src/lib/direct-entry/document-detail-projection.ts` calls its injected
parameter **bare** (`fetchImpl(...)`), which keeps a valid receiver and therefore works;
that is why read paths and entry detail loading are unaffected.

The existing unit suites inject async mock functions, so they exercise the same call
syntax with a legal receiver and cannot catch this class of defect. A real-browser check
of each write path is required to cover it.

No source change was made by this task; the fix belongs to the owning workstream.
