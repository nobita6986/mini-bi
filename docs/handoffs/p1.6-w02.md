## Actor/session/capability/scope

- Supabase `auth.getUser()` verifies the request cookie session through server-only `@supabase/ssr`; only the publishable key is used.
- `auth_subject` maps to `app_user_id` through an injected server repository. The actor contains enabled state, an explicit capability set, effective scopes and sanitized auth metadata; no role claim is used.
- `recruiter_id`, `candidate_id`, `app_user_id`, and `auth_subject` remain distinct.
- Only explicit verified effective-dated app-user/recruiter links create an optional recruiter suggestion. The suggestion grants no capability and does not select/overwrite a recruiter.
- Own scope checks `created_by_user_id`; team scope comes only from an explicit server-side effective scope grant referencing a stable P1.5 `team_id`; all scope remains capability-gated.
- Missing session/mapping/repository/capability data, malformed actor records, disabled actors, and ambiguous recruiter/team relations deny.
- Shared Pilot Basic Auth is not read by the adapter and cannot become a business actor.
- Client body fields for actor, role, capability, and scope are rejected (including nested fields). Resource and actor inputs to policy must be loaded server-side.
- Every policy decision yields an audit envelope with opaque actor/resource references, exact action/capability, scope, timestamp, outcome, and a restricted reason reference where applicable. No free-text reason, token, claim, email, bank or CCCD values enter general audit.

## R1 authorization boundary fixes

| Finding | Root cause | R1 behavior |
|---|---|---|
| Version checks affected read actions and were coupled to possession of `entry_admin` | A trailing `current_version` comparison was unconditional, and actor capabilities injected additional reason/version requirements | Only the explicit `VERSION_REQUIRED_ACTIONS` set checks expected/current version. Reason checks are a separate explicit action set; actor capabilities do not change action policy. |
| Client could claim ownership | Recursive payload deny-list omitted owner aliases | Rejects normalized `owner_user_id`/`ownerUserId`/`owner-user-id` and existing actor/creator/role/capability/scope fields recursively. Own-scope ownership is `created_by_user_id` from server-loaded resource context only. |
| Future team grant overlaps escaped resolution | Only memberships active at session time were counted; authorization accepted the first matching scope | Validates all grants by team across their full intervals, rejects any same-team overlap, allows half-open adjacent and simultaneous different-team grants, and checks matching grant cardinality at the resource date. |

Version compare actions: `entry_admin`, `change_review`, `entry_privileged_edit`, `employment_status.apply`, `payment_edit`, `recruiter_master_manage`, `team_master_manage`, `entry_restore`. Read actions are unaffected by `current_version`. Direct privileged edit, status apply, and payment edit require reason reference and version regardless of whether the actor is Admin or Accounting.

The injected session seam verifies `getUser()` only, asserts the publishable key is used, and confirms refreshed token values do not leak to returned actor/audit/output. It makes no Supabase provider call.
