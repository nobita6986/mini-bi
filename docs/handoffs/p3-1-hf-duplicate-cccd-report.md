# P3.1 hotfix — duplicate CMT/CCCD is reported, never blocked

- Base: `main@79f9a4e46635a832c3c1816a4c53e3df73fb0a5b` (`fix(p3.1): backfill canonical recruiter aliases`); append-only migration #74 is `20261009100000_p3_1_hf_duplicate_cccd_reporting.sql` and nothing before it is edited.
- Root cause: the P2.5-HF cohort made one canonical CMT/CCCD hold at most one live episode, so importing, correcting or rehiring a legitimate second episode (another project, another episode of the same person, a historical row) failed with a business error — and no screen could show which profiles are duplicated.
- Repair: #74 (a) removes the in-batch refusal inside `direct_entry_create_full_profile_batch` — the body v1, v2 and the unscoped v2 implementation all delegate to — through the same `prosrc` replacement technique #58 used, (b) drops the `direct_entry_active_episode_guard` trigger and its function from `public.direct_entries`, (c) re-creates `direct_entry_guard_episode_status_event` keeping only the append-only rule (an OFF episode is never reopened without a supersede marker), and (d) fails closed at install time if any duplicate-CCCD raiser or unique CCCD expression index survives in `public`.
- Validation is untouched: 9/12 ASCII digits, the leading zero, `direct_entry_canonical_national_id` / `direct_entry_is_canonical_national_id`, the `worker_details` validator and every TypeScript contract stay byte-stable.
- New surface: `public.direct_entry_duplicate_cccd_report(auth_subject, app_user_id, page, page_size)` groups every canonical CMT/CCCD that appears on two or more non-deleted `provided` profiles across projects and episodes. It is masked (only `cccd_last4` and `cccd_length` leave the database — never a raw CMT/CCCD and never an entry/worker UUID), bounded (`page_size <= 100`, `page <= 1000`, so the offset stays `<= 100000`), deterministic (`cccd`, then `first_work_date`, then `entry_id` for ordering only) and read-only by construction: one SELECT, no advisory lock, no merge, no repair, no write of any kind.
- Authority: `direct_entry_assert_duplicate_cccd_reader` maps the actor first, then allows the legacy Full Admin triple (`entry_admin` + `recruiter_master_manage` + `team_master_manage`), `catalog_master_manage` (Admin / Accounting) or `entry_privileged_edit` (BoD) **and** requires an effective `all` scope; every other actor, capability or team/own scope fails with `42501` before any read, so nobody receives an empty page that looks like “no duplicates”. Both functions are revoked from `public`, `anon`, `authenticated` and `service_role`; the report alone is granted to `service_role`.
- Regression: `test:p3-1-hf-duplicate-cccd-report` (10 tests) proves the append-only install, that create / import v2 / legacy batch / raw write all accept a second live episode, that no raiser and no unique index survive, the three-audience gate, masking, bounds, deterministic paging and that reading the report never writes, locks, merges or repairs.
- Rebaseline: the ledger moved from 73 to 74, so every lane that counts or positions migrations was rebaselined (P2.5-HF r1/r2/r3/r5, create-rehire, T0 import, W02/W02-R1, W03, W05, W06a, P2-DE, P3-W05a, P3-W07a/b/e, W01d/W02a, concurrency, production bootstrap, reconcile verify and the restore/rollback drill, whose duplicate-episode invariant now asserts the opposite direction). The P2-DE defect fixture and the leader lanes still cut explicitly before the migration whose defect they reproduce instead of dropping a fixed number of tail entries.
- Scope: no UI/API/dependency change; the writer-side duplicate contract of every caller is unchanged for every other code, and the report stays a service-role read for T0 / authorized operators.
