This contract separates authentication, application identity, recruiter identity, candidate identity, and authorization. Authentication proves the Supabase subject; a server-owned mapping resolves that subject to `app_user_id`. A selected `recruiter_id` and a `candidate_id` are separate domain identities. No equality, name, email, or Basic Auth credential infers one identity from another.

## Session and actor boundary

1. The server-only adapter reads request cookies using Next.js 16.3.8's asynchronous `cookies()` API.
2. A request-scoped `@supabase/ssr` client uses the publishable key and calls `auth.getUser()` to verify the cookie session. It never uses the service-role/secret key to impersonate a user.
3. The injected actor repository resolves the trusted `auth_subject` to an enabled application user and server-owned capability/scope data. The returned subject must match the verified session subject; a mismatched mapping is malformed and denied. A repository mapping is not client input.
4. The actor contains only `auth_subject`, `app_user_id`, enabled state, explicit capabilities, effective scopes, an optional recruiter suggestion, and sanitized session metadata (`provider`, verification method, nullable authentication time). Raw access/refresh tokens, user objects, email, and raw claims are not returned.
5. Missing session, missing repository/mapping, malformed record, disabled actor, or ambiguous verified recruiter/team membership denies. Repository exceptions are allowed to surface; no actor is synthesized.

The adapter is intended for a Route Handler or Server Action, where cookie refresh can be written before the response is committed. It returns the Supabase refresh cache headers (`Cache-Control`, `Expires`, `Pragma`) for the caller to apply to the response; callers must not drop them. It is not wired to the existing dashboard or Shared Pilot Basic Auth gate. Basic Auth is only the existing outer gate and never yields a business actor.

## Identity reconciliation with P1.5-W02

| P1.6 concept | Authority and relation |
|---|---|
| `auth_subject` | Verified Supabase Auth subject from server-side `getUser()` |
| `app_user_id` | Explicit repository mapping from `auth_subject`; mutation actor and owner for own scope |
| `recruiter_id` | Existing stable P1.5 recruiter ID; optional explicit verified effective-dated app-user/recruiter link only |
| `team_id` | Existing stable P1.5 team ID referenced by an explicit effective authorization scope |
| `candidate_id` | W01 worker/candidate identity; never an actor or authorization principal |
| Provider/team intervals | Existing P1.5 half-open `[valid_from, valid_to)` semantics; no second master/identity model |

A verified app-user/recruiter link may provide the `self_recruiter_suggestion` stable ID for a future “Bản thân” picker option. It does not add capabilities, change ownership, choose a recruiter automatically, or create any scope. More than one effective verified link fails closed. Team scopes are separate explicit authorization grants resolved by the injected repository, keyed only by stable P1.5 `team_id` and effective interval; they are not inferred from recruiter links, display text, or current-team labels. Multiple distinct team scopes are valid; duplicate overlapping grants for the same team fail closed. Active P1.5 team identity is required when a grant is effective now. This is an authorization scope relation, not a parallel recruiter/team identity master.

This uses stable IDs and the capability/action vocabulary directly. P3 may replace where grants are stored with RBAC assignments without changing `app_user_id`, recruiter/team IDs, action/capability names, or the audit envelope.

## Capability vocabulary and scope

The policy checks one exact capability for every action; roles are neither stored in the actor nor accepted from the client:

`entry_create`, `entry_own`, `entry_team`, `entry_admin`, `submission_create`, `change_request_create`, `change_review`, `entry_privileged_edit`, `employment_status.request`, `employment_status.review`, `employment_status.apply`, `document_upload`, `document_view`, `payment_view`, `payment_edit`, `recruiter_master_manage`, `team_master_manage`, `pii_view`, `pii_export`, `audit_view`, `entry_restore`.

Effective scopes are server-resolved `own`, `team`, or `all` references with effective intervals. The client payload validator rejects `owner_user_id` and aliases normalizing to `owneruserid`, plus the actor, creator, role, capability, and scope authority fields, recursively through objects and arrays. Fields such as `owner_label` and `ownership_note` are not authority fields and remain valid business payload. Ownership used for authorization is loaded in `TrustedResourceContext` as `created_by_user_id` by the server repository; never use a client field or `recruiter_id` for ownership.

A team decision must match exactly one server-loaded stable `team_id` grant effective on the resource date. All team grants are validated at actor resolution: invalid intervals are malformed; any overlapping intervals for the same team—including future-only or duplicate intervals—fail closed as ambiguous. Half-open adjacent intervals are allowed. Grants for different teams can overlap. Matching-scope cardinality is checked explicitly; multiple effective grants cannot be hidden by a first-match/`.some()` policy check. All scope remains a separate explicit grant, requires the exact action capability, and must be effective on the resource date.

`expected_version` is required and compared only for the following action set: `entry_admin`, `change_review`, `entry_privileged_edit`, `employment_status.apply`, `payment_edit`, `recruiter_master_manage`, `team_master_manage`, and `entry_restore`. Missing, malformed, malformed resource version, and stale expected version deny with distinct codes. Read actions—including `payment_view`, `document_view`, `pii_view`, `pii_export`, and `audit_view`—do not require or compare a version, even when resource context contains `current_version`. Reason requirements are independently action-based (`entry_admin`, `change_review`, `entry_privileged_edit`, `employment_status.review`, `employment_status.apply`, `payment_edit`, recruiter/team master management, and restore); holding `entry_admin` capability never silently changes another action's requirements.

| Capability group | Baseline |
|---|---|
| Staff | Explicit create, own-scope draft actions, submit, and change-request capabilities |
| Leader | Explicit capabilities plus effective team scope; no outside-team access |
| Internal Accounting | Explicit change-review, privileged-edit, payment, and status-apply capabilities; no implicit `pii_export` or `document_view` |
| Admin | May be granted all capabilities and scopes, but every mutation is still checked for scope, expected version, and restricted reason reference where required |

Direct privileged edits are one-step and do not require a second reviewer. They do require exact capability, applicable scope, a non-empty restricted reason reference, expected version, and audit. A stale version is denied; no admin bypass exists.

## Client payload and audit boundary

Business payloads containing `auth_subject`, `app_user_id`, actor ID, `created_by_user_id`, role, capability, or scope fields are rejected, including nested fields. The policy only accepts a separately resolved actor and server-loaded resource. No rejected field can supply the actor or enter audit as the actor.

Every authorization decision returns a sanitized audit envelope: opaque auth subject/app-user refs (nullable if unauthenticated), action/capability, opaque resource ref, resource scope, server timestamp, outcome, denial code, and optional opaque `reason_ref`. Free-text reason, business values, CCCD, bank account, token, email, and raw auth claims are excluded. The protected reason text, if required, belongs in a restricted store outside general audit; W03 must provide that storage and audit persistence.

## Supabase and Next.js adapter

- Uses `@supabase/ssr` with `createServerClient`, request `getAll`/`setAll` cookies, and Supabase `auth.getUser()`.
- Uses `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`; never `SUPABASE_SECRET_KEY`.
- `cookies()` is awaited. Cookie mutation is performed only when the adapter is invoked in a Route Handler/Server Action context that can write response cookies; callers also apply any returned auth-refresh cache headers to the response.
- No route, login flow, user creation, service-role client, dashboard gate change, or real Auth session is implemented in W02.
- Repository is injected for testability and because mapping/grant schema belongs to W03.
- An injected session-client seam tests the actual adapter flow without a provider call: it asserts `getUser()` is used, `getSession()` is not, only the publishable key is passed, and refreshed cookie tokens do not appear in the returned actor/headers.

## Deliberate boundary / follow-up

W02 defines policy and session integration only. W03 must define schema/grants, transactional capability and membership resolution, optimistic version checks at write time, RLS/grants, and durable audit/restricted reason storage. The existing Basic Auth gate remains unchanged. No schema, migration, DB write, UI, grid, upload, Drive, n8n, or production route is part of this contract.
