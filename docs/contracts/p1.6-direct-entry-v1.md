This is a versioned domain contract and pure validation/state-machine spike. It is not a database schema, authorization implementation, API, upload implementation, or production UI. Stable recruiter/provider/team identity and effective-date semantics are inherited from P1.5-W02 (`identity-projection/1.0`); W01 does not create a parallel recruiter/team identity.

## 1. Identity and recruiter selection

Three identifiers have separate meanings and storage fields:

| Identifier | Meaning | Source |
|---|---|---|
| `app_user_id` | Authenticated account and mutation actor | Future W02 session boundary |
| `recruiter_id` | Recruiter selected for the reported entry | Existing recruiter master identity |
| `candidate_id` | Stable identity of the worker/candidate | Direct-entry domain |

`DirectEntry.app_user_id` records the app user who created/entered the row and is the actor reference, not the selected recruiter. An actor can happen to be the selected recruiter only through an explicit, verified, effective-dated `app_user_recruiter_links` row. No match by ID equality, name, email, or phone is performed. No active link returns no recruiter suggestion; it does not guess.

Recruiter selection stores only a stable `recruiter_id` from the master. Text typed into a search field is a query, never a new recruiter or canonical value. Search normalization reuses the W02 normalized key (NFC, trim, collapse whitespace, lowercase) and folds accents for deterministic prefix matching. At `first_work_date`, exactly one provider membership across HRP and Vendor and exactly one team membership must be effective. Any overlapping provider memberships (including HRP+Vendor or same-type overlap) or team memberships are ambiguous and rejected. `provider_type` is derived from the sole provider membership; a submitted value is only a consistency assertion and must match. The recruiter and selected team must be active; membership intervals must include the date. Search returns stable IDs and sorts by ID.

Membership intervals use W02's half-open `[valid_from, valid_to)` rule. `valid_from` is included; `valid_to` is excluded. Provider/team membership changes do not rewrite historical facts. An inactive recruiter is not eligible for a new entry, even though W02 may still resolve historical facts for that identity.

## 2. Employee code

### Proposed canonical format

```text
hrp-[YYYY from first_work_date]-[exactly 6 ASCII digits]
example: hrp-2026-000001
```

- The entire canonical value is lowercase and matches `hrp-YYYY-NNNNNN`. Uppercase and any suffix other than exactly six digits are not canonical.
- The serial is a string. Leading zeros are preserved and never parsed as a number.
- The year must match the real calendar year in `first_work_date`.
- Uniqueness is global after canonicalization. Codes are not reused after OFF/cancellation.
- DB is authoritative for uniqueness/reservation and may issue a suggested code. UI manual entry of six digits is allowed, but the server must validate and reserve atomically. This spike does not allocate serials or reserve codes.
- After submission, a normal user proposes a code change in a change request. Admin/internal Accounting may apply it directly only with reason, expected version, revision, and audit.
- A numeric legacy code that is not exactly six digits is rejected from canonical entry and routed to a legacy/quarantine flow. Never pad, truncate, renumber, or canonicalize it into a new code. Legacy collisions are quarantined, not auto-resolved.
- If a corrected first-work date changes year, the same atomic request must provide a matching new employee code; never rewrite the code implicitly.


## 3. Entry fields and optional values

The entry contract covers project, first-work date, worker details, recruiter ID, provider type (`hrp`/`vendor`), labor type (`TEMPORARY`/`PERMANENT`), employee code, project/master references, documents, payment details, and append-only employment status events. Actor identity remains separate from recruiter identity.

Optional data uses explicit states:

```ts
{ state: "omitted" }
{ state: "unknown" }
{ state: "intentionally_blank" }
{ state: "provided", value: ... }
```

Do not convert missing data into a placeholder or an invented value. The payment group is either one of those three empty states or `provided` with all of account number, active `bank_id`, and account-holder name. Account number is text and preserves leading zeros. An all-empty/omitted payment group does not block first submission. Normal users may edit it in DRAFT/REVIEW; after submission they see masked data and use a change request. Admin/internal Accounting may view full values and edit directly with capability, reason, expected version, revision, and audit. General audit rows contain no plaintext account number; restricted revisions may retain before/after values. A later payment update is versioned.

PII fields in fixture data are explicitly synthetic. Do not place real PII in tests, report, logs, screenshots, query strings, or Git artifacts. Payment and worker revisions belong in a restricted private store; general audit rows carry revision references and changed field names rather than copying plaintext values.

## 4. Submission and changes

```text
DRAFT -> REVIEW -> SUBMITTED
           |
           +----> DRAFT

SUBMITTED -- normal user --> CHANGE_REQUEST (PENDING)
PENDING -- reviewer approve --> atomic apply + new version/revision/audit
PENDING -- reviewer reject --> rejected + reason; canonical data unchanged
SUBMITTED -- Admin/Accounting direct edit --> reason + expected version + audit
```

One submission is a non-empty batch of 1..N unique `entry_id`s with `created_by_user_id`, state, optimistic version, and created/updated/submitted timestamps. REVIEW and SUBMITTED transitions apply to the whole batch; an empty batch or duplicate row is invalid. Returning REVIEW to DRAFT permits edits. SUBMITTED publishes the batch as canonical immediately; the initial submission does not wait for Admin/Accounting approval.

- `DRAFT`: user with applicable entry capability may add/edit/remove draft rows in the batch.
- `REVIEW`: read-only review of the complete data/snapshot; `RETURN_TO_DRAFT` is allowed and creates no submitted snapshot.
- `SUBMITTED`: normal users cannot mutate canonical rows or current document/status/payment data and may only create change requests.
- A normal user must create a `CHANGE_REQUEST` that identifies each exact row and field, document, or status event plus its expected version. Pending requests are separate proposal data and do not affect canonical values, aggregates, or current status.
- Approval validates every target/version and stages every change before returning any mutation. A failure or stale version returns no partial change. Success increments row version once, retains before/after revision snapshots, and emits actor, reason, timestamp, version, changed fields, and audit references.
- The proposer may withdraw a request while it is PENDING. A reviewer decision stores reviewer actor, timestamp, and non-empty decision reason; decision does not rewrite proposal items. There is no hard SLA in this contract; timestamps and request age are retained for monitoring.
- Rejection retains canonical values and requires a reason.
- Admin/internal Accounting may apply a privileged direct edit without a second reviewer, but must provide capability, reason, expected version, and audit. There is no unaudited path.

W01 defines capability vocabulary only. The module does not implement login, session, policy evaluation, API endpoints, grants, or RLS.

## 5. Employment status

Statuses are `UNCONFIRMED`, `ON`, and `OFF`. The initial applied event is `UNCONFIRMED`, never a fabricated `OFF`. Current status is derived from the applied append-only event history; pending/rejected proposals are not included.

Allowed forward transitions:

| From | To |
|---|---|
| `UNCONFIRMED` | `ON`, `OFF` |
| `ON` | `OFF` |
| `OFF` | `ON` |

No-op transitions are rejected. An `OFF` proposal requires `leave_date` and non-empty free-text `leave_reason_text` suitable for a textarea. `ON` and `UNCONFIRMED` events cannot carry leave fields. An `OFF` to `ON` return appends a new event and retains the old leave information. Events include actor, reason, effective date, applied timestamp, and monotonic version.

`effective_date` cannot precede `first_work_date` or be in the future at MVP validation time. `OFF` requires a trimmed non-empty reason of at most 4,000 characters and `leave_date` equal to `effective_date`; `ON` and `UNCONFIRMED` require both leave fields to be null. An erroneous latest event is corrected by appending a replacement with `supersedes_event_id`; original history remains. Admin/Accounting direct application requires capability, reason, expected version, revision, and audit. W01 supports correcting only the latest active event; correcting a non-latest event is not allowed.

## 6. Document lifecycle

Logical types: `CCCD_FRONT`, `CCCD_BACK`, and `EMPLOYMENT_CONTRACT`. Every upload is a new immutable document version with idempotency key, SHA-256 checksum, byte size, allowlisted MIME, actor/time, attempt count, scan status, storage key, and optional superseded version.

```text
QUEUED -> UPLOADING -> QUARANTINED -> SCANNING -> READY
                    \---------------------------> FAILED -> QUEUED (retry)
READY -> SUPERSEDED (only after an approved replacement is applied)
```

PDF/JPEG/PNG have a 10 MiB hard ceiling. `CCCD_FRONT`, `CCCD_BACK`, and `EMPLOYMENT_CONTRACT` are not blockers for initial submit in MVP. Submission/read models expose per-type missing/present completeness so follow-up can address gaps. Idempotency uniqueness is scoped by `(candidate_ref, document_type, idempotency_key)`; retry with the same checksum returns the existing version, while reusing the key with different content is rejected. Replacement appends a version/storage object and never overwrites the old binary. Approval atomically changes the canonical version pointer/lineage. Quarantined/pending files are not current documents.

Physical storage keys are constructed only from an opaque `candidate_ref`, document type, random opaque `doc_<32 hex>` ID, and version. No browser filename or CCCD plaintext is accepted as a storage name. A UI may display a masked logical label. Quarantine and virus scan are placeholders here; there is no Drive call or upload.

W04 must implement server-side magic-byte inspection, antivirus/quarantine, retry/reconciliation, and authorized download before publishing real documents. Physical file naming never uses browser filename or plaintext CCCD. Legal retention duration is deferred to P3; W01 assigns no retention period.
