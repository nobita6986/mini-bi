## 3. Crypto envelope and AAD

Envelope version 1 uses `aes-256-gcm`, 12-byte random IV, 16-byte authentication tag, base64 ciphertext and ISO creation time. AAD is canonical JSON over:

`["ai-config-secret", envelope_version, config_id, provider_profile, config_version]`

The decrypt call requires the expected context and checks its identity/version against the envelope before authentication. Wrong key IDs, wrong keys, tampering and malformed envelopes fail closed with a small error code/message only. There is no plaintext fallback. API URL diagnostics and errors never contain a raw query; query strings are rejected at URL validation.

`keyringFromEnvironment` reads the active 32-byte base64 key from `AI_CONFIG_MASTER_KEY` and optional active ID from `AI_CONFIG_ACTIVE_KEY_ID` (default `k1`). It does not inspect `NEXT_PUBLIC_*`. The current test command uses Node's `react-server` condition for the installed `server-only` marker; Next client imports are rejected by that marker.

## 4. Keyring and rotation

The active key encrypts new config versions. Previous keys are supplied as an injected keyring, enabling old key IDs to decrypt without loading/persisting old master keys in this spike. Rotation returns a new config version/envelope and leaves the input version unchanged; it does not delete or overwrite audit/config history. `configNeedsKeyRotation` identifies envelopes whose key ID differs from the active ID.

The fingerprint is a 16-hex-character HMAC-SHA-256 prefix using a domain-separated input and active key. It is a short, keyed identifier, not the secret or a reversible encoding. It will change when recalculated under a different active master key.

No KMS, secret store, master-key backup, key distribution, or old-key lifecycle is implemented.

## 5. Config commands, projection, and audit

The config model includes provider profile, base URL, model, encrypted envelope, config/optimistic version, status, verification/update timestamps, sanitized host, and short fingerprint. Secret text is accepted only by create/rotate command inputs; test commands use synthetic text values.

`projectConfig` constructs an explicit field allowlist. It omits the encrypted envelope and full base URL, and therefore contains no plaintext key, ciphertext, IV, tag, Authorization header, or master key. There is no config/HTTP API that reads a secret. Decryption remains a server-only crypto primitive for a future provider request path.

The pure activation function permits one active config at a time and disables (does not delete) the previous active version. Failed candidate verification marks only that candidate `test_failed`, preserving the current active version. Disable retains the record. Audit construction returns exactly actor, action, version, provider, model, sanitized host, fingerprint, outcome, timestamp, and reason code.

These are in-memory domain functions, not concurrency-safe persistence. W04A must enforce optimistic writes and the single-active invariant transactionally in its selected storage layer.

## 6. URL normalization and allowlist

- Production/preview require HTTPS. Hostnames are normalized by WHATWG `URL`, lowercase/trailing-dot normalization and IDNA/punycode conversion.
- Allowlist matching is exact against `AI_PROVIDER_ALLOWED_HOSTS` (comma-separated) or an injected list. There is no suffix/wildcard matching.
- URLs with userinfo, any fragment/query delimiter, local hostnames, IP literals, metadata names, or non-allowlisted ports are rejected. Default port allowlist is only 443. Rejecting all queries avoids storing/logging API-key-like query material in a base URL.
- Development HTTP/local-address exception requires `environment=development`, `NODE_ENV=development`, and explicit `AI_CONFIG_ALLOW_LOCAL_HTTP=true` (or an injected explicit flag). Preview/production ignore this override. Local ports still must be explicitly added to the port list.
- Diagnostics return only normalized host and optional port, never path/query.

## 7. IP range policy

IPv4 answers in unspecified, private, CGNAT, loopback, link-local, protocol-assignment, documentation, benchmarking, multicast, reserved, broadcast/metadata ranges are rejected. This includes Azure `168.63.129.16` and cloud metadata addresses in link-local/CGNAT.

IPv6 answers are allowed only in global-unicast `2000::/3`, with special-use/protocol, documentation, 6to4, benchmarking-style and `3fff::/20` ranges excluded. ULA, link-local, loopback, unspecified, multicast and IPv4-mapped IPv6 are denied. The development exception allows only loopback, RFC1918 IPv4, and IPv6 ULA; link-local/metadata remains denied.

The policy is deliberately conservative. Range tables should be reviewed against current IANA special-purpose registries before production.

## 8. DNS pinning and rebinding

The default resolver uses Node `dns.lookup(host, { all: true, verbatim: true })` immediately before each request attempt. Every returned A/AAAA address is checked; any blocked address rejects the entire result. The injected transport receives that exact approved address set.

The default Node HTTP(S) request uses a custom `lookup` that can return only those checked addresses. HTTPS preserves the original normalized hostname for `servername` and `Host`, and explicitly keeps `rejectUnauthorized: true`. A changed answer on a later redirect is resolved and checked again. There is no hostname-validate-then-unpinned-fetch gap in this transport path.

Resolver and transport are injectable. All tests use fakes and do not make external requests.

## 9. Redirect and Authorization policy

Redirects are rejected by default. Opt-in following is capped (default 3, hard maximum 5), parses the target relative to the response URL, re-runs scheme/host/port policy, re-resolves DNS, checks every address, and pins that attempt. Disallowed private/metadata or off-allowlist targets fail before another transport call. Loops terminate at the redirect cap.

Same-origin redirects may retain credentials. A cross-origin redirect strips Authorization, cookies, token/secret/key/credential headers. POST-to-GET 301/302 and 303 transitions drop the request body and entity headers. Host is always replaced with the validated target host; callers cannot supply Host or proxy-auth headers.

## 10. Timeout, size limit, and errors

One deadline covers resolution and all redirect attempts; each request also receives remaining time and Node request timeout/abort. Default response limit is 256 KiB; callers cannot raise the configured ceiling above 2 MiB. Content-Length and streaming bytes are both checked. There are no retries. Resolver, transport and raw provider errors are mapped to fixed safe error codes/messages; the library does not log provider bodies or raw URLs.

## 13. Limits / not proven here

- IP block lists are local policy code and need periodic IANA review.
- No encrypted-secret persistence, transaction/unique constraint, audit storage, concurrency race, KMS, RBAC, rate limit, or key rotation runbook exists.
- No client bundle or browser serialization path imports this library; `server-only` guards future accidental Client Component imports. No UI/API route was created.
