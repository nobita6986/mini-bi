## 3. Supported Excel profile

The contract has **20 persisted fields** and **5 validation-only derived
hints**. Six fields are the minimal required profile; this does not mean the
application supports only six columns.

| Worker identity | `Giới tính`, `DOB`, `CMT/CCCD`, `Ngày cấp`, `Nơi cấp`, `Địa chỉ hiện tại`, `Số điện thoại` | Persisted, optional |

| Employment | `Tình trạng làm việc hiện tại`, `Ngày nghỉ thực tế`, `Ghi chú về nghỉ việc` | Persisted; leave fields are conditional for `OFF` |
| Account metadata | `STK`, `Tên ngân hàng`, `Tên chủ tài khoản` | Persisted, optional and independent; no bank-catalog lookup |

are import aliases only. Header order is not significant. Optional headers may
be absent.

## 4. Fixture and evidence policy

### 4.1 Synthetic data

Before mutation, create a run identifier in the form
`I06-YYYYMMDD-HHMM`. Use only visibly synthetic values:

- worker name beginning with `TEST I06`;
- an unused `hrp-2026-NNNNNN` code whose year matches the first-work date;
- synthetic 9- or 12-digit national ID checked for exact collision before use;
- synthetic phone and notes containing the run identifier;
- generic account metadata such as a leading-zero digit string, a synthetic
  bank label and a synthetic holder name;
- generic file names such as `i06-front.jpg` and `i06-back.png`.

Do not use a real person's name, national ID, phone, address, account number or
image. Do not place raw fixture values in screenshots or the committed
handoff. Evidence records field coverage, status, counts and sanitized codes.

### 4.2 Manifest

Create a local, gitignored run manifest before the first mutation. It records:

```json
{
  "test_id": "I06-YYYYMMDD-HHMM",
  "deployment_id": "<serving deployment id>",
  "source_sha": "dde2bbcfd75855976e6fa19ff2fc307a6db357bc",
  "submission_id": "<runtime UUID>",
  "entry_ids": ["<runtime UUID>"],
  "documents": [
    {
      "document_id": "<runtime UUID>",
      "document_type": "CCCD_FRONT",
      "expected_disposition": "retain-final-or-verify-staging-deleted"
    }
  ]
}
```

Runtime UUIDs and object keys remain in the local manifest only. The committed
handoff contains counts and outcomes, not identifiers.

There is no sanctioned Production delete operation for a successful Direct
Entry entry/submission. Therefore:

- do not use direct SQL or table DML to erase the fixture;
- retain a successfully finalized object while its document row remains;
- verify rejected/invalid staging objects are deleted by the server;
- delete an R2 object manually only when it is in the manifest **and** no
  retained database document references it;
- never enumerate and delete by a broad bucket prefix.

## 11. Stop and rollback

The default I06 rollback is **UI-only**:

1. Remove/unset `DIRECT_ENTRY_UI_ENABLED` in Production.
2. Redeploy the same approved `main@dde2bbc…` source.
3. Keep `DIRECT_ENTRY_API_ENABLED`, all R2 variables and the bucket unchanged.
4. Verify the navbar hides `Nhập liệu` and `/direct-entry` is fail-closed.
5. Verify the authenticated read-only API smoke from I05A remains healthy.

Do not rotate R2 credentials during an ordinary UI rollback. Credential
rotation is reserved for a separate credential/storage incident.

Immediate stop conditions:

- source, alias or migration drift;
- I05A not PASS;
- any secret or real PII in logs/screenshots;
- batch partial persistence;
- wrong bucket or permissive CORS;
- account metadata blocked only because `banks=0`;
- raw account number visible without `payment_view`;
- automatic retry after OCC conflict;
- finalized DB document without a valid final object;
- deletion attempted without a manifest or against a broad prefix;
- reporting baseline changes.

After rollback, record the deployment ID and the four UI-off assertions. Do
not claim I06 PASS merely because rollback succeeded.
