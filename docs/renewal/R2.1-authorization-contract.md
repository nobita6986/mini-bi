## 1. Change Request Queue & Historical Visibility Contract (`WP-2.1.1` & `WP-2.1.3`)

### 1.1 Canonical Queue Tokens (`state` query parameter on `GET /api/direct-entry/change-requests`)

The read contract (`src/lib/direct-entry/change-request-read-contract.ts`) and database RPC (`public.direct_entry_list_change_requests`) accept:

- **Canonical R2 Queue Filters:**
  1. `PROPOSER_PENDING` — Requests currently in `PENDING` state created by the current actor:
     - SQL predicate: `r.state = 'PENDING' and r.proposer_user_id = p_app_user_id`
     - `can_withdraw`: `(v_audience = 'PROPOSER')` (true **if and only if** the actor still holds current proposer authority over all items in the request, matching `public.direct_entry_withdraw_change_request`)
     - `can_decide`: `false`
  2. `PROPOSER_RESOLVED` — Terminal requests (`APPROVED`, `REJECTED`, `WITHDRAWN`) created by the current actor:
     - SQL predicate: `r.state in ('APPROVED', 'REJECTED', 'WITHDRAWN') and r.proposer_user_id = p_app_user_id`
     - Remains visible to the active proposer even if their Project Manager / team assignment was later revoked or changed.
     - `can_withdraw`: `false`
     - `can_decide`: `false`
  3. `REVIEWER_PENDING` — Requests currently in `PENDING` state that the actor has **current** review authority to decide:
     - SQL predicate: `r.state = 'PENDING' and r.proposer_user_id <> p_app_user_id and public.direct_entry_change_request_audience(p_app_user_id, r.proposer_user_id, r.request_id) = 'REVIEWER'`
     - Strict anti-self-approval: `r.proposer_user_id <> p_app_user_id` is enforced both in SQL and in `direct_entry_change_request_audience`.
     - `can_withdraw`: `false`
     - `can_decide`: `true`
  4. `REVIEWER_RESOLVED` — Terminal requests (`APPROVED`, `REJECTED`) that were **personally decided by the current actor**:
     - SQL predicate: `r.state in ('APPROVED', 'REJECTED') and r.decided_by_user_id = p_app_user_id and r.proposer_user_id <> p_app_user_id`
     - Keyed strictly on `r.decided_by_user_id = p_app_user_id` (not general reviewer scope), so a reviewer always sees the history of requests they personally approved/rejected even after scope changes, and does not conflate team/all scope history with their own review history.
     - `can_withdraw`: `false`
     - `can_decide`: `false`
- **Global Audit Mode (`GLOBAL_AUDIT`):**
  - Routed by `change-request-read-api.ts` to `public.direct_entry_list_global_change_request_history(p_auth_subject, p_app_user_id, p_page_size, p_cursor, p_days)`.
  - Requires `days` query parameter (`3 | 7 | 30 | all`); non-`GLOBAL_AUDIT` queues reject `days`.
  - Gated by `direct_entry_has_scope(p_app_user_id, 'all') and (direct_entry_has_capability(p_app_user_id, 'entry_admin') or direct_entry_has_capability(p_app_user_id, 'change_review'))`.
  - Distinct from `REVIEWER_RESOLVED` ("Lịch sử duyệt của tôi").
- **Legacy Compatibility Filters (`PENDING`, `RESOLVED`, `APPROVED`, `REJECTED`, `WITHDRAWN`, `null`):**
  - Retained during R2.1 so existing `/direct-entry` UI and existing P1.6/P2.5/P3.1 tests continue to work without regression until R2.2 migrates the UI.
  - For legacy resolved states (`RESOLVED`, `APPROVED`, `REJECTED`, `WITHDRAWN`, `null`), a request is visible if `v_audience <> 'NONE'` OR `r.proposer_user_id = p_app_user_id` (when `r.state in ('APPROVED', 'REJECTED', 'WITHDRAWN')`) OR `(r.state in ('APPROVED', 'REJECTED') and r.decided_by_user_id = p_app_user_id and r.proposer_user_id <> p_app_user_id)`.

### 1.2 Immutable Request History vs Current Entry Scope (`direct_entry_read_change_request`)

When reading a single request via `public.direct_entry_read_change_request(p_auth_subject, p_app_user_id, p_request_id)`:
1. Actor must be an active, mapped user (`direct_entry_assert_actor_mapping(p_auth_subject, p_app_user_id)`). Disabled/unmapped actors fail closed (`42501` -> HTTP `403`).
2. `v_audience` is resolved in order:
   - First, `public.direct_entry_change_request_audience(p_app_user_id, v_request.proposer_user_id, v_request.request_id)` (`'PROPOSER'` or `'REVIEWER'` when current authority over all items holds).
   - If `'NONE'` and `v_request.proposer_user_id = p_app_user_id`: `v_audience := 'PROPOSER_HISTORY'`.
   - Else if `'NONE'` and `v_request.state in ('APPROVED', 'REJECTED') and v_request.decided_by_user_id = p_app_user_id and v_request.proposer_user_id <> p_app_user_id`: `v_audience := 'DECIDER_HISTORY'`.
   - Else if `'NONE'` and `v_request.state in ('APPROVED', 'REJECTED') and public.direct_entry_has_scope(p_app_user_id, 'all') and (public.direct_entry_has_capability(p_app_user_id, 'entry_admin') or public.direct_entry_has_capability(p_app_user_id, 'change_review'))`: `v_audience := 'AUDITOR'`.
   - Otherwise: raise `insufficient_privilege` (`42501` -> HTTP `403`).
3. **Strict Boundary Between Request Snapshot and Current Worker Profile:**
   - `direct_entry_read_change_request` returns ONLY the immutable change-request record (`request_id`, `state`, `version`, `created_at`, `request_reason` for reviewer/auditor/decider-history, `can_withdraw`, `can_decide`) and its sanitized item proposals (`entry_id`, `target_kind`, `expected_version`, `proposal` via `direct_entry_change_request_proposal_projection`, `labor_type_display`).
   - It **never** grants access to `direct_entry_read_projection`, `direct_entry_list_workers`, or document download RPCs for entries outside the actor's current scope.
   - `can_withdraw` is `(v_audience = 'PROPOSER' and v_request.state = 'PENDING')`. For `'PROPOSER_HISTORY'` (an actor who submitted a request while PM, then lost PM assignment while the request is still `PENDING`), `can_withdraw` is `false` — matching `direct_entry_withdraw_change_request` which requires `v_audience = 'PROPOSER'`.
   - `can_decide` is `(v_audience = 'REVIEWER' and v_request.state = 'PENDING')`.

## 2. Project–Team Effective Scope Guard & Subtransaction Removal (`WP-2.1.2`, P0)

### 2.1 Cross-Project Boundary Guard in `public.direct_entry_apply_change_item` (P0 Security Fix)

- **Vulnerability Confirmed at Gate 0:** In `20261020200000_r1_current_state_authorization.sql`, when `direct_entry_decide_change_request` approves an `ENTRY_FIELD` item via Team Leader review (`v_team_review = true`), `direct_entry_apply_change_item` checked `v_team_id is distinct from p_entry.team_id` for the target recruiter, but **did not check** `public.direct_entry_project_team_scope_effective(v_target_project_id, v_team_id)` (nor on `p_entry.project_id`). A Team Leader could approve an `ENTRY_FIELD` proposal moving an entry's `project_id` to a project outside their team's effective project–team scope.
- **Contracted Fix:**
  - In `public.direct_entry_apply_change_item`, whenever `v_team_review` is `true`:
    1. Assert `public.direct_entry_project_team_scope_effective(p_entry.project_id, p_entry.team_id)` before applying any item.
    2. In the `ENTRY_FIELD` branch, after resolving `v_target_project_id` and `v_team_id`, assert `public.direct_entry_project_team_scope_effective(v_target_project_id, v_team_id)` (raising `sqlstate '42501'` if false), matching the exact invariant enforced by `direct_entry_privileged_edit`.

### 2.2 Exception-Free `public.direct_entry_resolve_direct_edit_authority`

- Replace the `begin v_scope := public.direct_entry_assert_entry_access(...); ... exception when insufficient_privilege then null; end;` subtransaction block in `public.direct_entry_resolve_direct_edit_authority` with a pure boolean check using `public.direct_entry_has_entry_access(p_app_user_id, 'entry_privileged_edit', p_entry_owner, p_team_id, null)` (plus active actor mapping check), eliminating per-row savepoint/subtransaction overhead during `direct_entry_list_workers_search`.
