## 2. Team Leader direct edit

1. Reuse the existing Worker Operations direct-edit flow, API, repository, and RPC. The current call path is worker-operations.tsx → privileged-edit-api.ts → privileged-edit-repository.ts → direct_entry_privileged_edit.
2. The API derives actor identity from the authenticated server session. Do not accept user ID, title, capability, scope, or team authority from the client.
3. Add the minimal row signal allowed_actions.direct_edit to the server-projected worker-directory row. Admin/BoD retain current behavior; a Team Leader gets true only for a row in the one current team they manage and only when the row is in an editable state. Out-of-team rows must never receive a direct-edit CTA. This flag is a display hint, not authority; the mutation RPC rechecks every request.
4. Add a team worker-directory audience using the existing current team Resource Scope so a Team Leader can find team rows. Do not infer this from client role/title or reuse all scope. Keep other directory scopes and output fields unchanged.
5. The database/RPC is the final authority on every request. Use one strict canonical Team Leader current-team predicate across directory projection, row read, request audience/decision, and direct edit. It must bind actor identity and require team_manager_assign, one active current team scope, current verified account/recruiter link, active HRP recruiter/current membership, and one current assignment. Use current-state is_current values, not effective-date authorization.
6. The general read helper direct_entry_assert_team_leader_read_authority has a catalog-operator bypass. Preserve that behavior only for its existing read use. Never treat that branch as proof of Team Leader authority or use it to project direct_edit=true or authorize the Team Leader mutation path.
7. Permit changes only while the row remains inside that same currently managed team. Check both the existing row and the proposed row. In particular, changing recruiter_id, project_id, provider, or another ownership-affecting field must not move the row outside the actor's current team scope. Do not grant all scope or add a new capability/table/policy engine.
8. Preserve strict patch allowlists, field validation, row locks, expected-version OCC, idempotency, history/revision, audit, and existing state restrictions. DRAFT and SUBMITTED are currently accepted; REVIEW and other locked states remain locked.
9. A direct edit must not approve, withdraw, delete, or silently rewrite pending change requests. A request whose expected version is stale must fail without overwriting the direct edit.
10. Keep current status values UNCONFIRMED, ON, OFF. For OFF, the business field leave_reason is mandatory, nonblank, and length-checked in every path. It is not an optional action reason.
11. Admin/BoD behavior remains as implemented. This change adds only the existing team-scoped Team Leader path.

## 3. Team change-request review

- Reuse direct_entry_team_leader_request_team, direct_entry_change_request_audience, direct_entry_read_change_request, direct_entry_decide_change_request, the existing queue, and the server-returned can_decide flag.
- List and detail must derive from the same server audience. Every item in a multi-entry request must be in the same currently authorized team; otherwise deny the whole request.
- The strict Team Leader current-team predicate must be shared with row-level worker-directory projection and direct edit. The catalog-operator bypass in the general read helper cannot be inherited as Team Leader authority.
- Staff may propose; the Team Leader for that team may read and decide. Staff cannot decide their own request. A Team Leader may see their own proposal only where the existing proposer rules permit it; that does not grant self-approval. Use direct edit for self-service changes.
- Revocation, disablement, ambiguity, inactive team/recruiter, or a mismatched current assignment must deny the next request. Do not infer authority from a role label or frontend state.
- The current entry projection is required for before/after review. Keep existing projection and document/payment/PII guards; do not widen fields to make the dialog render.
- For WORK_STATUS, render both the current status and proposed status from the existing safe projection, then use the existing server-authorized decision flow. Do not rewrite the reviewer or widen DOCUMENT/ENTRY_VOID policy as a workaround.
- Every load path must reach a terminal UI state: loading, reviewable/read-only, stale, unsupported, or explicit error. Handle 403, 404, 500, invalid payload, and failed entry projections without a stuck loading dialog.
- Current source distinction: database target_kind values are ENTRY_FIELD, PAYMENT, WORK_STATUS, DOCUMENT, and ENTRY_VOID. WORKER is a Worker Operations proposal-form label, not a persisted target_kind; the form maps worker fields to ENTRY_FIELD. Do not introduce a WORKER database kind. Confirm all supported kinds remain safely projectable before enabling decisions.
- ENTRY_VOID already has a one-item rule and explicit reviewer policy in the existing migration. Preserve that exact policy and guard; do not broaden it as a side effect of ordinary worker-change review.

## 4. Action reasons

### A. Optional action reason

All user-entered action justifications may be absent, null, or blank and must normalize to NULL at the nearest trusted boundary. Examples found in source include:

- create/update, direct edit, change-request submission and decision;
- payment/document operations and document edits that currently ask for an action reason;
- draft status action reason, distinct from the leave reason;
- worker export;
- account access grant/revoke and administrative/catalog operations for personnel, teams, memberships, projects, vendors, labor types, and Team Leaders.

The specific modules include privileged-edit-api.ts, change-request-contract.ts/change-request-api.ts, draft-employment-status-api.ts, payment-api.ts, document-api.ts, worker-export-contract.ts, app-user-access-contract.ts, and the catalog API modules. T1-C must finish the call-site inventory, including UI forms and SQL RPCs, before changing the contract.

When a nonblank action reason is supplied, keep its existing type and per-field length limits. Preserve old clients where practical. Do not replace an omitted reason with a made-up string or a hard-coded fallback.

### B. Required business reason

The currently verified business invariant is the leave reason when employment status is OFF:

- privileged-edit patch employment_status.leave_reason;
- a WORK_STATUS proposal leave_reason when status is OFF;
- initial worker profile employment.leave_reason_text when initial status is OFF.

Keep these nonblank and length-validated. Reject leave fields for non-OFF statuses wherever current contracts do so. T0 found no other reason field proven to be a domain requirement; a NOT NULL reason_id constraint alone is a storage constraint, not evidence of a business rule.

### Persistence and audit

- Keep the audit/revision/event row even when no action reason is entered. Preserve actor, action, time, before/after, version, and idempotency.
- direct_entry_reason currently rejects null/blank and inserts into direct_entry_restricted_reasons. Several revision/event/catalog tables have NOT NULL reason_id; approved/rejected requests also have a check requiring decision_reason_id. The database contract must support genuine absence with minimal forward-only migration(s), not a placeholder row. T1-A may split independent SQL pieces into two migrations when that reduces risk; A owns both and orders them explicitly.
- Normalize before computing request hashes so omitted, null, and blank optional reasons have one canonical representation. Keep meaningful nonblank text in the restricted-reason path.
- Existing server-authored labels such as “Draft row creation” are not user input. Do not use them to pretend a user supplied an optional reason. T1-C must classify each such call and T1-A must preserve or remove it only as an accurately named audit action, never as a validation bypass.

## 5. Security invariants

- No new role manager, policy engine, capability, broad scope, direct table access, service-role shortcut, or authorization table.
- Preserve S0 function ACL allowlist, RLS, owner, SECURITY DEFINER search paths, and service-role boundary.
- Keep decision authority in server/RPC checks; UI hints only reflect server-projected authority.
- Keep export scope policy, 10,000-row limit, reason field optionality only, audit, validation, and spreadsheet-safety protections.
- No production reads/writes, migration application, or deployment.
