### 2.4 Revision snapshot redaction (R1 — `20261005030000_…_s03b3_r1_change_policy_closure.sql:556–613`)

After migration #32 (S03B3-R1), `direct_entry_entry_snapshot` no longer writes raw PII to `direct_entry_revisions.after_snapshot`. Specifically:

- `worker_details` is reduced to `{ present: true }` (no `display_name`, no `national_id`, no `dob`, no `address`, no `phone`).
- `payment` is reduced to `{ state, version }` (no `account_number`, no `bank_id`, no `account_holder_name`).
- `employment_status` is reduced to `{ status, effective_date, version }` (no `leave_date`, no `leave_reason_text`).
- `documents` is reduced (no `idempotency_key`, no `checksum_sha256`, no `size_bytes`, no `mime_type`).

This means **revisions written after #32 are PII-safe at the source**. Revisions written **before** #32 (i.e. between #1 and #31) still contain raw PII in `before_snapshot/after_snapshot` and are NOT auto-redacted; they remain in the DB unless an explicit purge is run. This is a known gap and is listed in §6 (Gap analysis).

## 3. Canonical field matrix — full worker profile (T0-locked superset)

The following is the **target** matrix after the next T1B migration. It maps every column from the existing "mẫu hiện hành" and the "hồ sơ đầy đủ mong muốn" to either a **persisted** location, a **derived** location, a **server-resolved** location, or **OUTSIDE_EXCEL** (document link, not a paste column).

Status taxonomy:
- `SUPPORTED` — already in DB schema, contract, and projection.
- `PARTIAL` — partially modeled (e.g. legacy field exists, but new field is missing).
- `MISSING` — no schema/contract today; required by the superset.
- `DERIVED` — not persisted; computed at read or render time.
- `OUTSIDE_EXCEL` — lives outside the paste payload (e.g. CCCD photo is a document).

### 5.1 Atomic full-profile batch (T0-locked 2026-10-04)

D16: initial `leave_date` / `leave_reason_text` is importable **for historical records only**, atomic with the batch, and requires `employment_status.apply` on the actor. New records continue via the existing post-submission workflow (no batch-time status event).

When a single batch contains entry + PII + payment + status items:

1. **Phase 1**: server runs the new `direct_entry_create_full_profile_batch` RPC (T1B design — see §11) inside a single transaction. The entry + `worker_details` + (optional) `payment` + (optional, historical only) initial status event are all committed together.
2. **Phase 2 (if payment is in the row)**: `direct_entry_update_payment` is called for the same entry, in the same transaction. If `payment_state` is `provided`, the four payment fields must be present and valid.
3. **Phase 3 (if historical status is in the row)**: a new `direct_entry_apply_initial_status_event` RPC appends the `UNCONFIRMED` / `ON` / `OFF` event for the entry, in the same transaction. `OFF` requires `leave_date = effective_date` and non-empty `leave_reason_text` (≤ 4000 chars per D13). Requires `employment_status.apply` on the actor (D16).
4. **Phase 4 (if any)**: document reserve / finalize is **never** part of the batch — it is its own flow with its own idempotency key (T0 D10: no JSON-with-bytes).

If **any** of Phase 1/2/3 fails, the entire batch is rolled back (single transaction). This is stricter than the current `direct_entry_create_batch` which only handles entry creation.

The **capability union** check must run before Phase 1 (D18: no new capability; reuse existing 21):

- `entry_create` + `submission_create` (always; today's `direct_entry_create_batch` already requires both — `20261002170000_…:1263–1267`).
- If any row has payment, `payment_view` + `payment_edit` are required (today's `direct_entry_apply_change_item` PAYMENT branch already enforces this — `20261005030000_…:241–246`).
- If any row has historical status event, `employment_status.apply` is required (D16).
- `pii_view` is required to **read back** the full PII; without it, the read projection returns `{ present: true }` for `worker_details` (D18: no new capability; reuse the existing `pii_view`).

If the union is incomplete for any row, the entire batch is rejected (no partial commit). This mirrors the S03B3-R1 all-or-nothing pattern for change-request decisions (`20261005030000_…:401`).

### 5.2 Out-of-scope capability decisions (D18)

D18 (T0 2026-10-04) confirms the 21 existing capabilities are sufficient for the full superset. **No new capability is created** in P1.6. If a future superset needs more granular control (e.g. "can edit `general_note` but not `address`"), the T0 contract says it must be decided at T0 level, not by T1C.

T1B reuses:

- `pii_view` as the umbrella PII read capability (already exists).
- `pii_export` for the future full-profile Excel export (D19: capability stays in the grants table, **no RPC is added in P1.6**, deferred to P3).
- `payment_view` + `payment_edit` for the payment fields (already in `direct_entry_apply_change_item` PAYMENT branch, `20261005030000_…:241–246`).
- `employment_status.apply` for the historical batch-time `OFF` event (D16).
- `document_upload` + `document_view` for documents (existing).
- `change_review` + per-item union for change-request approval (existing S03B3-R1 pattern).

## 7. Search / document linkage design (docs only, no implementation)

The brief says: "Khi truy cập web và tìm tên NLĐ thì thấy hồ sơ và ảnh CCCD."

This section is a design proposal for the future search feature. It is **not** implemented in this task.

### 7.1 Search keys (D22, A2)

| Key | Type | Storage | Index | Notes |
| --- | --- | --- | --- | --- |
| `employee_code` | exact text | `direct_entries.employee_code` | unique btree (already exists) | Year-prefix can be used for prefix query |
| `lower(employee_code)` | exact text | derived | btree on `lower(employee_code)` for case-insensitive search | Add in T1B |
| `national_id` | exact text (D15: 9 or 12 digits, leading-zero preserved) | `direct_entries.worker_details->'national_id'->>'value'` | partial btree on the JSONB path where `state = 'provided'` | Exact-match after `trim` outer whitespace; no checksum, no fuzzy |
| `display_name` (A2) | exact text (after lower + trim) | `direct_entries.worker_details->>'display_name'` (plain string, **NOT** `worker_details->'display_name'->>'value'`) | btree on `lower(worker_details->>'display_name') text_pattern_ops` | Add in T1B; no diacritic-stripping, no fuzzy |
| `phone` | NOT a search key in P1.6 | n/a | n/a | `phone` format normalization is deferred (D22 does not cover phone) |

**A2 correction (vs. T1C first draft)**: the first audit draft wrote `lower(worker_details->'display_name'->>'value')`. That was wrong — `display_name` is stored as a plain JSONB string in `direct_entries.worker_details`, not wrapped in `OptionalValue`. The correct index expression is **`lower(worker_details->>'display_name')`**.

**T0 D9 enforcement**: never use `display_name` / `national_id` / `phone` in:
- R2 storage key (already enforced by `STORAGE_KEY` regex in `direct_entry_document_versions`).
- URL path of any signed download.
- Filename of any browser download.
- Log / error / audit message.
- Idempotency key.

### 7.2 Search query design

- **Capability**: `pii_view` is required to search across PII fields; `entry_own/team/admin` for scope; `audit_view` if the search is to be logged in audit.
- **Pagination**: keyset pagination (same pattern as `direct_entry_list_change_requests` line 142–250). Default `page_size=20`, max `page_size=50`.
- **Anti-enumeration (D22)**: `no-match` and `out-of-scope` return the **same response shape** to prevent enumeration. Concretely: both return the P0002 pattern (`{ code: "NOT_FOUND", message: "..." }`) mirroring `direct_entry_read_own_submission` line 188–192. No "matches but masked" hits (that would leak existence). Optional capability `pii_view` is independent of the existence of a row.
- **Masking**: response includes the actor-relevant fields:
  - `entry_id`, `employee_code`, `first_work_date` (non-PII): always FULL.
  - `worker_display_name`: FULL (with `pii_view`).
  - `national_id`, `address`, `phone`: only if `pii_view`; otherwise PRESENCE_ONLY (`{ present: true }`).
  - `documents` summary: only `{ document_id, document_type, version, upload_status, validation_status, scan_status }` (no `checksum_sha256`, no `idempotency_key`); only if `document_view`.

### 7.3 Document lookup chain

After a search returns an `entry_id`, the UI must:

1. Call `GET /api/direct-entry/entries/{entryId}` (or the new search endpoint that returns a slim entry record).
2. The UI then iterates the `documents` array and for each `CCCD_FRONT` / `CCCD_BACK` / `EMPLOYMENT_CONTRACT`:
   - Calls `GET /api/direct-entry/entries/{entryId}/documents/{documentId}/download` to get the signed URL.
   - The server checks `document_view` capability + scope + that document is `READY+VALIDATED+(CLEAN|NOT_REQUIRED)` (per R2A line 437–441).
3. The signed URL is short-lived (TTL `DOCUMENT_DOWNLOAD_URL_TTL_SECONDS = 120` from `document-r2-contract.ts`).
4. The signed URL is **never** written to:
   - The search response (T0 D9: response must not contain signed URL).
   - localStorage / sessionStorage (T0 D9).
   - Log / error (T0 D9).
5. The UI passes the signed URL directly to a `<img>` / `<object>` tag and forgets it after the request completes.

### 7.4 Indices required (T1B)

- `create index direct_entries_employee_code_lower_idx on public.direct_entries (lower(employee_code));`
- `create index direct_entries_worker_display_name_lower_idx on public.direct_entries (lower(worker_details->'display_name'->>'value')) where worker_details ? 'display_name';` — **partial index** because `worker_details->>'display_name'` is required but `state` may not be `provided`.
- `create index direct_entries_worker_national_id_idx on public.direct_entries ((worker_details->'national_id'->>'value')) where worker_details->'national_id'->>'state' = 'provided';`
- `create index direct_entries_worker_phone_idx on public.direct_entries ((worker_details->'phone'->>'value')) where worker_details->'phone'->>'state' = 'provided';`

**No** full-text search index is recommended at this stage. The search is exact-match by design (T0 D9: anti-enumeration).

### 7.5 What this design does NOT do

- It does **not** implement search. It only documents the contract.
- It does **not** add a new RPC. The existing `direct_entry_read_projection` is the entry-point; a new search endpoint can be added in a later task.
- It does **not** change the existing PII redaction rules.

### 8.3 Empty-cell states

| State | Meaning | Server action |
| --- | --- | --- |
| `omitted` | column not provided in source | treat as not set; do not error |
| `unknown` | column provided but unparseable (e.g. "?" or "N/A") | mark row as `issues += { code: "WORKER_FIELD_UNKNOWN", path }`; do not store value |
| `intentionally_blank` | column provided as empty string | treat as not set; do not error |
| `provided` | column has a real value | validate per vocabulary; store in DB |

### 8.5 Server derivation (T0 D6)

The server **must not** accept from the paste:
- `provider_type` (D1): server resolves from `recruiter_provider_memberships` matching `first_work_date`.
- `team` (D2): server resolves from `recruiter_team_memberships` matching `first_work_date`.
- `age` (A3): never read or accept; computed in UI from `date_of_birth` if provided.
- `month` (A2): never read; computed in UI from `first_work_date`.

If any of these fields appear in the paste header, the server returns `CLIENT_AUTHORITY_FIELD_FORBIDDEN` (mirroring `direct_entry_contains_authority` line 1195–1219 of the foundation migration).

### 8.6 Anti-fuzz / exact-match policy

Following the T1A R2 `excel-paste-import.ts` precedent:

- Catalog match: **exact ID OR exact display name** (after `trim().toLowerCase()`), no fuzzy, no prefix, no substring.
- Result codes: `EMPTY` / `MISSING` / `AMBIGUOUS` per the existing `CatalogMatch` type.

### 8.7 Numbers, dates, leading zeros

- `national_id`, `phone`, `account_number` are **strings** in the protocol. The server does not coerce. The Excel parser is responsible for **not** coercing leading zeros (this is why T1A R2 uses `text` rather than `number`; same pattern must apply).
- Dates: `YYYY-MM-DD` only. If Excel sends a serial number, the parser converts it before sending to the server. The server does not parse Excel serials.
- No Excel formula evaluation (`=A1+B1` must be left as a string and reported as `unknown`).

### 8.8 Unknown header / unknown value

- **Unknown header** (not in vocabulary): row is rejected with `code: "PASTE_HEADER_UNKNOWN"`; the entire batch is rejected (no partial commit).
- **Unknown value** (cell not parseable per vocabulary): row is marked with `issues += { code: "PASTE_VALUE_UNKNOWN", path: "..." }`. The server still processes the row with the cell mapped to `unknown` (or skips that cell, depending on T0 decision).
- **Missing required header**: `code: "PASTE_HEADER_REQUIRED"`; entire batch rejected.
- **Missing required value in a row**: row marked with `code: "PASTE_VALUE_REQUIRED"`; row is rejected (not stored), but other rows in the batch proceed if T0 allows partial commit, or the entire batch is rejected (recommended).

### 8.9 Body limit and idempotency

- `MAX_BODY_BYTES` for the new RPC: at least **128 KiB** (the current 64 KiB is borderline for 100 rows of full profile).
- One idempotency key per batch (mirroring T1A R2 `paste-batch-save.ts`).
- Server returns `IDEMPOTENCY_CONFLICT` (409) if the same key is replayed with a different row payload, or `200` with the same projection if the same key is replayed with the same payload (existing pattern in `direct_entry_idempotency_begin` line 818–850 of foundation).

### 8.10 Single superset template (A1 / D4, T0-locked 2026-10-04)

The full-profile contract is a **single header-based superset template** with optional columns. There is **no two-template split**, and there is **no second parser**. The T1C first draft called this a "recommendation, not T0-locked"; on 2026-10-04 T0 locked it as A1 / D4. Concretely:

- Header-based parser reads the column headers from the first row; missing columns are accepted (D4: union of two Excel templates, not a fixed 5/6-column import).
- Optional columns are encoded as `OptionalValue` (`{ state: omitted | unknown | provided, value }`) per T1A R2 convention; absent cells become `state = omitted`.
- Single projection RPC (`direct_entry_read_projection`) and a single list RPC (`direct_entry_list_own_drafts`) cover both minimal and full payloads.
- The minimal required profile (T01 acceptance test) is "all required columns populated, all optional columns absent" — same parser, same projection.

### 8.11 Document bytes — never in paste

- Document upload is its own flow: `POST /api/direct-entry/entries/{entryId}/documents` → `PUT` to R2 → `POST /finalize`.
- The paste payload never carries image bytes. The UI lists document status as a per-row cell (UNSAVED / 0/2 / 1/2 / 2/2) using the T1A R2 `cccd-status.ts` pattern.
- T0 D10: "Không được đề xuất nhét toàn bộ profile vào một JSON không kiểm soát" — documents are not in JSON, they are in R2.

### 8.12 Response shape

On success, the server returns:

```json
{
  "ok": true,
  "submission_id": "...",
  "submission_version": 1,
  "state": "DRAFT",
  "entry_ids": ["...", "..."],
  "rows": [
    {
      "entry_id": "...",
      "entry_version": 1,
      "warnings": []
    }
  ]
}
```

**`warnings[]` is empty for now** (T0 D10: no surprise fields). Future warning codes (e.g. `DOB_IN_FUTURE_REJECTED`) would be added with T0 approval.

The response **must not** contain: `national_id`, `phone`, `address`, `account_number`, `account_holder_name`, `national_id_issued_*`, `general_note`, `leave_reason_text`, `checksum_sha256`, `storage_key`, `idempotency_key` for documents, signed URL, bucket name, R2 account ID.

## Appendix B — Glossary

- **App user** — `direct_entry_app_users` row (UUID, `auth_subject`, `enabled`).
- **Actor** — runtime subject: `{ auth_subject, app_user_id, enabled, capabilities[], scopes[], recruiter_links[] }` resolved by `direct_entry_resolve_actor_context`.
- **Capability** — grant row in `direct_entry_capability_grants`; 21 values today.
- **Scope grant** — row in `direct_entry_scope_grants`; `own` / `team` / `all` with `valid_from` / `valid_to`.
- **Submission** — `direct_entry_submissions` row; state `DRAFT` / `REVIEW` / `SUBMITTED`.
- **Entry** — `direct_entries` row; **always** part of one submission; one `employee_code`; one `worker_details` JSONB; one `team_id` (server-derived).
- **Candidate** — `direct_entry_candidates` row (1:1 with entry; existence row; no PII).
- **Document** — `direct_entry_document_versions` row + `direct_entry_document_objects` row (R2A) + `direct_entry_document_events` rows (lifecycle).
- **Revision** — `direct_entry_revisions` row; `before_snapshot` / `after_snapshot` (redacted post-#32).
- **Audit event** — `direct_entry_audit_events` row; `changed_fields` is `text[]` of field NAMES (never raw values); `resource_ref` is UUID only.
- **Change request** — `direct_entry_change_requests` + `direct_entry_change_request_items` (target kind `ENTRY_FIELD` / `PAYMENT` / `WORK_STATUS`; `DOCUMENT` blocked at DB).
- **Reason** — `direct_entry_restricted_reasons.reason_text` (1–4000 chars); always linked to a revision/audit via `reason_id`; never inlined.
