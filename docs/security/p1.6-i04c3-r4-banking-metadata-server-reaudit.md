## 2. Migration #37 review (20 verification points)

### 2.1 Byte-identical with #1–#36

- Migration #37 file name and hash match what is in `b6569b49..42abd668`.
- PGlite **applies all 37 migrations from scratch** with no errors
  (`migration #37 accepts partial banking metadata without a catalog and preserves
  redaction` test passes). All earlier tests in the S01 suite still pass against
  the same 37-migration database.
- `pnpm run db:migrate -- --dry-run` reports **36 applied / #37 pending / 0 mismatch**
  on the shared DB. `pnpm run db:migrate -- --offline` reports all 37 valid.

### 2.2 #37 forward-only

- Only DDL changes: one `add column` and one `drop constraint if exists … add constraint`.
- Three function bodies replaced with `create or replace function …`:
  `direct_entry_validate_payment`, `direct_entry_read_projection`,
  `direct_entry_create_full_profile_batch`. **No new function created, no
  function dropped, no function renamed.**
- Two function `revoke … from public, anon, authenticated, service_role` followed
  by `grant execute … to service_role` for the two replaced functions —
  identical pattern to the original ACLs.
- The trigger `direct_entry_payment_active_bank` (defined in foundation) is
  **not re-issued**; it remains bound to the new function body via
  `create or replace function`. Trigger is preserved.

### 2.3 No data rewrite / no backfill / no catalog seed

- No `UPDATE` against `direct_entry_payments` or `direct_entry_banks`.
- No `INSERT INTO direct_entry_banks` (no bank row seed).
- No `DELETE` against any existing table.
- The migration sets `bank_name` column to `null` by default (no `DEFAULT` clause
  → existing rows get `bank_name = null` via PostgreSQL's standard `ADD COLUMN`
  semantics, which is metadata-only and does not rewrite the row).

### 2.4 Trigger/FK preservation

- `bank_id` column unchanged (still `text`, still
  `references public.direct_entry_banks(bank_id) on delete restrict` from
  foundation line 237).
- The new constraint `direct_entry_payments_metadata_check` accepts
  `(state = 'provided' AND (account_number OR bank_name OR account_holder_name)
  is not null AND (each non-null field has bound 1..64/1..256/1..256 and no
  control chars)) OR (state <> 'provided' AND all metadata columns null)`.
  This is **strictly a relaxation**: the old check required
  `state='provided' → (account_number AND bank_id AND account_holder_name)`;
  the new check only requires at least one text field. Legacy rows with
  `state='provided' + 3 fields` continue to satisfy the new check.
- The new trigger function:
  - Trims ASCII + Unicode whitespace (NBSP, ideographic space, ZWSP, BOM, etc.) on
    `account_number / bank_name / account_holder_name` and converts empty to NULL.
  - Validates active bank only when `bank_id is not null` — `if new.bank_id is not
    null and not exists … active → raise`. **No active-bank check when
    `bank_id` is null**, which is exactly the spec ("banks=0 must not block text
    metadata").
- `direct_entry_update_payment` (legacy payment editor) is **not redefined** —
  legacy write path is unchanged. Because the legacy contract requires all three
  fields when `state='provided'`, existing legacy callers continue to satisfy
  the new check.

### 2.5 RLS / FORCE RLS / no broad grants

- Migration #37 does not `enable row level security` on any new table (it does
  not create any new table). It does not `revoke` or `grant` on any table. The
  existing `direct_entry_payments` RLS policy is untouched.
- The migration does `revoke all on function … from public, anon, authenticated,
  service_role` followed by `grant execute … to service_role` for the two
  replaced RPCs — exactly the pattern required for boundary RPCs.

### 2.6 No SQL injection / no dynamic SQL

- The new SQL uses only static parameter binding via `jsonb` accessors
  (`v_row->'payment'->>'state'`, `length(btrim(v_account_number))`, etc.).
- No `execute` of dynamic SQL. No `format` of user input. No `USING` of unsafe
  expressions. No extension / DDL inside function bodies.

### 2.7 Atomicity / OCC / idempotency

- `direct_entry_create_full_profile_batch` keeps the existing per-iteration
  `v_codes / v_national_ids` duplicate detection.
- `direct_entry_idempotency_begin/finish` calls unchanged.

- The new test also asserts that `direct_entry_update_payment` with a stale

`parseFullProfilePayload` (TypeScript) and consumed by
`direct_entry_create_full_profile_batch` (SQL). I exercised each case from both
sides:

| Case | TS verdict | SQL verdict | Match |
| --- | --- | --- | --- |
| `payment` key absent | DTO `payment: null`; no error | `v_row ? 'payment'` false; no insert | ✓ |
| `payment: null` (literal) | **BATCH_INVALID** `rows[0].payment` | `nullif(..., 'null'::jsonb)` ⇒ no insert; no error | ✗ TS stricter (defensive over-rejection) |
| `payment: {state:"omitted"}` | DTO `{state:"omitted"}` | `v_payment_state := 'omitted'`; no insert | ✓ |
| `payment: {state:"unknown"}` | DTO `{state:"unknown"}` | `v_payment_state := 'unknown'`; no insert | ✓ |
| `payment: {state:"intentionally_blank"}` | DTO `{state:"intentionally_blank"}` | `v_payment_state := 'intentionally_blank'`; no insert | ✓ |
| `payment: {state:"omitted", bank_name:"X"}` | **PAYMENT_DETAILS_INVALID** | `v_payment_state <> 'provided'` + `v_bank_name` non-null ⇒ `PAYMENT_DETAILS_INVALID` | ✓ |
| `payment: {state:"unknown", account_number:"X"}` | **PAYMENT_DETAILS_INVALID** | Same logic; non-null text with non-`provided` state ⇒ rejected | ✓ |
| `payment: {state:"unknown", bank_id:"<active>"}` | **PAYMENT_DETAILS_INVALID** | Rejected at `v_payment_state <> 'provided'` branch | ✓ |
| `payment: {state:"provided", account_number:"00001234"}` | DTO `{state:"provided", account_number:"00001234"}` | Insert with leading zero preserved | ✓ |
| `payment: {state:"provided", bank_name:"Ngân hàng Á Châu"}` | DTO `{state:"provided", bank_name:"Ngân hàng Á Châu"}` | Insert trimmed + btrim'd; Unicode preserved | ✓ |
| `payment: {state:"provided", account_holder_name:"<holder>"}` | DTO `{state:"provided", account_holder_name:"<holder>"}` | Insert | ✓ |
| `payment: {state:"provided", account_number, bank_name, account_holder_name}` | DTO with all 3 | Insert; constraint OK | ✓ |
| `payment: {state:"provided", bank_id:"<active>", account_number, account_holder_name}` | DTO legacy 3-field | Insert; active bank check OK | ✓ |
| `payment: {state:"provided", bank_id:"<inactive>"}` | bank_id normalizes to null ⇒ no metadata ⇒ **PAYMENT_DETAILS_INVALID** | `BANK_NOT_ACTIVE` | ≈ TS gives more generic code; SQL more specific. Both reject. |
| `payment: {state:"provided", bank_id:"<active>"}` (no text) | bank_id normalized ⇒ no metadata ⇒ **PAYMENT_DETAILS_INVALID** | `v_payment_state := 'omitted'` coerced (line 487–489) | ✗ divergent — TS rejects, SQL downgrades to omitted |
| `payment: {state:"provided", account_number:" \t"}` | normalises to null ⇒ no metadata ⇒ coerce to `{state:"omitted"}` | Trigger `nullif(btrim(...))` ⇒ NULL; no insert | ✓ |
| `payment: {state:"provided", account_number:"  00001234  "}` | DTO `{state:"provided", account_number:"00001234"}` | Trigger btrim; leading zero preserved | ✓ |
| `payment: {state:"provided", bank_name:"a".repeat(257)}` | **PAYMENT_DETAILS_INVALID** | `length(btrim(bank_name))` > 256 ⇒ `PAYMENT_DETAILS_INVALID` | ✓ |
| `payment: {state:"provided", bank_name:"bad\u0000name"}` | **PAYMENT_DETAILS_INVALID** (`/[\u0000-\u001f\u007f]/` rejects) | `bank_name ~ '[[:cntrl:]]'` ⇒ `PAYMENT_DETAILS_INVALID` | ✓ |
| `payment: {state:"provided", bank_id:"not in catalog"}` | bank_id normalizes to null ⇒ coerce to `{state:"omitted"}`? (no — `bankIdValue != null` triggers PAYMENT_DETAILS_INVALID) | `BANK_NOT_ACTIVE` | ≈ both reject; different code names |
| `payment: {state:"provided", unknown:true}` | **BATCH_INVALID** (TS rejects row first) | SQL `v_row - array[…] <> '{}'` ⇒ `BATCH_INVALID` | ✓ |
| `payment: {state:"provided", bank_name:5}` | **PAYMENT_DETAILS_INVALID** (typeof check) | `jsonb_typeof` check ⇒ `PAYMENT_DETAILS_INVALID` | ✓ |
| `payment: {state:"FOO"}` | **BATCH_INVALID** | `v_payment_state not in (...)` ⇒ `PAYMENT_DETAILS_INVALID` | ≈ both reject; SQL code is more specific |

**Findings on parity**:

- **(F-01, LOW)** TS rejects `payment: null` literally; SQL treats it as omitted.
  This is **defensive over-rejection** at the TS layer. The repository / API
  surface never produces a row with `payment: null`; the row-contract allows
  `payment` to be absent (`hasOnlyKeys` requires subset, not exact match). No
  real client call site sends `payment: null` per the API design. **No impact
  on happy path; logged as a LOW documentation gap.**

- **(F-02, LOW)** `payment: {state:"provided", bank_id:"<active>"}` (no text
  fields): TS rejects with `PAYMENT_DETAILS_INVALID`; SQL coerces `state` to
  `'omitted'` (line 487–489 of #37). Both reject the user's intent of
  "provided metadata without text", but TS gives a 400 with a clearer
  contract code while SQL silently treats it as no-payment. **Not a security
  issue** (no data leaks), and **not a semantic mismatch** in the sense of
  the brief — the user receives an error in both paths. Documented as a LOW
  follow-up: the TS contract could mirror SQL by also coercing to
  `{state:"omitted"}`. Out of scope for this server audit; the SQL behaviour
  is correct and TS defensive behaviour is acceptable.

All other cases agree.

## 6. banks=0 evidence

The PGlite test explicitly exercises `banks=0`:

```js
await db.exec("delete from public.direct_entry_banks;");
assert.equal(await count(db, "direct_entry_banks"), 0);
const result = await rpc(db, [
  row(600),                                                     // no payment metadata
  row(601, { payment: { state: "provided", bank_name: "..." } }), // bank_name only
  row(602, { payment: { state: "provided", account_number: "..." } }), // account only
  row(603, { payment: { state: "provided", account_holder_name: "..." } }), // holder only
  row(604, { payment: { state: "provided", account_number, bank_name, account_holder_name } }), // all three
], "91600000-0000-4000-8000-000000000601");
assert.equal(result.entry_ids.length, 5);
assert.equal(await count(db, "direct_entry_payments"), 4);
```

The row `hrp-2020-000600` (no payment key) is accepted with no payment row;
rows `hrp-2020-000601..000604` are accepted with one payment row each. The
expected persisted shape is asserted row-by-row including leading-zero
preservation on `00001234` and trimmed Vietnamese diacritics
(`"Ngân hàng Á Châu"` from `"\u00a0 Ngân hàng Á Châu \u3000"`).

**Verdict**: banks=0 is no longer a blocker for the full-profile batch.
