## TL;DR

T1A has confirmed a **BLOCKER** in source `b5162b24`. The metadata edit
path is **destructive-by-default full-replacement** with no safe KEEP
operation: an actor who holds `payment_edit` but not `payment_view`
sees only a masked `account_number` from the read projection, and the
contract requires them to send all three text fields explicitly. The
only way to "preserve" the canonical STK is to either (1) send the
masked value back (which the server would persist, corrupting the row)
or (2) send `null` (which would clear the STK). Both outcomes are
destructive. Migration #38 is still pending on the shared DB, so it can
be amended forward-only without re-integration cost.

The previous audit verdict (`READY_FOR_S04_AND_MIGRATION_38_INTEGRATION`)
is **revoked**. Status is now `BLOCKED_UNSAFE_FULL_REPLACEMENT_WITH_MASKED_ACCOUNT`.

The fix path is **T0-locked**: per-field explicit `KEEP / SET / CLEAR`
operations on `{account_number, bank_name, account_holder_name}`. The
repair must:

1. Make KEEP an explicit operation (not inferred from key omission or
   `null`).
2. Reject sending a value with KEEP or CLEAR.
3. Server-side read of the current value when KEEP is requested for
   `account_number`; never return the raw STK to the client.
4. SET / CLEAR `bank_name` must null `bank_id`; KEEP `bank_name` must
   preserve current `bank_id`.
5. All-KEEP must be rejected as no-op (no increment, no audit).
6. OCC / idempotency fingerprint must include the operation map and the
   SET values.
7. Audit / revision remain free of raw values.
8. Capability model is unchanged: `payment_view / payment_edit`
   compatibility guards only; do **not** force `payment_view` for
   `payment_edit`-only actors (server-side read inside trusted SQL
   transaction is the only acceptable read path).

The T1A UI branch is still clean (no workaround), and T1B source
`b5162b24` has not been touched. Migration #38 is still pending on the
shared DB; the apply owner can amend the migration forward-only before
`pnpm run db:migrate -- --apply-38`.

## 1. Audit questions answered with concrete source anchors

### Q1. Does the current API have any safe KEEP path?

**Answer: NO.**

`projectRequest` in `src/lib/direct-entry/payment-api.ts` (lines 60–89)
only accepts two body shapes:

- `{ expected_entry_version, expected_payment_version, reason, payment }`
  where `payment` is `{ state, account_number, bank_id, account_holder_name }`
  (legacy full-replacement).
- `{ expected_entry_version, expected_payment_version, reason,
  account_metadata }` where `account_metadata` is exactly
  `{ account_number, bank_name, account_holder_name }` (metadata
  full-replacement).

Both shapes are **full-replacement**: every key in the nested object is
assigned to its column in the SQL `insert on conflict do update`
statement. There is no `{ op: "keep" }` sentinel. There is no field
omission that means "don't touch this field". The only way to indicate
"don't touch" is to send the **current** value, but the read projection
never returns the raw STK when `payment_view` is not granted
(`direct_entry_read_projection` replaced in #37, line 130–138 of
`20261005070000_p1_6_i04c3_r4_banking_metadata.sql`):

```sql
'payment', (
  select case when v_payment then jsonb_build_object(
    'state', p.state, 'account_number', p.account_number, 'bank_id', p.bank_id,
    'bank_name', p.bank_name, 'account_holder_name', p.account_holder_name,
    'version', p.version
  ) else jsonb_build_object(
    'state', p.state,
    'account_number', case when p.account_number is null then null
      else repeat('•', greatest(length(p.account_number) - 4, 0)) ||
        right(p.account_number, 4) end,
    'version', p.version
  ) end
    from public.direct_entry_payments p
   where p.entry_id = p_entry_id
)
```

`v_payment = exists (… capability = 'payment_view' …)` from
`direct_entry_capability_grants`. When the actor has only
`payment_edit`, `v_payment` is `false`, the masked branch returns
only `{state, account_number (masked), version}`. **No `bank_name`,
no `bank_id`, no `account_holder_name` in the masked branch.**

Therefore an actor with `payment_edit` only cannot read the raw STK
to safely re-send it. They have no safe KEEP path.

### Q2. Can a masked value be persisted as `account_number`?

**Answer: YES.**

`projectOptionalText` in `payment-contract.ts` (lines 75–82):

```ts
function projectOptionalText(value: unknown, maxLength: number): string | null | undefined {
  if (value === null) return null;
  if (typeof value !== "string") return undefined;
  const normalized = value.trim();
  if (normalized.length === 0) return null;
  const length = Array.from(normalized).length;
  if (length > maxLength || /[\u0000-\u001f\u007f-\u009f]/.test(normalized)) return undefined;
  return normalized;
}
```

The only rejections are: not a string (returns `undefined`), empty after
trim (returns `null`), length > 64 (returns `undefined`), or
control characters in `[\u0000-\u001f\u007f-\u009f]`. A masked string
like `"••••••••0056"` (U+2022 bullet) is a string, non-empty, length 12
≤ 64, contains no control character. `projectOptionalText` returns the
normalized string. `projectAccountMetadataInput` (lines 86–93) returns
the DTO. The SQL metadata branch (migration #38 lines 49–73) similarly
accepts the masked string: it only checks `length between 1 and 64`
(passes) and `~ '[[:cntrl:]]'` (passes — `•` is not a control
character).

**The server would persist the masked display value as the canonical
`account_number`**. This is destructive and silent: no warning, no
audit event mentioning masked value, just a corrupted row.

This is finding **F-03** in my earlier re-audit — promoted to
**BLOCKER** in this addendum (F-00), because the KEEP absence makes
this persistence path the **default outcome** for the `payment_edit`-only
actor scenario, not a corner case.

### Q3. Can an actor with only `payment_edit` call the route / RPC?

**Answer: YES.**

`patchDraftPayment` in `payment-api.ts` calls
`direct_entry_read_projection` for the catalog (only when
`payment.state === "provided"` in legacy mode), then calls
`updatePayment` on the repository, which calls
`direct_entry_update_payment(uuid,uuid,uuid,integer,integer,jsonb,text,text)`
RPC. The RPC's authority check is
`direct_entry_assert_payment_document_access(..., 'payment_edit')`
(migration #38 line 102). This helper accepts DRAFT entries with
`entry_own / entry_team / admin` scope, and SUBMITTED entries with the
`payment_edit` capability.

**Critically: the RPC authority check requires `payment_edit`, but
makes no claim about `payment_view`.** An actor with only
`payment_edit` can call the route and the RPC. The actor just cannot
read the raw STK back from the projection. This is the scenario in
Q1+Q2.

### Q4. Can an actor with both `payment_view` and `payment_edit` read the raw STK for full replacement?

**Answer: YES (but this does not save the contract).**

When `v_payment = true` (payment_view granted), the projection returns
the raw `account_number`, `bank_id`, `bank_name`, `account_holder_name`
in `direct_entry_read_projection`. The actor can read the raw STK, copy
it into the metadata request body, and send it back. The server
persists the same value. **No data loss in this case.**

**However**, this does not save the contract for two reasons:

1. The `payment_view / payment_edit` capability split is a
   **security policy**: they are documented as two independent
   capabilities. Forcing `payment_view` for `payment_edit`-only actors
   to enable "safe edits" would violate the capability model (rule 17
   of the brief).
2. The masked projection is the **default** read for any actor who does
   not have `payment_view`. For these actors, there is **no safe KEEP
   path** even when they have `payment_edit`.

The contract is **unsafe by design for any actor without
`payment_view`**, regardless of whether a higher-privileged actor can
use the contract safely.

### Q5. Does empty / null mean CLEAR or KEEP in the current contract?

**Answer: CLEAR.**

In `projectOptionalText`:

- `null` (JSON null literal) → returns `null` (the SQL layer then treats
  it as `nullif(btrim(p_payment->>'account_number', v_trim_chars), '')`
  which is `null`).
- Blank string or whitespace-only string → trimmed to empty → returns
  `null` (same SQL nullification).
- Omitted key → not allowed: `exactKeys(value, [...])` rejects the
  body.

So `null` and blank both mean **CLEAR**, not KEEP. There is **no way
to express KEEP** with the current contract.

### Q6. Can a load failure or projection lacking a field cause destructive clear?

**Answer: YES (via the masked-path scenario).**

`patchDraftPayment` calls `direct_entry_read_projection` for the
catalog (only when `payment.state === "provided"` in legacy mode). For
the metadata branch, **no read projection is required** — the route
forwards the request body to the repository's `updatePayment`, which
forwards it to the RPC. The RPC does not look at the projection at
all in the metadata branch. The route only validates the body shape
(`projectRequest`) and the table contents (`projectAccountMetadataInput`).

A load failure of the read projection (e.g. read returns 500 because
the DB is unreachable) is unrelated to the metadata edit. The
metadata edit does not depend on the read projection; it only
depends on the request body. So load failure does not directly cause
destructive clear.

**However**, the **projection lack** scenario is the real concern: if
the actor does not have `payment_view`, the projection returns only
the masked STK. The actor cannot reconstruct the raw STK to send
back. The only choices are:

- Send `null` → destructive clear.
- Send masked value → destructive corruption.

Both are destructive. There is no third option.

### Q7. Does an all-null request clear-all?

**Answer: YES.**

`{ account_number: null, bank_name: null, account_holder_name: null }`
sets:

```sql
v_payment_state := 'omitted'
v_account_number := null
v_bank_id := null
v_bank_name := null
v_account_holder_name := null
```

(migration #38 lines 79–84). The next `insert on conflict do update`
writes `(null, null, null, 'omitted', null)` (state, account_number,
bank_id, bank_name, account_holder_name).

The PGlite test `r4s03_metadata_clear` asserts this:
`{state: 'omitted', account_number: null, bank_id: null, bank_name: null,
account_holder_name: null, version: 5}`.

This is **intentional destructive clear**. The PGlite test labels it
`"r4s03_metadata_clear"` and the handoff documents it as "all-null
metadata replacement clears the legacy bank ID as well".

The risk is that an actor who **did not intend** to clear can send
`null` for the STK as the only safe-looking option (per Q5 / Q6).

### Q8. How is legacy `bank_id` handled when a different field is updated?

**Answer: Cleared to NULL by the metadata branch.**

The metadata branch (migration #38 lines 47–84) sets
`v_bank_id := null` unconditionally. The subsequent `insert on conflict
do update` writes `bank_id = excluded.bank_id` which is `null`. So
**any** metadata edit (including holder-only or bank_name-only) clears
the legacy `bank_id`.

The legacy branch (lines 85–99) does not touch `bank_name` directly
because the `case when … when excluded.state = 'provided' then
public.direct_entry_payments.bank_name …` clause preserves
`bank_name` from the existing row.

The interaction is asymmetric: the metadata branch clears `bank_id`
but the legacy branch preserves `bank_name`. This is by design (the
metadata branch always represents a "I'm telling you the new free-text
metadata, no catalog authority anymore" intent). The asymmetry is
**not** a security issue per se, but it is the
**destructive-clear-masking-pattern interaction** that produces the
BLOCKER.

### Q9. Do existing tests miss the edit-one-field-while-keeping-masked-account case?

**Answer: YES.**

Reviewing `scripts/p1.6-i04c3-r4-s03-db.test.mjs`:

The test seeds `proposer` with capabilities `["entry_create",
"submission_create", "entry_own", "change_request_create",
"change_review"]` (via `seedChangeRequestFixture` in
`scripts/lib/s04c-read-fixture.mjs` line 130). **`payment_view` is
not granted in the seed**. The test runs `r4s03_metadata_partial` with
`{ account_number: " 000012340056 ", bank_name: "Ngân hàng Á Châu",
account_holder_name: null }` — this is a **full-replacement** payload,
not an "edit bank_name while keeping account_number" scenario. The
test asserts the persisted row has `account_number = "000012340056"` —
but this is because **the test author had to know the raw STK to
hardcode it in the test**, which is exactly what an actor without
`payment_view` cannot do.

There is **no test** that exercises the destructive-by-default
scenario:

1. Seed a row with a known `account_number` (e.g. `"000012340056"`)
   and a known `bank_name` (e.g. `"Old Bank"`).
2. Strip the actor's `payment_view` capability (or never grant it).
3. Issue a metadata edit that **intends** to keep the STK but only
   change `bank_name`.
4. With the current contract, the only options are:
   - `account_number: null` → STK is cleared.
   - `account_number: "••••••••0056"` → masked value is persisted.
   - `account_number: "000012340056"` (raw) → if the actor knew it.
5. The expected outcome for "keep STK, change bank_name" is
   `account_number = "000012340056"` (unchanged), `bank_name = "New
   Bank"`. With the current contract, this outcome is **only
   reachable if the actor already knew the raw STK**.

The PGlite test `r4s03_metadata_partial` uses a hardcoded raw STK
because **the test author was simulating a privileged actor**. A real
actor without `payment_view` cannot produce the same request body
without corrupting the row.

**Missing test**: `r4s03_metadata_keep_masked_account` — should
seed a row, strip `payment_view`, attempt to edit only `bank_name`,
and assert either:

- (current behavior) the request is rejected with `400 PAYMENT_INVALID`
  because there is no safe way to express "keep STK", **OR**
- (fixed behavior, with KEEP operation) the request succeeds with
  `account_number` unchanged server-side, `bank_name` updated.

`direct_entry_payload_hash(jsonb_build_object(

## 3. T0-locked repair design (per-field explicit operations)

### 3.1 Request shape

Per-field explicit operation, applied independently to
`account_number`, `bank_name`, `account_holder_name`. The shape is a
semantic example; the exact JSON shape is T1B's design choice.

```jsonc
{
  "expected_entry_version": 3,
  "expected_payment_version": 2,
  "reason": "Edit bank name",
  "idempotency_key": "<uuid>",

  "account_metadata": {
    "account_number":      { "op": "keep" },                                    // KEEP: read current value inside the SQL transaction
    "bank_name":           { "op": "set",  "value": "Ngân hàng Á Châu" },        // SET: validate and overwrite
    "account_holder_name": { "op": "clear" }                                     // CLEAR: set to NULL
  }
}
```

Each field is an object with:

- `op`: `"keep"`, `"set"`, or `"clear"` (mandatory).
- `value`: required iff `op === "set"`. Must satisfy the existing type /
  length / control-char bounds (digits 1..64 for `account_number`,
  text 1..256 for `bank_name` and `account_holder_name`). Leading zeros
  preserved.
- No `value` for `keep` or `clear`. Sending `value` with `keep` or
  `clear` is a 400 (`PAYMENT_INVALID`).

### 3.2 Required behaviors

1. **Each field must have an explicit operation.** Omitted field
   ⇒ `400 PAYMENT_INVALID` (no sentinel-less "keep").
2. **`op: "keep"` reads current value inside trusted SQL transaction.**
   The RPC performs a `SELECT direct_entry_payments.account_number
   WHERE entry_id = p_entry_id FOR UPDATE` (the row is already locked
   earlier in the function via `select * into v_entry from
   public.direct_entries … for update` and `select * into v_payment
   from public.direct_entry_payments … for update`). The current value
   is read from the locked row; the raw STK is **never returned to the
   client** (the response is `{entry_id, entry_version,
   payment_version}`).
3. **`op: "clear"` sets the field to NULL.** No `value` allowed.
4. **`op: "set"` overwrites with the supplied `value`.** Validation
   unchanged from the current contract (length / control / digits for
   STK).
5. **All-KEEP rejected as no-op.** No increment, no audit, no
   idempotency entry. Return `400 PAYMENT_INVALID` or a specific
   `noop_no_change` code.
6. **`op: "set" / "clear"` for `bank_name` ⇒ `bank_id = NULL`** (same
   as the current metadata branch).
7. **`op: "keep"` for `bank_name` ⇒ preserve `bank_name` and
   `bank_id`** (current row values, both columns untouched).
8. **Clear-all = all three fields CLEAR, `bank_id = NULL`, state =
   `'omitted'`** (consistent with the current clear-all semantics).
9. **OCC / idempotency fingerprint** must include the operation map
   (KEEP / SET / CLEAR for each field) and the SET values. Same
   payload + same ops + same key ⇒ same fingerprint ⇒ idempotent
   replay. Same key + different ops or different SET values ⇒ conflict
   (`22023 idempotency key reused with different input`).
10. **Audit / revision remain free of raw values.** `changed_fields`
    continues to be `array['payment']` (no per-field expansion).
    `direct_entry_write_revision` continues to use the foundation
    `direct_entry_entry_snapshot` which **does not include raw
    `account_number`** (foundation redaction).
11. **Capability model unchanged.** `payment_view / payment_edit`
    compatibility guards only. No requirement to grant
    `payment_view` for `payment_edit`-only actors. The server-side
    read inside the trusted SQL transaction is the only acceptable
    KEEP path.
12. **Banks=0 compatibility preserved.** The KEEP path reads
    `bank_id` from the locked row; if `bank_id` was non-null but the
    bank is now inactive (or banks=0), the KEEP path **preserves the
    existing `bank_id`** without re-validating active status. The
    active-bank validation only fires when a new `bank_id` is set
    via the legacy `payment` path.

### 3.3 Response projection

Response is unchanged from current contract:
`{entry_id, entry_version, payment_version}`. No raw STK, no
`bank_name`, no `account_holder_name`. The KEEP path is fully
server-side; the client cannot observe the raw STK through the
response.

## 5. Destructive scenario (concrete)

**Setup**:

- Entry `e1` with payment row
  `(state='provided', account_number='000012340056', bank_id=null,
  bank_name='Old Bank', account_holder_name='Holder', version=1)`.
- Actor `u1` with capabilities `['entry_own', 'payment_edit']` (no
  `payment_view`).

**Read**:

- `direct_entry_read_projection(u1, e1)` returns
  `{payment: {state: 'provided', account_number: '••••••••0056',
  version: 1}}` (masked).

**Intended edit**: change `bank_name` from `'Old Bank'` to `'New
Bank'` while preserving everything else.

**Required request body (per the current contract)**:

```json
{
  "expected_entry_version": 1,
  "expected_payment_version": 1,
  "reason": "Update bank name",
  "idempotency_key": "<uuid>",
  "account_metadata": {
    "account_number": "...STK...",
    "bank_name": "New Bank",
    "account_holder_name": "...Holder..."
  }
}
```

The actor **cannot fill in** the STK or holder fields. Their only
options:

1. `account_number: null, account_holder_name: null` ⇒ destructive
   clear of STK + holder. After update, the row is
   `(state='provided', account_number=null, bank_id=null,
   bank_name='New Bank', account_holder_name=null, version=2)`. **STK
   is lost.**
2. `account_number: "••••••••0056", account_holder_name: "Holder"` ⇒
   the server persists the masked value. After update, the row is
   `(state='provided', account_number='••••••••0056', bank_id=null,
   bank_name='New Bank', account_holder_name='Holder', version=2)`.
   **STK is corrupted with masked value.**
3. **There is no third option.**

This is the BLOCKER scenario. The actor cannot perform a non-
destructive edit without already knowing the raw STK (which the
security policy says they should not need to know).

**After the repair (T0-locked)**:

```json
{
  "expected_entry_version": 1,
  "expected_payment_version": 1,
  "reason": "Update bank name",
  "idempotency_key": "<uuid>",
  "account_metadata": {
    "account_number":      { "op": "keep" },
    "bank_name":           { "op": "set", "value": "New Bank" },
    "account_holder_name": { "op": "keep" }
  }
}
```

The server reads the current `account_number` and
`account_holder_name` from the locked row inside the SQL transaction,
writes `bank_name='New Bank'`, preserves everything else. The actor
never sees the raw STK.
