## 1. What is implemented today (source-verified)

### 1.1 Bank table — `direct_entry_banks`

`supabase/migrations/20261002170000_p1_6_direct_entry_foundation.sql:185–193`

```sql
create table public.direct_entry_banks (
  bank_id text primary key check (bank_id ~ '^[a-zA-Z0-9][a-zA-Z0-9._:-]{0,127}$'),
  display_name text not null check (length(btrim(display_name)) between 1 and 256),
  active boolean not null default true,
  version integer not null default 1 check (version >= 1)
);
```

Properties:

| Aspect | Value | Source |
| --- | --- | --- |
| Key | `bank_id text PK` with fixed regex `^[a-zA-Z0-9][a-zA-Z0-9._:-]{0,127}$` | `20261002170000_…:185–193` |
| Display name | `text not null`, length 1–256 after `btrim` | same |
| Active | `boolean not null default true` | same |
| Effective dating | **NONE** (no `valid_from` / `valid_to` columns) | derived |
| Short name | **NONE** | derived |
| Source / provenance column | **NONE** | derived |
| Surrogate key | **NONE** (text PK is the canonical identifier) | derived |
| `version` column | `integer not null default 1 check (>= 1)` — internal row-version, not a provenance marker | derived |

**Key stability** is enforced by the **PK itself**. A bank row cannot be silently renamed — renaming requires changing `bank_id`, which is the FK target of `direct_entry_payments.bank_id` (`20261002170000_…:237`) with `on delete restrict`. Today there is **no UPDATE RPC** for banks; renames would be a manual DML by an `Owner` (only). There is also no `direct_entry_*` trigger that propagates a rename — and `direct_entry_payments` rows reference `bank_id` text, so renaming a bank breaks every historical payment.

### 1.2 Trigger — `direct_entry_payment_active_bank`

`supabase/migrations/20261002170000_p1_6_direct_entry_foundation.sql:617–633`

```sql
create or replace function public.direct_entry_validate_payment()
returns trigger language plpgsql set search_path = pg_catalog, public
as $$
begin
  if new.state = 'provided' and not exists (
    select 1 from public.direct_entry_banks b
     where b.bank_id = new.bank_id and b.active
  ) then
    raise exception 'bank is not active' using errcode = '23514';
  end if;
  return new;
end;
$$;

create trigger direct_entry_payment_active_bank
  before insert or update on public.direct_entry_payments
  for each row execute function public.direct_entry_validate_payment();
```

This is a **DB-layer safety net**. It rejects any `direct_entries.payment` INSERT/UPDATE whose `bank_id` is missing from the active set. The check is **`active=true` only** — there is no `valid_from` / `valid_to` window. The trigger is the **only DB guarantee** that an active payment bank really exists.

### 1.3 RLS / FORCE RLS / grants on `direct_entry_banks`

`supabase/migrations/20261002170000_p1_6_direct_entry_foundation.sql:3226–3246` includes `direct_entry_in_bank` in the bulk RLS loop:

- `enable row level security` and `force row level security` — every role is subjected to RLS, including table owner.
- `revoke all on table public.direct_entry_banks from public, anon, authenticated, service_role` — **no DML grant to API roles**.

**Result**: there is **no API path** (anon / authenticated / service_role) to read or write the bank catalog outside a SECURITY DEFINER function. Today the only readers are `direct_entry_input_catalog` (foundation-projection RPC) and `direct_entry_apply_change_item` / `direct_entry_update_payment` / `direct_entry_validate_payment` (write paths).

### 1.4 Catalog projection — `direct_entry_input_catalog`

`supabase/migrations/20261003210000_p1_6_w04_s04a_payment_projection.sql:5–84`

Returns `{ effective_date, projects[], recruiters[], banks[] }`. Banks:

```sql
'banks', coalesce((
  select jsonb_agg(jsonb_build_object(
    'bank_id', b.bank_id, 'display_name', b.display_name
  ) order by b.display_name, b.bank_id)
    from public.direct_entry_banks b
   where b.active
), '[]'::jsonb)
```

- **Ordering**: `display_name, bank_id` (alphabetical on display name; PK is tiebreaker). This is the **only** ordering the UI sees.
- **Filter**: `active = true`. The TS client (`write-repository.ts:251–291`) enforces duplicate-by-id, regex, and length; the RPC enforces `active=true`.
- **Empty case**: returns `'[]'::jsonb`; the API layer returns `banks: []`. Every payment-bearing row that calls the catalog will see an empty bank set (see §1.5).

The RPC is `security definer`, `revoke all … from public, anon, authenticated`, `grant execute to service_role` (`…:179–180`). It is reachable via the `/api/direct-entry/catalog` Next.js route (already in source).

### 1.5 Payment write path — `direct_entry_update_payment` (TS layer)

`src/lib/direct-entry/payment-api.ts:127–139`:

```ts
if (parsed.payment.state === "provided") {
  const catalog = await dependencies.repository.loadInputCatalog({
    ...trustedActor,
    effective_date: entry.first_work_date,
  });
  if (!catalog.ok) {
    if (catalog.kind === "denied") return fail("PAYMENT_DENIED", 403);
    console.error("[direct-entry] payment bank catalog unavailable");
    return fail("PAYMENT_UNAVAILABLE", 500);
  }
  const activeBankIds = new Set(catalog.data.banks.map(({ bank_id }) => bank_id));
  if (!projectPaymentInput(parsed.payment, activeBankIds)) {
    return fail("BANK_INVALID", 400);
  }
}
```

**Mechanism** (failure-closed): when payment state is `provided`, the API calls `loadInputCatalog` for `entry.first_work_date`. The set of active bank_ids is built from the catalog response. `projectPaymentInput` (in `payment-contract.ts:47–64`) verifies the user-supplied `bank_id` against `activeBankIds`. **If the catalog is empty (`banks: []`), every `provided` payment is rejected with `BANK_INVALID` 400 before reaching the DB.** This is confirmed by `payment-api.test.mjs:165–176` (test "unknown/inactive bank, invalid versions, and missing reason fail closed").

**Even with an empty catalog**: `payment_state = omitted | unknown | intentionally_blank` (non-`provided`) is **still allowed** — `projectPaymentInput` returns a valid object with null fields. So a user can save a `direct_entry_payments` row with no bank at all, by leaving the state non-`provided`.

### 1.8 I04C2B catalog bootstrap — boundary, NOT banks

`supabase/migrations/20261005050000_p1_6_i04c2b_catalog_bootstrap_boundary.sql` introduces a `direct_entry_catalog_bootstrap_executor` role (NOLOGIN, NOINHERIT, NOBYPASSRLS) and three SECURITY DEFINER RPCs:

The migration also has a comprehensive `do $$ … end $$` security check (lines 466–614) that:

- Asserts the migration installer is **not** `service_role / anon / authenticated / direct_entry_catalog_bootstrap_executor`.
- Asserts the executor role is `NOLOGIN, NOINHERIT, NOBYPASSRLS`.
- Asserts `service_role`, `anon`, `authenticated` have **no INSERT/UPDATE/DELETE/TRUNCATE** privileges on `direct_entry_catalog_bootstrap_runs, direct_entry_projects, recruiters, teams, recruiter_aliases, recruiter_provider_memberships, recruiter_team_memberships, direct_entry_audit_events` (lines 569–583).
- Asserts the projection function is **not** API-executable.
- Asserts `direct_entry_catalog_bootstrap_plan` and `direct_entry_apply_catalog_bootstrap` are **only** executable by `service_role`.

**Bank table is intentionally excluded from both the grant list and the policy coverage of this boundary** — banks are not derived from `daily_recruitment_breakdown` and need an authoritative Owner-supplied input. The boundary also grants the executor role `select on direct_entry_banks` (line 39) — a **read-only** view of banks — but no INSERT/UPDATE/DELETE.

**Conclusion**: the I04C2B boundary is the **template** for any future bank boundary (audited, idempotent, source-fingerprint-gated, advisory-locked, NOLOGIN executor). It does **not** populate banks today.

## 3. Missing authoritative bank dataset — Owner input schema

Per **D14** (`13bed05` §1.2): **"Bank catalog is an Owner-approved versioned list shipped in the master-catalog mutation boundary. No live bank API at runtime; never fabricate bank values."** The Owner must supply the following per row.

### 3.1 Minimum Owner-supplied fields (proposed)

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `bank_id` | text | yes | Canonical code/key. Must match `^[a-zA-Z0-9][a-zA-Z0-9._:-]{0,127}$` (PK regex, foundation 185–186). Examples: `vcb`, `tcb.vc`, `bidv`, `mb-bank`, `techcombank`, `vpbank`, `acb`, `sacombank`, `hdbank`, `vib`, `shb`, `ocb`, `tpbank`, `vietcapital-bank`, `seabank`. Owner decides between BIN-style code (`vcb`), SWIFT/BIC (`vcbvvnvx`), or Vietnamese mnemonic (`vietcombank`); the audit does **not** prescribe. |
| `display_name` | text | yes | Vietnamese display name. 1–256 chars after `btrim`. Example: `Ngân hàng TMCP Ngoại thương Việt Nam (Vietcombank)`. |
| `short_name` | text | optional | Short Vietnamese label. 1–64 chars. Used by UI dropdowns. **Not in today's schema** (gap G-BANK-4). |
| `valid_from` | date | optional (TBD) | First effective date. If the dataset is "current", omit and default to `1900-01-01`. |
| `valid_to` | date | optional (TBD) | Last effective date (half-open). `null` means "still active". Required only if banks ever cease to exist (mergers, license revocations). |
| `active` | boolean | yes | Today schema. With `valid_from`/`valid_to` added, `active` could become derived (`valid_from <= effective_date < coalesce(valid_to, infinity)`). |
| `provenance` | text | optional | Short tag like `owner-2026-10-XX`, `sbv-q4-2026`, `napas-2026`. **Not in today's schema** (gap G-BANK-5). Recorded in the audit event `changed_fields` and/or a new column. |
| `notes` | text | optional | Short note (1–400 chars). **Not in today's schema**. |

### 3.2 Owner-supplied dataset format

The audit recommends a **single CSV or JSON file** with the fields above. The file is **not** loaded automatically; it is the input to the `direct_entry_apply_bank_bootstrap` RPC (gap G-BANK-1 / G-BANK-6). Suggested format:

```csv
bank_id,display_name,short_name,active,provenance
vcb,"Ngân hàng TMCP Ngoại thương Việt Nam",Vietcombank,true,owner-2026-10-XX
tcb.vc,"Ngân hàng TMCP Kỹ thương Việt Nam",Techcombank,true,owner-2026-10-XX
bidv,"Ngân hàng TMCP Đầu tư và Phát triển Việt Nam",BIDV,true,owner-2026-10-XX
…
```

The audit does **not** enumerate the dataset (D14: never fabricate bank values). The Owner supplies the actual list with the canonical codes.

### 3.3 What T0 must lock

1. **Bank id vocabulary**: Owner decides whether to use BIN, SWIFT/BIC, or Vietnamese mnemonic. The audit recommends **BIN/SWIFT-style codes** because they survive renames; Owner decides.
2. **Display name**: Vietnamese (`Ngân hàng TMCP Ngoại thương Việt Nam`) or English (`Joint Stock Commercial Bank for Foreign Trade of Vietnam`)? The audit recommends **Vietnamese display_name + optional short_name**; the API layer never returns English unless an explicit i18n is added (D14).
3. **Effective dating** (G-BANK-3): add `valid_from date` / `valid_to date` columns? Or stay with `active boolean` only? The audit recommends **adding `valid_from`/`valid_to`** if the dataset encodes historical validity, otherwise keep `active` only. **Lock this before T1B scopes.**
5. **Provenance column** (G-BANK-5): add a `provenance text` column to record the source? The audit recommends **yes**, for audit trail.
6. **Short name** (G-BANK-4): add `short_name text`? Recommended **yes** if the dropdown UX needs it; otherwise display_name is enough.

### 3.4 What the audit explicitly does NOT do

- **No fabricated dataset.** T1C does not list any bank by name; the Owner provides the dataset.
- **No scraped list.** No external API call, no SBV/NAPAS scrape, no SWIFT download.
- **No free-text bank name as authority.** `direct_entry_banks` is the only authority; any free-text "Ngân hàng ABC" from a paste is rejected.
- **No use of `account_number` / `account_holder_name` in this audit.** Per T0 D9, no PII in logs, no PII in storage key, no PII in idempotency key. The audit only deals with `bank_id` and `display_name`.

## 4. Capability union & authority rules

### 4.1 Capability union (D18: no new capability)

The bank-catalog activation must reuse the existing 21 capabilities. Concretely:

| Action | Required capabilities | Source |
| --- | --- | --- |
| **Read** bank catalog (input projection) | `entry_create` **OR** `entry_own` (today's gate) | `20261003210000_…:24–32` |
| **Read** banks for `payment_view` | `payment_view` (used in `payment-api.ts:127–139` to gate the catalog load) | `src/lib/direct-entry/payment-api.ts:127` |
| **Bootstrap banks (initial insert, one-time, audited)** | `entry_admin` **AND** `recruiter_master_manage` **AND** `team_master_manage` (all three, distinct, on the same `app_user_id`); same gate as I04C2B | `20261005050000_…:255–266` |
| **Deactivate bank** (e.g. merger) | `entry_admin` **AND** `recruiter_master_manage` (proposed; same as master-data mutations) | T1B design |
| **Owner-only catalog bootstrap apply** | `direct_entry_catalog_bootstrap_executor` role (NOLOGIN, NOINHERIT, NOBYPASSRLS); invoked via `service_role` | `20261005050000_…:469–530` |

**No new capability** is created in this audit. `recruiter_master_manage` and `team_master_manage` are already in the grants table; their combined authority covers master-data mutations including banks.

### 4.2 Authority & scope rules (mirrors I04C2B)

1. **Actor must be the Owner**: `direct_entry_app_users.auth_subject = auth_subject` and `enabled = true`. Disabled users are rejected.
2. **Capability check at request entry** (not at DML time). The plan RPC checks the 3-capability union; the apply RPC re-checks.
3. **Idempotency**: `direct_entry_*` writes use `direct_entry_rpc_idempotency` (foundation) — every bank-bootstrap RPC must accept `p_idempotency_key text` and replay without duplicate inserts.
4. **Source fingerprint**: like `direct_entry_catalog_bootstrap_projection.source_fingerprint = sha256(...)`, the bank bootstrap should accept `p_expected_source_fingerprint` and reject if the catalog response fingerprint mismatches (anti-tamper).
6. **Service-role table DML denial**: `service_role`, `anon`, `authenticated` must have **no INSERT/UPDATE/DELETE/TRUNCATE** on `direct_entry_banks` (mirroring the assertion in `20261005050000_…:569–583`). The migration's `do $$ … end $$` block can be extended with one extra table name.
7. **Owner check-in / check-out**: a separate `direct_entry_bank_bootstrap_runs` table (analogous to `direct_entry_catalog_bootstrap_runs`) records `run_id, app_user_id, source_fingerprint, bank_count, status, idempotency_key, reason_id, created_at` with `unique (app_user_id, idempotency_key)`.
8. **Audit**: every successful apply inserts one `direct_entry_audit_events` row with `action='bank_bootstrap'`, `capability='entry_admin'`, `resource_ref='bank-bootstrap:'+run_id::text`, `scope_kind='all'`, `outcome='APPLIED'`, `changed_fields=array['direct_entry_banks']` (entity name only; no raw values).

### 4.3 Service-role DML denial — explicit reminder

The T1C matrix at `13bed05` §6 G12/G13 already locks **D20**: pre-#32 revisions are not rewritten. The bank boundary must follow the same principle: **service-role cannot raw-DML** the bank table even after banks exist. Only the audited bootstrap RPC may insert; only an authenticated edition of an update RPC may update.

## 5. Implementation recommendation: separate RPC vs reusable versioned boundary

### 5.1 Two options considered

**Option A — Dedicated one-time audited RPC** (analogue of I04C2B):
- New role `direct_entry_bank_bootstrap_executor` (NOLOGIN, NOINHERIT, NOBYPASSRLS).
- Three SECURITY DEFINER RPCs: `direct_entry_bank_bootstrap_projection()`, `direct_entry_bank_bootstrap_plan(p_auth_subject, p_app_user_id)`, `direct_entry_apply_bank_bootstrap(p_auth_subject, p_app_user_id, p_expected_source_fingerprint, p_idempotency_key, p_reason)`.
- New ledger table `direct_entry_bank_bootstrap_runs`.
- Migration `2026????????_p1_6_i04c3_a02_bank_bootstrap_boundary.sql`.

**Option B — Reusable versioned master-data boundary** (a single boundary for projects / recruiters / teams / banks):
- Extend the I04C2B role with INSERT on `direct_entry_banks` and policies to read/insert the bank table.
- Extend `direct_entry_catalog_bootstrap_projection()` to also include `banks[]` from a **separate** authoritative input source (not `daily_recruitment_breakdown`).
- Extend `direct_entry_apply_catalog_bootstrap()` to insert `direct_entry_banks` rows.

### 5.2 Recommendation: Option A (separate bank boundary)

Rationale:

1. **Source-of-truth is different**. I04C2B derives projects/recruiters/teams from `daily_recruitment_breakdown` (a verifiable, deterministic source). Banks have **no equivalent in `daily_recruitment_breakdown`** — they are an Owner-curated list. Mixing the two sources in one fingerprint breaks the existing audit guarantee.
2. **Re-bootstrap semantics differ**. Projects/recruiters/teams are bootstrapped once per environment (the I04C2B plan RPC requires `catalog_empty = true` and fails closed if any catalog table is non-empty). Banks may need to be **re-applied** when a row is deactivated (e.g. merger), so the bank boundary must support **append-only with versioning**, not just one-shot insert.
3. **Capability union differs**. I04C2B requires `entry_admin + recruiter_master_manage + team_master_manage`. Bank bootstrap likely requires `entry_admin + recruiter_master_manage` only (no team business). Reusing the same union forces a stronger gate than necessary.
4. **Idempotency / replay differ**. I04C2B's `direct_entry_catalog_bootstrap_runs` has `unique (app_user_id, idempotency_key)`; replay with same fingerprint returns `ALREADY_APPLIED`; replay with different fingerprint raises `catalog_bootstrap_replay_conflict` (lines 366–378). The bank boundary should follow the same pattern but may need **multiple successful runs** over the lifetime (e.g. add a new bank, deactivate another), which Option B's one-shot design does not allow.

### 5.3 Option A sketch

```text
supabase/migrations/2026????????_p1_6_i04c3_a02_bank_bootstrap_boundary.sql
  -- Mirrors 20261005050000_p1_6_i04c2b_catalog_bootstrap_boundary.sql, but for banks.
  -- NOLOGIN/NOINHERIT/NOBYPASSRLS role: direct_entry_bank_bootstrap_executor.
  -- Three SECURITY DEFINER RPCs:
  --   direct_entry_bank_bootstrap_projection()  -- reads Owner-supplied source-of-truth (NOT daily_recruitment_breakdown)
  --   direct_entry_bank_bootstrap_plan(uuid, uuid)
  --   direct_entry_apply_bank_bootstrap(uuid, uuid, text, text, text)
  -- Ledger table: direct_entry_bank_bootstrap_runs.
  -- do $$ ... end $$ security block (mirrors lines 466-614).
```

**Source-of-truth for Option A**: the Owner-supplied dataset (§3). The dataset is committed to the repo (e.g. `supabase/seeds/banks/v1.csv`) and the migration computes a fingerprint of the file at install time. The apply RPC re-computes the fingerprint and rejects on mismatch (anti-tamper).

### 5.4 When to consider Option B

If Owner agrees to a **single, unified master-data surface** (projects, recruiters, teams, banks, all from a single JSON/YAML committed to the repo), Option B becomes attractive. **Today's split is cleanest with Option A.**

## 6. Duplicate / effective-dating / idempotency / audit / rollback rules

### 6.1 Duplicate rules

| Scenario | Behavior | Source / decision |
| --- | --- | --- |
| Two rows with same `bank_id` in same Owner-supplied file | reject entire apply with `BANK_SOURCE_DUPLICATE` | new (T1B) |
| Two rows with same `display_name` (after `btrim`) in same file | reject (catalog ordering on `display_name` would be ambiguous) | new |
| Re-applying with same idempotency key + same fingerprint | return `ALREADY_APPLIED` | mirror I04C2B |
| Re-applying with same idempotency key + **different** fingerprint | raise `BANK_BOOTSTRAP_REPLAY_CONFLICT` (23505) | mirror I04C2B line 367–368 |
| `bank_id` already exists in `direct_entry_banks` | reject with `BANK_BOOTSTRAP_TARGET_NOT_EMPTY` (23505) on **initial** apply; for **re-apply** (versioned), `upsert version` increments `version` | new |
| `direct_entry_payments.bank_id` references a `bank_id` that is later deactivated | DB trigger `direct_entry_payment_active_bank` rejects **new** payments but **does not** reject existing rows (D20: revisions not rewritten; legacy data stays valid as historical fact). | `20261002170000_…:617–633` |

### 6.2 Key stability

| Scenario | Behavior | Source / decision |
| --- | --- | --- |
| Rename a bank (`bank_id` change) | **NOT ALLOWED** via bank bootstrap. Owner must (a) deactivate old `bank_id` and (b) insert new `bank_id`; historical payment rows referencing the old `bank_id` keep their reference (DB trigger only checks `active=true` on **new** writes). | derived from FK `on delete restrict` + D20 |
| Delete a bank (`DELETE FROM direct_entry_banks WHERE bank_id = ?`) | **BLOCKED** by FK `on delete restrict` if any `direct_entry_payments.bank_id` references it. | derived |
| Re-activate a previously-deactivated bank | allowed via a future `direct_entry_update_bank_active(uuid, bank_id, active, reason)` RPC (T1B). | new |

### 6.3 Effective-dating rules (proposed; pending T0 lock per G-BANK-3)

If T0 chooses to **add `valid_from date` / `valid_to date`** columns:

| Scenario | Behavior |
| --- | --- |
| A row's effective window is `[valid_from, valid_to)` (half-open) | `valid_to IS NULL` means "still active" (infinite) |
| Read projection filter | `active=true AND valid_from <= effective_date < COALESCE(valid_to, 'infinity'::date)` (TBD; the half-open convention mirrors `recruiter_provider_memberships`) |
| Overlap rule | No two rows may overlap on `(bank_id, [valid_from, valid_to))`. Rejected with `BANK_VALIDITY_OVERLAP`. |
| Deactivation | set `valid_to = current_date` for the old row; insert a new row with `valid_from = current_date` if there is a successor; or set `active = false` for the old row and leave `valid_to` null (decision needed). |

If T0 chooses to **stay with `active boolean` only**, this section is skipped and the trigger stays as-is. **Lock this before T1B scopes.**

### 6.4 Idempotency

- `direct_entry_apply_bank_bootstrap` accepts `p_idempotency_key text` (regex `^[A-Za-z0-9._:-]{1,128}$`, same as I04C2B).
- Replay with same `(app_user_id, idempotency_key)` returns the cached response (mirror `direct_entry_idempotency_begin`/`direct_entry_idempotency_finish` in `20261002170000_…`).
- Idempotency key contains **no PII** (T0 D9). No `bank_id` literal in the key (the fingerprint already commits to the dataset).

### 6.5 Audit field-name-only policy (T0 D9)

- `direct_entry_audit_events.changed_fields` = `array['direct_entry_banks']` — entity name only.
- `direct_entry_audit_events.resource_ref` = `'bank-bootstrap:'+run_id::text` (UUID-based; no `bank_id` literal).
- Log lines (`console.error`/`console.warn`) must not contain raw `bank_id` literals or `display_name`. Today the codebase uses `console.error("[direct-entry] payment bank catalog unavailable")` (no PII), so this is already a precedent.

### 6.6 Rollback

- **Bootstrap rollback** (before commit): a single `BEGIN … EXCEPTION WHEN OTHERS THEN ROLLBACK` (mirror I04C2B).
- **Post-commit rollback**: not allowed. The Owner must (a) issue a deactivation RPC for affected `bank_id`s, (b) leave historical `direct_entry_payments.bank_id` references intact (D20), (c) issue a corrective `direct_entry_apply_bank_bootstrap` with a new idempotency key and updated dataset (correcting the upstream file).
- **Audit-trail guarantee**: once `direct_entry_bank_bootstrap_runs` has a row, it stays. Rollbacks do not delete the ledger; they only deactivate bank rows.

### 6.7 Service-role DML denial (mirrors I04C2B)

- `service_role` may **execute** `direct_entry_bank_bootstrap_plan`, `direct_entry_apply_bank_bootstrap` (via grant in migration).
- `service_role` may **NOT** have `INSERT, UPDATE, DELETE, TRUNCATE` on `direct_entry_banks`, `direct_entry_bank_bootstrap_runs`, or `direct_entry_audit_events`. The migration's `do $$ … end $$` security check asserts this.
